# ADR-014：平台服务拆分策略

## 上下文

平台侧需要承载大量能力：定义中心、实例中心、Issue 状态机、知识索引、权限系统、审计日志、能力注册中心、上下文组装层、通知服务、配额管理。需要确定这些能力的部署架构——单体、少量服务还是全面微服务。

## 决策

**按业务域拆分为 6 个服务，每个服务内部模块化。**

### 服务划分

| 服务 | 职责 | 核心能力 |
|------|------|----------|
| **定义服务** | Soul 原型全生命周期 | Soul 压缩包 CRUD、版本管理、配置校验、测试沙箱调度、审核流、上架/下架、能力注册中心 |
| **项目服务** | Project 与成员管理 | Project CRUD、成员与角色管理、Project Objective 管理、配额管理、项目状态机 |
| **运行服务** | 实例与 Body 生命周期 | 实例 CRUD、Body WebSocket 连接管理、上下文组装层、实例状态机、心跳监控、更新与回滚、派发调度 |
| **任务服务** | Issue 全生命周期 | Issue CRUD、structured brief 生成（调用 LLM）、Issue 状态机、TaskEvent 管理、TaskArtifact 管理、联动事件分发 |
| **知识服务** | Wiki + Memory + RAG | Wiki 文档管理、文档分段与向量化、Project Memory 管理、Personal Memory 管理、RAG 检索、记忆加载策略 |
| **治理服务** | 权限 + 审计 + 审批 | 角色/权限管理、审批流、审计日志、风险控制、质量评价 |

### 服务间交互

```
定义服务 ──Soul版本查询──→ 运行服务（上下文组装时获取 Soul）
项目服务 ──Project上下文──→ 运行服务（上下文组装时获取 Project Objective）
项目服务 ──配额校验──→ 运行服务（实例派发时校验配额）
运行服务 ──状态变更──→ 任务服务（实例停止/回收影响 Issue）
任务服务 ──知识检索──→ 知识服务（Issue 执行中 RAG 查询）
任务服务 ──联动事件──→ 前端 WebSocket（模块联动）
任务服务 ──产物沉淀──→ 知识服务（Issue 完成后写 Project Memory）
治理服务 ──权限校验──→ 所有服务（权限拦截）
治理服务 ──审计记录──→ 所有服务（审计写入）
```

### Phase 1 约束

- 每个服务内部模块化，但不拆分子服务
- 服务间通过 REST API 通信，Phase 1 不引入消息队列
- 各服务共享一个数据库实例，按服务分 schema 隔离
- 统一 API Gateway 做路由和鉴权

### M0 阶段要求

在 M0 阶段必须定义：
- 各服务的 API 契约（OpenAPI 规范）
- 共享的数据对象模型
- 服务间调用的错误处理和重试策略
- 统一的身份认证和租户上下文传递

## 被拒绝的替代方案

1. **单体服务**——一个后端应用模块化划分。被拒绝因为 Issue 状态机（频繁轻量操作）和 RAG 检索（重 CPU+IO）的负载特征完全不同，放一起会互相影响。

2. **全面微服务**——每个能力域独立服务（10+ 个服务）。被拒绝因为对当前团队规模来说运维成本过高，服务间通信、调试、部署流水线都是负担。

## 后果

### 正面

- 按业务域拆分，团队可以按域分工
- 各服务独立部署和扩展，负载隔离
- Phase 2 如果某个域（如知识服务）需要独立扩展，已天然隔离
- 与 PRD 分册结构对应，职责清晰

### 负面

- 6 个服务需要 6 套部署配置，运维复杂度高于单体
- 服务间 API 契约必须在 M0 阶段定义好，否则集成成本高
- 分布式事务问题（如实例回收 + Issue 状态变更需要一致性）——Phase 1 用最终一致性 + 补偿机制

## 复审条件

- 当团队规模显著扩大（>20 人）需要更细拆分时
- 当某个服务成为性能瓶颈需要独立优化时
- 当需要引入消息队列替代同步调用时
