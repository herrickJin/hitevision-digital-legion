# ADR-012：Soul 更新三级策略

## 上下文

Soul 原型发布新版本后，已派发的实例需要更新。由于上下文是运行时动态加载的（ADR-009），更新本质上是改实例绑定的 Soul 版本引用。但不同级别的更新对实例的影响不同。

## 决策

**按 Patch / Minor / Major 三级分别处理更新策略。**

### 三级更新定义

| 级别 | 典型变更 | 更新策略 | 实例影响 |
|------|----------|----------|----------|
| Patch | 修改人格描述、新增 Skill 文件、修改约束文案 | 改版本号引用，下次 Issue 自动生效 | 无中断，无需确认 |
| Minor | 新增 Tool、修改知识引用、调整模块布局 | 通知用户确认后改版本号，下次 Issue 生效 | 无中断，需确认 |
| Major | 更换 MCP Server、修改核心工具集、改变职责范围 | 需用户确认 + 创建实例快照 + 可能重启 Body | 可能有中断 |

### 更新流程

```
Soul 原型发布新版本
  → 判断更新级别（Patch / Minor / Major）
  → Patch：自动更新实例的 prototype_version 引用
  → Minor：向项目负责人发通知，确认后更新版本引用
  → Major：
    → 向项目负责人发通知
    → 等待确认
    → 确认后创建实例快照
    → 更新版本引用
    → 如果涉及运行时能力变化（MCP、核心 Tool），可能需要重启 Body
```

### 快照与回滚

- Major 更新前必须创建实例快照（当前 Soul 版本 + 配置状态）
- 更新失败（如新 Soul 加载出错）自动回滚到快照版本
- 快照保留策略由配额管理控制

### 版本号语义

- Soul 压缩包的 manifest.yaml 中维护版本号（Major.Minor.Patch）
- 版本号由定义者在发布时指定，系统不做自动递增

## 被拒绝的替代方案

1. **Phase 1 统一处理，不分级**——所有更新都需要确认 + 快照。被拒绝因为 Patch 级变更（改个文案）也要确认，使用体验差。

2. **所有更新自动生效**——被拒绝因为 Major 更新可能导致实例不可用，用户需要知情权。

## 后果

### 正面

- Patch 级更新无感，不增加使用摩擦
- Major 级更新有保障，用户可以控制风险
- 快照机制提供回滚安全网

### 负面

- 更新级别的判断需要规则定义——谁来判断是 Patch 还是 Major？Phase 1 由定义者在发布时指定，P1 考虑系统自动判断
- Body 重启会中断正在执行的 Issue（见 ADR-013 跨状态机联动）

## 复审条件

- 当更新级别判断不准确导致问题时
- 当需要自动化级别判断时
