# ADR-010：Issue 执行前规划检查

## 上下文

Issue 状态机有 7 个状态，其中"执行中"表示数字员工正在执行任务。但"执行中"的语义应该更精确——是已经在调用工具生成产物，还是在做前期准备？信息不足和越界检测应该在进入执行前完成还是执行中完成？

## 决策

**"执行中"的进入条件：必须先通过上下文组装 + 规划检查。确认信息充足且不越界才进入执行中。**

### 调整后的状态流转

```
待开始
  → [上下文组装 + 规划检查]
    → 信息充足且不越界 → 执行中 → 已完成
    → 信息不足 → 等待补充信息 → [人类补充] → 执行中 → 已完成
    → 越界 → 已拒绝
  → 已取消（人类主动取消）
```

### 规划检查的内容

1. **上下文组装**——加载 Soul 配置、Project Objective、知识通道、权限边界
2. **信息充足性检查**——Agent 根据 structured brief 判断是否有足够信息开始执行
3. **越界检测**——检查任务是否在 Soul 定义的职责范围内

### 不增加状态数量

- 规划检查不对应独立状态
- 它是"待开始 → 执行中"转换的前置条件
- 用户看到的是：确认 Issue → 直接进入执行中（或等待补充信息、或已拒绝）
- 规划检查的耗时应该在 3~5 秒内

注意：ADR-024 对本 ADR 的状态转换做了补充——"等待补充信息"和"已拒绝"不仅可以由"待开始"进入，也可以由"执行中"进入。完整状态转换见 ADR-024。

### 对"执行中"语义的影响

"执行中"只意味着 Agent 正在调用工具、生成产物。语义干净：
- 不包含"思考要做什么"
- 不包含"检查信息够不够"
- 用户看到执行中就知道 Agent 在干活了

## 被拒绝的替代方案

1. **全部隐藏在执行中**——信息不足和越界在执行中才发现。被拒绝因为用户看到"执行中"后又被拉回"等待补充信息"，体验差。

2. **增加"准备中""规划中"状态**——被拒绝因为 Phase 1 的 7 状态已经够多，增加用户认知负担。

## 后果

### 正面

- "执行中"语义干净，用户不会误解
- 信息不足在执行前就发现，减少无效执行
- 越界检测提前，避免 Agent 开始执行后才拒绝

### 负面

- 规划检查增加"待开始 → 执行中"的延迟（预估 3~5 秒）
- 如果规划检查本身出错（误判信息不足），用户体验受影响

## 复审条件

- 当规划检查延迟超过可接受范围时
- 当误判率偏高时
