# ADR-018：部署形态与多组织预留

## 上下文

数字军团OS 定位为企业级产品。Phase 1 需要确定部署形态——单组织私有部署、多组织 SaaS，还是介于两者之间。这个决策影响数据模型、API 设计、权限体系和知识归属。

## 决策

**Phase 1 单组织为主，数据模型预留多组织能力。**

### 具体措施

1. **数据模型层面**
   - 所有核心数据表统一包含 `tenant_id` 字段
   - API 层统一走租户上下文（从认证 token 中提取 tenant_id）
   - 数据库查询统一带 tenant_id 过滤
   - Phase 1 所有数据使用同一个固定 tenant_id

2. **架构层面**
   - 不做多组织租户隔离的运行时实现
   - 不做租户自助注册、管理、计费
   - 不做多组织间的数据隔离策略（行级隔离 vs schema 隔离 vs 库隔离）

3. **资产归属**
   ```
   全局资产（跨组织复用）
     → Hermes Agent 本身
     → 标准模块组件库
     → 通用工具定义（git、terminal、http）

   组织级资产（tenant_id 隔离）
     → Soul 原型
     → Wiki 文档
     → 能力注册中心里的自定义工具
     → 角色定义、权限策略、审批规则
     → 组织成员

   项目级资产（project_id 隔离）
     → 数字员工实例
     → Issue + 产物
     → Project Memory
     → Personal Memory
   ```

4. **Phase 2 扩展路径**
   - 引入租户管理服务
   - 实现数据隔离策略
   - 支持跨组织的原型共享（总部推送标准数字员工给分公司）

## 被拒绝的替代方案

1. **纯单组织，不预留**——不加 tenant_id。被拒绝因为 Phase 2 加多组织时几乎所有数据表都要改造，改造成本巨大。

2. **Phase 1 做完整多组织**——租户管理、数据隔离、注册、计费。被拒绝因为完全是另一个量级的工作，会严重拖慢 Phase 1 交付。

## 后果

### 正面

- Phase 2 加多组织时数据迁移成本极低（tenant_id 已存在）
- API 层已预留租户上下文，不需要重构
- Phase 1 开发成本几乎不增加

### 负面

- 每个查询多一个 tenant_id 过滤，轻微性能开销（可忽略）
- 开发时需要始终记得带 tenant_id，否则后续改造困难

## 复审条件

- 当 Phase 2 规划多组织能力时
- 当数据隔离策略需要确定时
