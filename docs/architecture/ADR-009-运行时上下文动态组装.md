# ADR-009：运行时上下文动态组装

## 上下文

数字员工实例在执行 Issue 时需要完整的运行上下文：Soul 配置、Project Objective、Wiki 知识、Project Memory、权限边界。需要确定上下文是打包时注入还是运行时动态加载。

## 决策

**每次 Issue 执行时动态组装上下文，不在实例派发时打包。**

### 组装流程

```
Issue 执行触发
  → 上下文组装层启动
  → 加载 Soul 压缩包（从版本引用获取最新配置）
  → 注入 Project Objective（实时从 Project 读取）
  → 绑定 Project 权限边界（实时从权限服务获取）
  → 建立 Wiki + Project Memory 检索通道（实时连接知识服务）
  → 注入 Personal Memory（UI 偏好，不注入 Agent）
  → 合成为完整运行配置
  → 传给 Body 开始执行
```

### 各元素的生命周期

| 元素 | 加载时机 | 变化频率 | 存储位置 |
|------|----------|----------|----------|
| Soul 配置 | 每次 Issue 执行 | 低（版本更新时变） | 定义服务 |
| Project Objective | 每次 Issue 执行 | 中（项目负责人可能修改） | 项目服务 |
| 权限边界 | 每次 Issue 执行 | 低 | 治理服务 |
| Wiki 索引 | 每次 Issue 执行 | 中（文档会更新） | 知识服务 |
| Project Memory | 每次 Issue 执行 | 高（持续沉淀） | 知识服务 |
| Personal Memory | 每次 Issue 执行 | 低 | 知识服务 |

### 设计意义

1. **Soul 压缩包是稳定的版本化资产**——不变
2. **动态变化的东西在运行时绑定**——保证始终使用最新状态
3. **上下文组装层是 Body 和平台之间的中间层**——Body 不需要知道上下文从哪来

## 被拒绝的替代方案

1. **打包时注入**——实例派发时把所有上下文一次性打包。被拒绝因为 Wiki 和 Project Memory 会持续更新，打包后知识过时。

2. **Body 启动时注入**——Body 进程启动时加载一次上下文。被拒绝因为 Project Objective 和权限可能在中途变更。

## 后果

### 正面

- 保证每个 Issue 使用最新的 Project 上下文
- Soul 版本更新不需要重启 Body（下次 Issue 自动使用新版本）
- 上下文组装层作为明确架构组件，职责清晰

### 负面

- 每次 Issue 执行前有上下文组装延迟（预估 1~3 秒）
- 上下文组装层成为关键路径，如果失败则 Issue 无法开始执行
- 需要缓存策略避免频繁重复加载不变的内容（如 Soul 配置）

## 复审条件

- 当上下文组装延迟影响用户体验时（考虑缓存）
- 当需要支持离线执行场景时
