# ADR-024：Phase 1 审批与 Issue 状态机收口

## 上下文

当前文档中，实例审批、申请权限和 Issue 状态机存在三类口径分叉：

1. PRD-102 仍保留双人审批和"项目负责人 / 授权成员"申请实例。
2. ADR-021 把实例申请权限放给了 Member。
3. ADR-010 与 PRD-103 对"等待补充信息"、"已拒绝"发生在执行前还是执行中存在不同表述。

这些分叉会直接影响后端状态机、前端交互、测试用例和审计模型，需要在 Phase 1 明确收口。

## 决策

**Phase 1 的实例审批采用"自动通过 + 项目负责人单人审批"两档；Issue 保持 7 状态，但补充前置分流和原因码规则。**

### 实例申请与审批

1. **申请权限**
   - 仅项目负责人（Owner）可以为项目申请实例
   - Member 和 Viewer 不能直接申请实例
   - Phase 1 不做"授权成员"、权限委托和代理

2. **审批档位**
   - 低风险 / 中风险：自动通过
   - 高风险：项目负责人单人审批
   - 无法判定：按高风险处理，进入项目负责人审批

3. **Phase 1 明确不做**
   - 双人审批
   - 会签
   - 多级审批
   - 可配置审批流

### Issue 状态机解释

Phase 1 继续使用 7 状态：

```text
待开始 / 执行中 / 等待补充信息 / 已完成 / 执行失败 / 已拒绝 / 已取消
```

但状态语义收口如下：

1. **待开始**
   - Issue 已创建，等待执行触发
   - 启动前会先经过上下文组装和规划检查

2. **执行中**
   - 只表示 Agent 已开始真实执行
   - 不包含纯准备态

3. **等待补充信息**
   - 允许两类来源：
     - `待开始 -> 等待补充信息`：启动前信息不足
     - `执行中 -> 等待补充信息`：执行中发现新的关键信息缺口

4. **已拒绝**
   - 允许两类来源：
     - `待开始 -> 已拒绝`：启动前越界
     - `执行中 -> 已拒绝`：执行中发现真实边界越界

### 已拒绝与执行失败的边界

为避免语义混淆，Phase 1 保持同一状态，但增加 `reason_code`：

- `precheck_out_of_scope`
- `runtime_out_of_scope`

并统一边界：

1. **已拒绝** = 系统有意不继续做
   - 典型原因：职责越界、权限越界、治理规则拦截

2. **执行失败** = 系统想做但没做成
   - 典型原因：工具异常、运行异常、外部依赖失败、Body 离线超时

### 推荐状态转换

```text
待开始
  → 执行中
  → 等待补充信息
  → 已拒绝
  → 已取消

执行中
  → 已完成
  → 执行失败
  → 等待补充信息
  → 已拒绝

等待补充信息
  → 执行中
  → 已取消
```

## 被拒绝的替代方案

1. **保留双人审批**——被拒绝因为会把 Phase 1 审批对象模型、通知和审计复杂度显著拉高，不符合单数字员工主链路优先级。

2. **Member 也可申请实例**——被拒绝因为会造成"申请人和固定审批人分离"的治理口径松散，且与 Phase 1 不做权限委托冲突。

3. **把拒绝分拆成更多状态**——被拒绝因为会扩大状态机规模，增加产品认知负担；原因码已足够表达差异。

## 后果

### 正面

- 审批模型、权限模型和状态机口径统一
- 后端对象模型更稳定，测试矩阵更清晰
- 前端可以同时表达"启动前补充"和"执行中补充"两种真实场景

### 负面

- "授权成员申请实例"需要推迟到后续版本
- PRD 与既有 ADR 需要同步勘误
- 前端在 `已拒绝` 展示上需要带出 `reason_code`

## 复审条件

- 当需要恢复"授权成员"或权限委托时
- 当需要双人审批或可配置审批流时
- 当 Issue 状态机需要扩展更多治理中间态时
