# ADR-002：Soul 压缩包结构与自包含性

## 上下文

Soul 是数字员工的专业身份定义资产。需要确定 Soul 的内部结构以及"自包含"的边界——打开一个 Soul 压缩包后，是否足以完整描述这个数字员工的能力、人格和工作方式。

## 决策

**Soul 压缩包是自包含的**——打开它就能完整描述这个数字员工。

### 标准目录结构

```
soul.zip
├── soul.md              # 人格定义、职责范围、安全约束、输出规范
├── tools.yaml           # 工具集声明 + 工作台模块映射
├── skills/              # 技能文件目录（指导 Agent "怎么做"的 prompt 级知识）
│   ├── code-review.md
│   ├── prd-writing.md
│   └── ...
├── memory/              # 初始记忆（原型级知识引用）
│   ├── initial-context.yaml
│   └── ...
├── mcp/                 # MCP Server 配置
│   ├── servers.yaml
│   └── ...
├── functions/           # Function Calling 定义
│   ├── api-calls.yaml
│   └── ...
└── manifest.yaml        # 元数据（版本号、角色类型、适用场景、负责人等）
```

### 自包含原则

1. **soul.md 包含完整的人格/职责/约束定义**——不需要从平台数据库补充基础定义
2. **tools.yaml 描述工具集和工作台模块映射**——不需要平台额外配置模块布局
3. **skills/ 包含所有技能文件**——不需要运行时从外部拉取
4. **memory/ 包含初始记忆引用**——指向 Wiki 文档 ID 列表，实际文档内容在运行时从平台拉取
5. **manifest.yaml 包含版本和元数据**——支持版本管理和兼容性检查

### 唯一的外部依赖

Soul 压缩包在运行时只有一个外部依赖：**工具的实际实现**。tools.yaml 声明了需要哪些工具，但工具的注册和能力来源在平台的"能力注册中心"。Soul 压缩包不包含工具的实现代码。

## 被拒绝的替代方案

1. **Soul 为纯数据库记录**——人格、职责、工具分表存储，导出时动态打包。被拒绝因为无法作为独立资产版本化管理和离线传输。

2. **Soul 包含前端渲染代码**——压缩包内包含自定义工作台模块组件。被拒绝因为 Phase 1 不支持自定义前端模块，标准模块排列组合已够用。

## 后果

### 正面

- 定义中心（PRD-101）的架构清晰：它是 Soul 压缩包的编辑器 + 测试沙箱 + 版本管理 + 审核发布平台
- Soul 可以独立于平台进行版本管理、diff 对比、回滚操作
- Soul 可以在组织间传输（Phase 2 多组织场景）

### 负面

- manifest.yaml 的 schema 版本需要严格管理，避免旧版 Body 无法加载新版 Soul
- 压缩包大小需要控制，避免包含过多初始记忆导致加载缓慢

## 复审条件

- 当需要支持自定义前端模块组件时（Phase 2+）
- 当 Soul schema 需要不兼容变更时
- 当压缩包大小超过合理阈值时
