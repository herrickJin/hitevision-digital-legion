# ADR-021：权限模型

## 上下文

数字军团OS 涉及多种操作：定义 Soul 原型、申请实例、创建 Issue、审批、查看结果、管理成员等。需要一个权限模型来控制谁能做什么。

## 决策

**采用 RBAC（基于角色的访问控制），Phase 1 定义少量角色和权限点。**

### 角色定义

**组织级角色（2 个）：**

| 角色 | 权限范围 |
|------|----------|
| 组织管理员 | 管理 Soul 原型定义、能力注册、组织级配置、组织成员管理 |
| 组织成员 | 可被邀请加入项目，浏览组织市场 |

**项目级角色（3 个）：**

| 角色 | 权限范围 |
|------|----------|
| 项目负责人（Owner） | 项目全部权限：实例申请、成员管理、项目状态管理、项目归档 |
| 项目成员（Member） | 使用工作台、创建 Issue、查看结果、补充信息 |
| 项目观察者（Viewer） | 只读查看 Issue 列表和产物 |

### 关键权限点

| 操作 | Owner | Member | Viewer | 组织管理员 |
|------|-------|--------|--------|-----------|
| Soul 原型定义 | - | - | - | ✓ |
| 原型审核/上架 | - | - | - | ✓ |
| 浏览组织市场 | ✓ | ✓ | - | ✓ |
| 为项目申请实例 | ✓ | - | - | ✓ |
| 创建 Issue | ✓ | ✓ | - | - |
| 取消 Issue | 自己创建的或任意 | 自己创建的 | - | - |
| 查看执行过程 | ✓ | ✓ | ✓ | - |
| 查看最终结果 | ✓ | ✓ | ✓ | - |
| 补充信息 | ✓ | ✓ | - | - |
| 管理项目成员 | ✓ | - | - | - |
| 项目暂停/恢复/归档 | ✓ | - | - | - |
| 审批高风险申请 | ✓（默认审批人） | - | - | ✓ |

### Phase 1 不做

- 自定义角色
- 细粒度权限点配置（如"只允许创建低优先级 Issue"）
- 数据行级权限（如"只能看自己负责的模块代码"）
- 权限委托和代理
- 项目内"授权成员"代项目负责人申请实例

### 授权业务专家

PRD 提到的"授权业务专家"不是独立角色，而是组织管理员对某个组织成员的标记——允许该成员定义特定业务域的 Soul 原型。实现上可以在组织管理员操作中直接授权，不需要新增角色。

注意：Phase 1 "授权业务专家"仅限 Soul 原型定义权限，不含实例申请权限。实例申请权限仅限项目负责人（Owner），见 ADR-024。

## 被拒绝的替代方案

1. **简单固定角色，无权限点**——每个角色硬编码固定权限。被拒绝因为不够灵活，后续扩展困难。

2. **ABAC 动态权限**——根据属性动态判断。被拒绝因为 Phase 1 需求简单，ABAC 复杂度不值得。

3. **更多角色细分**——如"项目审批人""知识管理员"等。被拒绝因为 Phase 1 角色过多增加管理负担。

## 后果

### 正面

- 2+3 角色模型简单，用户和管理员理解成本低
- 覆盖 Phase 1 核心操作场景
- RBAC 扩展性好，Phase 2 可增加角色和权限点

### 负面

- 申请权限收敛到 Owner，项目负责人可能成为实例申请链路的单点入口
- Phase 2 如果需要细粒度权限，可能需要重构权限检查逻辑

## 复审条件

- 当需要细粒度权限控制时
- 当需要自定义角色时
- 当需要跨项目权限时
