# ADR-019：Soul 原型组织内共享机制

## 上下文

Soul 原型上架后，哪些项目能用到它？需要一个共享机制来连接原型定义和项目使用。

## 决策

**上架的原型进入组织内部市场，组织内所有项目可见。项目负责人从市场发现和申请实例。**

### 组织内部市场（Phase 1 最简版）

1. **可见范围**——上架的原型对同一组织内所有项目开放，Phase 1 不做可见范围控制

2. **市场入口**
   - 独立浏览入口：项目负责人浏览组织市场，搜索/筛选原型
   - 项目创建入口：创建项目时可勾选需要的数字员工（ADR-020）

3. **Phase 1 市场能力**
   - 原型列表（名称、角色类型、业务域、版本、风险等级）
   - 搜索和筛选
   - 原型详情页（职责、能力、权限、支持载体、更新记录、审批规则）
   - 申请入口（跳转实例申请流程）

4. **Phase 1 不做**
   - 评分和评价
   - 智能推荐
   - 分类体系
   - 按业务域/项目组的可见范围控制
   - 跨组织原型共享

### Phase 2 扩展方向

- 原型评分和使用数据展示
- 按角色场景推荐
- 按业务域/部门限制可见范围
- 跨组织原型推送（总部 → 分公司）

## 被拒绝的替代方案

1. **原型定义时指定可见范围**——可以设为"全组织可见"或"仅指定项目可见"。被拒绝因为 Phase 1 增加配置复杂度，且组织内共享是默认需求。

2. **每个项目独立维护原型库**——项目不共享原型。被拒绝因为违反"定义一次、全组织复用"的核心原则。

## 后果

### 正面

- 原型定义一次，全组织复用，符合数字员工资产沉淀的目标
- 市场作为自然的中介层，连接定义和使用

### 负色

- 全组织可见意味着低质量原型可能被误用。缓解：PRD-101 的测试+审核流程保证上架质量
- Phase 1 市场功能很简陋，只是列表+搜索+详情。P1 再丰富

## 复审条件

- 当需要按部门/业务域限制原型可见范围时
- 当需要跨组织共享原型时
