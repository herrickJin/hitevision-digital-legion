# ADR-008：知识三层模型——Wiki、Project Memory、Personal Memory

## 上下文

数字员工在执行任务时需要访问组织知识、项目经验和用户偏好。PRD-105 定义了三个知识/记忆层，但技术实现的边界和交互方式需要明确。

## 决策

### 三层定义

| 层 | 性质 | 写入方式 | 检索方式 | 存储特征 |
|---|---|---|---|---|
| Wiki | 权威知识，只读 | 人工上传 + 审核 | RAG 检索 | 组织级，结构化文档 + 向量索引 |
| Project Memory | 执行经验，可写 | 数字员工自动写入 + 来源标记 | RAG 检索 | 项目级，经验摘要 + 向量索引 |
| Personal Memory | 个人偏好，不参与 RAG | 用户手动配置 | 不检索，UI 层直接读取 | 用户级，键值对 |

### 读写规则

1. **Wiki**
   - 数字员工只读，不可写入
   - 人工上传、人工审核后生效
   - 支持文档版本和来源记录

2. **Project Memory**
   - 数字员工可写入，但必须标记来源类型（自动写入 / 人工确认）
   - Phase 1 先做自动写入 + 来源标记，不做强制人工审核（审核机制放到 P1）
   - 写入内容为经验摘要，非原始任务结果（原始结果存 TaskArtifact）

3. **Personal Memory**
   - 不参与 RAG 检索
   - 只影响 UI 层面的展示偏好和通知配置
   - 分通用偏好和项目特定偏好（见 ADR-005）

### 检索优先级

```
Project Memory > Wiki > Personal Memory（不检索）
```

理由：
- Project Memory 是项目上下文，最精确、最相关
- Wiki 是通用知识，权威但可能不够具体
- Personal Memory 不参与知识检索，只影响展示

### 技术实现

- Wiki 和 Project Memory 可以共用向量存储引擎
- 通过元数据字段区分来源类型（wiki / project_memory）
- 向量检索时按优先级加权排序

## 被拒绝的替代方案

1. **三层共用一个检索通道，不区分优先级**——被拒绝因为 Project Memory 的经验摘要比 Wiki 的通用文档更精确，应该优先命中。

2. **Personal Memory 参与 RAG 检索**——被拒绝因为个人偏好不是知识，混入检索会增加噪音。

3. **Project Memory 强制人工审核后才写入**——被拒绝因为 Phase 1 的审核机制会增加使用摩擦，先用来源标记做可追溯即可。

## 后果

### 正面

- 三层概念在数据模型和产品界面上清晰区分
- 检索优先级保证项目上下文优先命中
- Phase 1 不强制审核，降低使用门槛

### 负面

- Project Memory 自动写入可能导致脏数据累积。缓解：来源标记 + P1 引入过期和清理机制
- Wiki 和 Project Memory 共用向量存储需要仔细的元数据管理

## 复审条件

- 当 Project Memory 脏数据影响检索质量时
- 当 P1 引入审核机制时
- 当需要支持跨项目知识引用时
