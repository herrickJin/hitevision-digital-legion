# ADR-028：前端架构与工作台渲染

## 上下文

ADR-003 定义了工作台由平台预置 10-15 个标准模块，通过 Soul 的 tools.yaml 声明组合。但前端本身的技术选型、模块加载机制、页面布局策略没有确定。工作台是数字军团 OS 的核心交互界面，需要实时性（WebSocket 联动）、模块化和合理的工程投入。

## 决策

### 技术栈：Vue 3 + TypeScript + Vite

- Vue 3 Composition API 适合模块间状态共享和响应式联动
- TypeScript 保障类型安全，API 契约（ADR-014 OpenAPI）可自动生成类型
- Vite 构建速度快，开发体验好

### 渲染模式：SPA（Single Page Application）

- 工作台需要 WebSocket/SSE 实时推送联动事件（ADR-015），SPA 天然支持
- 模块间联动（ADR-003）在 SPA 内通过组件间通信实现，比 iframe/MPA 跨页通信简单
- 工作台交互密集（终端流、代码视图、文档编辑、实时状态），SPA 体验远优于 MPA

### 模块加载：静态注册 + 条件渲染

所有标准模块组件打包在主应用内。运行时根据后端返回的模块列表，条件渲染对应组件。

```
用户打开工作台
  → 前端请求 GET /api/instances/{id}/workbench/modules
  → 后端返回模块列表：[{type: "code-view"}, {type: "terminal-view"}, {type: "doc-editor"}]
  → 前端从组件注册表取出对应 Vue 组件
  → 按布局模板渲染
```

理由：Phase 1 只有 10-15 个标准模块，全部打包体积可控。新增标准模块本身是平台发版行为（ADR-003），跟主应用一起发版是自然的。

Phase 2 开放第三方自定义模块时，再引入动态加载机制（微前端）。

### 页面布局：预置模板 + 固定 Shell

**固定 Shell：**

```
┌──────────────────────────────────────────────┐
│  顶栏：实例名称 · 状态 · 版本 · 操作按钮      │
├──────────┬───────────────────────────────────┤
│          │                                   │
│  左侧    │      主工作区                      │
│  导航    │   （按布局模板渲染模块）              │
│  Issue   │                                   │
│  列表    │                                   │
│          │                                   │
├──────────┴───────────────────────────────────┤
│  底栏：通知 / 状态信息                         │
└──────────────────────────────────────────────┘
```

**预置布局模板（Phase 1）：**

| 模板 | 适用模块组合 | 布局 |
|------|-------------|------|
| 左右分栏 | code-view + terminal-view | 左 60% 代码视图，右 40% 终端 |
| 标签页 + 侧栏 | doc-editor + requirements + knowledge-context | 主区标签页切换，右侧知识上下文 |
| 上下分栏 | test-cases + test-result + bug-list | 上方用例列表，下方结果/缺陷 |
| 单栏 | doc-editor / api-docs | 全屏单一模块 |

**模板匹配逻辑：**

后端返回模块列表时，同时返回推荐的布局模板 ID。匹配规则定义在能力注册中心——模块组合到模板的映射由平台维护。前端只负责渲染。

### Phase 1 不做

- 用户拖拽自定义布局
- 模块大小调整
- 自定义模块组件（ADR-003 已明确）
- 微前端动态加载
- 离线 PWA 支持
- 多工作台标签页

## 被拒绝的替代方案

1. **MPA（多页应用）**——每个页面独立加载。被拒绝因为模块间实时联动需要跨页通信，复杂度远高于 SPA 内组件通信。

2. **微前端动态加载**——每个模块独立构建，运行时按需加载。被拒绝因为 Phase 1 标准模块数量有限（10-15），全部打包体积可控；微前端引入的模块版本管理、样式隔离、公共依赖共享问题不值得 Phase 1 解决。

3. **用户自由布局**——拖拽排列模块，位置和大小可调。被拒绝因为工程量大，且 Phase 1 模块组合有限，预置模板已够用。

4. **React 技术栈**——React 同样可行，但 Vue 3 的响应式系统和 Composition API 在声明式模块组合场景下更直观。选 Vue 不代表技术优越性，只是方向性统一。

## 后果

### 正面

- SPA + Vue 3 技术栈成熟，生态丰富，招聘和培训成本低
- 静态注册避免微前端复杂度，Phase 1 交付快
- 预置模板覆盖核心角色需求，开发成本可控
- 组件化架构为 Phase 2 动态加载预留空间

### 负面

- 所有模块打包在主应用内，随着模块增加前端包体积会增长
- 预置模板无法覆盖所有模块组合，极端组合可能体验不佳
- 绑定 Vue 技术栈，如果未来需要引入非 Vue 生态的模块组件，需要架构调整

## 复审条件

- 当标准模块超过 20 个，前端包体积影响加载速度时
- 当需要支持第三方自定义模块时（引入微前端）
- 当需要用户自定义布局时
- 当预置模板无法满足新角色的工作台需求时
