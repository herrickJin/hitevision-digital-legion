# ADR-015：Body-Platform 通信架构

## 上下文

Hermes Agent（Body）运行在用户侧（PC/Linux/容器），平台运行服务是中心化的。Issue 执行时 Body 需要和平台频繁交互：接收任务、报告进度、传输操作过程。需要确定通信架构。

## 决策

**WebSocket 长连接 + 事件驱动，平台作为中间层解耦 Body 和前端。**

### 两段通信架构

```
Body ←──WebSocket长连接──→ 平台运行服务 ←──WebSocket/SSE──→ 前端
```

### 段一：Body ↔ 平台运行服务（WebSocket 长连接）

**连接生命周期：**
- Body 启动时与平台运行服务建立 WebSocket
- 连接期间维持心跳（每 30 秒一次 ping）
- 连接断开时 Body 自动重连

**平台 → Body（下行）：**
- 上下文注入（Soul 配置 + Project Objective + 权限边界）
- Issue 执行指令
- 停止/更新指令
- 心跳响应

**Body → 平台（上行）：**
- 心跳 ping
- 执行事件上报（工具调用、阶段产物、状态变更）
- 终端输出流（stdout/stderr 实时推送）
- 结构化操作事件（文件操作、浏览操作）
- 产物发布

### 段二：平台运行服务 ↔ 前端（WebSocket 或 SSE）

**连接生命周期：**
- 用户打开工作台时建立连接
- 关闭工作台时断开

**平台 → 前端（推送）：**
- Issue 联动事件（issue_created、context_resolved、artifact_published 等）
- Body 在线状态变化
- 实例状态变更通知
- 审批结果通知

**前端 → 平台（请求）：**
- 用户操作（确认 Issue、补充信息、取消任务、审批操作）

### 关键设计点

1. **Body 不直接和前端通信**——平台运行服务作为中间层，解耦两端
2. **终端输出走 WebSocket**——Body 的 terminal stdout/stderr 通过 WebSocket 流式推送到平台，平台透传给前端，前端用终端组件渲染
3. **结构化事件走 WebSocket**——工具调用、文件操作等结构化事件同样通过 WebSocket 上报

## 被拒绝的替代方案

1. **Body 完成后 HTTP 回传**——被拒绝因为无法满足实时观看操作过程的需求，也无法实时感知 Body 掉线。

2. **Body 直接和前端 WebSocket**——被拒绝因为绕过平台会导致审计缺失、权限控制缺失，且前端需要管理多条连接。

## 后果

### 正面

- 实时感知 Body 在线状态（心跳机制）
- 用户可实时观看 Body 操作过程（终端流 + 结构化事件）
- 平台作为中间层统一管理权限、审计和事件分发
- Body 和前端解耦，各自独立演进

### 负面

- WebSocket 长连接增加平台运行服务的连接管理复杂度
- 需要处理断连恢复和状态同步（见 ADR-016）
- 终端输出流的带宽消耗需要控制（考虑限流和截断）

## 复审条件

- 当 Body 并发连接数超过单节点承载能力时（考虑负载均衡）
- 当终端输出流带宽成为瓶颈时
- 当需要支持离线执行场景时
