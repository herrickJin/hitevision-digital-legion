# ADR-023：失联场景下的受限执行与副作用控制

## 上下文

ADR-015 定义了 Sidecar 与平台之间基于 WebSocket 的实时通信（更新后为三段架构：Agent↔Sidecar↔平台↔前端），ADR-016 进一步定义了断连检测、等待窗口和补传机制。但 Phase 1 同时存在三个约束：

1. Body 失联后不能让用户长期处于不确定状态。
2. Body 失联后如果继续执行外部副作用操作，可能出现"平台已判失败、用户已重试、原任务晚到成功"的一致性事故。
3. Phase 1 不做完整的分布式事务、断点续执行和跨系统幂等编排。

需要在可用性和一致性之间做一个适合 Phase 1 的取舍。

引入 Sidecar（ADR-025）后，副作用拦截的执行点从 Agent 内部转移到 Sidecar——Sidecar 监听 Agent stdout 的 tool_call 事件，根据 side_effect 标记决定是否放行。

## 决策

**Phase 1 采用受限继续策略：平台失联后，Sidecar 禁止 Agent 继续产生外部副作用；仅允许继续执行无副作用、可缓存、可恢复的本地步骤。**

### 失联后的执行语义

当 Sidecar 与平台连接断开后：

1. **允许继续**
   - 本地推理
   - 读取类操作
   - 本地草稿生成
   - 本地事件缓存（Sidecar 缓存 Agent stdout 事件）
   - 尚未提交的产物整理

2. **禁止继续**——由 Sidecar 拦截
   - 一切会改变外部系统状态的操作
   - 一切需要平台实时审计和确认的人机动作

**拦截机制**：Sidecar 监听 Agent stdout 的 `tool_call` 事件。当 Agent 发出 `side_effect=true` 的工具调用时：
- 连接正常：放行，正常上报平台
- 连接断开：Sidecar 丢弃该 tool_call，通过 stdin 向 Agent 返回错误事件，Agent 需要自行处理调用失败

### 副作用工具定义

Phase 1 统一通过 `side_effect=true` 标记副作用工具和工作流节点。至少包括以下四类：

1. **远端写操作**
   - 向代码仓库推送
   - 创建或更新 PR
   - 写远端文件
   - 改数据库
   - 写知识库
   - 写业务系统

2. **对外通知/触达**
   - 发 IM
   - 发邮件
   - 发审批
   - 发 webhook
   - 发短信

3. **改变外部状态的工作流节点**
   - 提交工单
   - 触发发布
   - 修改配置
   - 调用设备控制接口

4. **不可幂等的人机确认动作**
   - 代用户点击确认
   - 代用户提交审批
   - 代用户执行删除或回收

### 断连后的处理流程

```text
Sidecar 与平台断连
  → 平台标记疑似离线
  → Sidecar 进入受限继续模式
    → 允许 Agent 本地无副作用步骤继续
    → 拦截 Agent stdout 中 side_effect=true 的 tool_call 事件
    → 向 Agent 返回错误事件，Agent 自行处理
  → 重连成功
    → Sidecar 补传缓存事件
    → 平台按顺序补齐时间线和审计
  → 超过等待窗口仍未恢复
    → Issue 标记为"执行失败"
```

### 晚到事件与结果的规则

1. Issue 一旦因 Body 离线超时被标记为"执行失败"，不得再接受新的外部副作用结果落账。
2. 超时后的晚到补传仅用于：
   - 审计补账
   - 时间线补全
   - 本地草稿或中间产物归档
3. 用户重试会创建新的执行轮次；旧轮次不得在恢复后继续提交副作用结果。

### 与重试机制的关系

1. `执行失败` 仍保留重试能力，沿用 PRD-103 的 `retry_count` 规则。
2. 重试前提是旧轮次已经被平台判定终止，不再有副作用提交权限。
3. Phase 1 不要求跨轮次断点续执行，采用"重新发起一轮执行"的简化模型。

## 被拒绝的替代方案

1. **完全继续执行**——断连后 Body 不受限制地继续跑完，恢复后统一补传。被拒绝因为会导致副作用重复、审计滞后和重试冲突。

2. **立即冻结全部执行**——一断连就暂停一切动作。被拒绝因为会显著放大弱网影响，也要求 Body 具备更复杂的可中断恢复机制。

3. **Phase 1 引入完整幂等事务模型**——所有外部动作都由平台发幂等键统一编排。被拒绝因为实现成本超出 Phase 1 范围。

## 后果

### 正面

- 保留弱网场景下的基本连续性，不必一断网就完全停摆
- 阻断副作用重复提交，降低一致性事故风险
- 测试边界明确：只需验证失联时副作用工具被拦截

### 负面

- Body 需要通过 Sidecar 拦截 `side_effect=true` 的工具调用。Sidecar 监听 Agent stdout 的 tool_call 事件并做过滤
- 用户可能看到"任务失败但本地草稿仍被保留"的结果，需要 UI 解释
- 晚到事件只能补账，不能挽回已失败轮次的业务结果
- Agent 需要能处理 Sidecar 返回的"副作用调用被拦截"错误事件

## 复审条件

- 当 Phase 2 需要支持断点续执行时
- 当需要引入统一幂等键和外部副作用事务编排时
- 当副作用工具分类无法覆盖实际场景时
