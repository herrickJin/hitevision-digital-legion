# ADR-016：断连恢复与超时策略

## 上下文

Body 和平台之间通过 WebSocket 长连接通信（ADR-015）。网络闪断、Body 进程崩溃、机器断电都会导致连接中断。需要定义平台如何检测断连、如何区分故障类型、如何恢复。

## 决策

### 心跳与检测机制

```
Body 侧：
  每 30 秒发送一次 ping
  WebSocket 断开时本地继续执行
  事件缓存到本地队列
  自动尝试重连
  重连成功后补传缓存事件

平台侧：
  3 次未收到心跳（90 秒）标记为"疑似离线"
  前端显示"Body 连接中断，等待恢复"
  该 Body 上运行中的 Issue 不立即失败
  进入 5 分钟等待窗口
```

### 三种掉线场景的处理

| 场景 | 特征 | 处理方式 |
|------|------|----------|
| **网络闪断** | Body 进程还在，WebSocket 断了 | Body 自动重连，补传事件。5 分钟内恢复则 Issue 无影响 |
| **Body 进程崩溃** | 进程没了，不可能重连 | 5 分钟超时后 Issue 标记"执行失败"，原因"Body 离线超时" |
| **机器断电/离线** | 进程停了，但重启后可恢复 | 同进程崩溃处理。重启后 Body 重新建立连接，但运行中 Issue 已标记失败 |

### 超时策略

- **等待窗口：5 分钟**——覆盖大多数网络闪断和 Body 重启场景
- **超时后动作：Issue 标记为"执行失败"**——原因记录为"Body 离线超时"
- **Phase 1 不区分场景 2 和场景 3**——统一按超时处理，用户可手动重试

### Body 侧关键行为

1. **本地继续执行**——WebSocket 断开不影响 Body 正在执行的工具调用
2. **事件缓存**——断连期间的事件缓存到本地队列，按时间排序
3. **重连补传**——WebSocket 重连成功后，把缓存事件按顺序补传给平台
4. **缓存上限**——本地缓存最大保留 1000 条事件或 10MB（超出则丢弃最旧的）

### 前端状态展示

```
正常         → "实例运行中 · PC · 版本 v1.2.0"
疑似离线     → "Body 连接中断，等待恢复...（剩余 N 分钟）"
恢复成功     → "连接已恢复" + 刷新事件流
超时失败     → "任务执行失败 · 原因：Body 离线超时 · 可重试"
```

## 被拒绝的替代方案

1. **立即判定失败**——WebSocket 断开立刻标记 Issue 失败。被拒绝因为网络闪断在企业内网常见，一刀切误判率高。

2. **无限等待**——一直等 Body 重连。被拒绝因为用户需要明确知道任务状态，不能永远挂着。

3. **Phase 1 区分崩溃和断电**——通过 Body 上报诊断信息区分场景。被拒绝因为增加 Body 侧复杂度，且 Phase 1 处理方式相同（都等重连或超时失败）。

## 后果

### 正面

- 网络闪断不丢失执行进度（本地缓存 + 补传）
- 5 分钟窗口覆盖大多数恢复场景
- 用户体验明确——知道在等、知道等多久、知道超时后怎么办

### 负面

- Body 侧需要实现本地事件缓存机制，增加 Agent 侧开发量
- 缓存补传可能导致事件乱序——需要时间戳 + 序列号保证有序性
- 5 分钟等待期间前端需要展示中间状态

## 复审条件

- 当 5 分钟窗口覆盖不了实际恢复场景时
- 当需要支持断点续执行时（Phase 2）
- 当缓存策略需要调整时
