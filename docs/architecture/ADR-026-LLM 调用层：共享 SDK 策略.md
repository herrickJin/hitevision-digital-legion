# ADR-026：LLM 调用层——共享 SDK 策略

## 上下文

平台多处需要调用 LLM：structured brief 生成（ADR-017）、经验摘要生成（ADR-011）、越界预检（ADR-017）、文档分段与向量化（ADR-008）、规划检查（ADR-010）。这些调用分散在任务服务和知识服务中。如果各服务各自管理 LLM provider 适配、重试和计费，会导致重复代码和统计口径不一致。

## 决策

**采用共享 SDK（独立内部包），不新增独立服务。各服务通过引入 SDK 统一 LLM 调用。**

### SDK 形态

独立 Git 仓库或 monorepo 独立模块（如 `@digital-legion/llm-sdk`），各服务通过包依赖引入。

不放在 `platform-common` 公共库中，理由：LLM SDK 的变更频率（provider API 变更、新增模型、prompt 策略调整）远高于公共库，混入会污染公共库发版节奏。

### 调用场景分布

| 场景 | 所在服务 | 调用频率 | 质量要求 |
|------|----------|----------|----------|
| structured brief 生成 | 任务服务 | 每次 Issue 创建 | 中 |
| 经验摘要生成 | 任务服务 | 每次 Issue 完成 | 中 |
| 越界预检 | 任务服务 | 每次 Issue 创建 | 低 |
| 文档分段与向量化 | 知识服务 | 文档上传时 | 低 |
| 规划检查 | 任务服务 | 每次 Issue 执行前 | 高 |

### Phase 1 SDK 最小能力集

| 能力 | 说明 |
|------|------|
| Provider 适配 | 统一接口封装 OpenAI / Anthropic / 国产模型 |
| 重试 + 降级 | 主 provider 失败自动切备用，指数退避 |
| Token 统计 | 按调用方 + 场景记录用量，写审计表 |
| Prompt 模板 | 简单的模板变量替换 |

### Phase 1 不做

- Prompt 版本管理和 A/B 测试
- LLM 调用缓存（相同 prompt 复用结果）
- 流式输出的统一封装（各场景自行处理）
- 独立 LLM Gateway 服务部署

### 演进路径

Phase 2 如果调用量上来或需要 prompt 版本管理、跨团队 prompt 共享、统一限流，将 SDK 升级为独立 LLM Gateway 服务。SDK 作为 Gateway 的客户端保留。

## 被拒绝的替代方案

1. **各服务各自调用**——每个服务自己管理 provider、API key、重试。被拒绝因为重复代码多、Token 统计口径不一致、provider 切换时每个服务都要改。

2. **独立 LLM Gateway 服务**——新增一个内部服务统一代理所有 LLM 调用。被拒绝因为 Phase 1 调用场景只有两个服务、量级不大，独立服务的部署和运维成本不值得。

## 后果

### 正面

- LLM 调用逻辑统一，provider 切换只改 SDK
- Token 用量统计集中，便于成本控制
- 重试和降级策略一致，减少各服务重复实现

### 负面

- SDK 是共享依赖，SDK 变更需要各服务配合升级
- 如果 SDK 出 bug，影响所有使用 LLM 的服务

## 复审条件

- 当调用量需要统一限流时
- 当需要 prompt 版本管理时
- 当需要跨团队 prompt 共享时
- 当 SDK 发版节奏成为瓶颈时（考虑升级为 Gateway 服务）
