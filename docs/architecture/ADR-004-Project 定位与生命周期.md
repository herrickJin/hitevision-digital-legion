# ADR-004：Project 定位与生命周期

## 上下文

PRD 定义 Project 为"一级业务容器"，承载项目成员、知识、数字员工实例和 Issue。但"项目"在企业中有两种含义：有明确起止时间的业务项目（A 型），和长期存续的组织空间（B 型）。Project 的定位直接影响权限模型、知识归属、数据生命周期和产品交互设计。

## 决策

**Phase 1 的 Project 定位为业务项目（A 型），但支持持续维护。**

### 具体含义

1. **Project 是以业务目标为核心的组织单元**
   - 有明确目标（Objective），注入所有数字员工实例的 System Prompt
   - 有生命周期（筹备中 → 进行中 → 已暂停 → 已归档）
   - 归档是主动决策，不是必然终点

2. **支持持续维护**
   - 进行中 → 已暂停 → 进行中是常态循环
   - 很多项目上线后进入长期维护期，Project 仍然在运行
   - 不强制项目必须归档

3. **Project 不是组织空间**
   - 不承载组织级知识库（Wiki 是组织级的）
   - 不承载组织级权限（权限跨项目存在）
   - 不承载跨项目实例复用

### Phase 2 保留

- 组织空间能力（团队级知识库、长期偏好、跨项目实例复用）
- 子项目或项目组层级
- 跨项目知识引用和实例共享

## 被拒绝的替代方案

1. **B 型组织空间**——Project 是长期团队空间，没有明确起止。被拒绝因为 Phase 1 核心链路（定义→引入→执行→交付）天然依附于有目标的业务项目，组织空间增加了概念复杂度。

2. **混合型**——同时支持 A 型和 B 型，用项目类型字段区分。被拒绝因为两种类型在权限、知识归属、状态机上的差异太大，Phase 1 承担不起。

## 后果

### 正面

- Project 概念简单，用户理解成本低
- Issue 和实例的归属明确（都绑定在具体业务项目上）
- 状态机简洁（4 状态），生命周期管理直接

### 负面

- 用户在多项目间的偏好不能自动迁移（由 ADR-005 的 Personal Memory 分层解决）
- 如果真实使用场景中有大量"长期空间"需求，Phase 1 的 Project 模型会显得局限

### 风险

- Phase 2 引入组织空间时，需要处理已有 Project 的迁移。缓解：Phase 1 在数据模型上预留 tenant_id，为后续扩展留空间。

## 复审条件

- 当试点用户反馈需要"长期空间"而非"业务项目"时
- 当 Phase 2 规划组织空间能力时
