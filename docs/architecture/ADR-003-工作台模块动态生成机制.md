# ADR-003：工作台模块动态生成机制

## 上下文

PRD 的核心差异化之一是"角色工作台不是聊天页"。不同数字员工角色（产品经理、前端研发、后端研发、测试工程师）需要不同的工作面模块组合。需要确定模块如何根据数字员工角色动态生成。

## 决策

### Phase 1 策略：平台预置标准模块 + tools.yaml 声明组合

1. **平台预置 10~15 个标准模块组件**，包括但不限于：
   - 代码库视图（code-view）
   - API 定义（api-docs）
   - 文档区（doc-editor）
   - 需求池（requirements）
   - 测试结果（test-result）
   - 组件库（component-lib）
   - 视觉走查（visual-review）
   - 用例库（test-cases）
   - 缺陷列表（bug-list）
   - 知识上下文（knowledge-context）
   - 构建状态（build-status）
   - 设计稿（design-view）

2. **tools.yaml 声明数字员工需要哪些模块**——Soul 压缩包里定义了工具集，每个工具在能力注册中心关联了模块类型，tools.yaml 选中的工具自动映射到对应模块

3. **不做自定义前端模块代码**——Phase 1 的差异化完全靠标准模块的排列组合实现

4. **联动事件是平台统一的**——所有模块自动接收 Issue 事件（issue_created、context_resolved、artifact_published 等），每个模块自己决定是否响应以及如何响应

### 模块生成流程

```
Soul 压缩包中的 tools.yaml
  → 声明工具列表
  → 能力注册中心查询每个工具关联的模块类型
  → 去重合并得到模块列表
  → 平台按模块列表渲染工作台布局
```

## 被拒绝的替代方案

1. **Soul 压缩包包含自定义前端代码**——允许数字员工定义者编写自定义 Vue/React 组件。被拒绝因为 Phase 1 安全风险高、审核成本大、标准模块已覆盖核心角色需求。

2. **前端根据工具类型自行推断模块**——没有显式映射，前端按 tool 名称猜测。被拒绝因为映射关系不明确，新增工具时前端需要硬编码适配。

3. **模块布局写死在 Soul 里**——soul.md 直接描述"第一行放代码库，第二行放终端"。被拒绝因为耦合太紧，布局调整需要改 Soul 压缩包。

## 后果

### 正面

- 工作台差异化通过声明式配置实现，不需要写代码
- 新增标准模块只需要平台发版，不需要改 Soul schema
- 联动事件统一管理，模块间行为一致

### 负面

- Phase 1 无法支持非标准模块需求（如果有角色需要全新的工作面组件，必须等平台扩展标准模块库）
- 标准模块数量有限（10~15 个），可能无法覆盖所有角色差异

## 复审条件

- 当标准模块无法满足新角色需求时
- 当需要支持第三方贡献模块时（Phase 2+）
- 当模块联动事件需要扩展时
