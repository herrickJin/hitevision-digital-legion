# ADR-007：Tool 到工作台模块的映射机制

## 上下文

工作台模块布局由 Soul 的工具集决定。需要明确 Tool 到模块的映射关系在哪里定义、如何维护。

## 决策

**映射关系在能力注册中心定义，作为 Tool 的自然属性。**

### 映射机制

1. **每个 Tool 在能力注册中心注册时，声明关联的标准模块类型**
   - 模块类型是枚举值，只能从平台预置的标准模块列表中选择
   - 不能自由填写或自定义

2. **tools.yaml 不直接声明模块**——只声明需要的 Tool 列表，平台根据 Tool 的模块映射关系推导出模块布局

3. **多对多映射**——一个 Tool 可以关联多个模块，一个模块可以被多个 Tool 关联。平台对结果去重。

### 映射流程

```
Soul 压缩包 tools.yaml
  → 声明 Tool ID 列表：[git, swagger, terminal]
  → 查询能力注册中心
    git → 关联模块：code-view
    swagger → 关联模块：api-docs
    terminal → 关联模块：terminal-view
  → 去重得到模块列表：[code-view, api-docs, terminal-view]
  → 渲染工作台布局
```

### Phase 1 约束

- 标准模块枚举由平台管理，Phase 1 约定义 10~15 个
- 新增 Tool 注册时必须选择一个已有模块类型，不能创建新模块
- 如果新 Tool 需要新模块，需要先由平台扩展标准模块库

## 被拒绝的替代方案

1. **平台硬编码映射表**——映射关系写死在平台代码里。被拒绝因为新 Tool 上线需要平台发版。

2. **Soul 压缩包直接声明模块**——tools.yaml 里显式写出需要哪些模块。被拒绝因为 Tool 和模块的映射被分散到每个 Soul 里，维护成本高且容易不一致。

## 后果

### 正面

- 第三方贡献新 Tool 时，注册时指定模块类型即可，不需要改平台代码
- 映射关系集中管理，便于审计和维护

### 负面

- 能力注册中心的模块枚举字段是扩展瓶颈——新模块类型需要平台发版
- Tool 注册时需要理解模块映射的含义，对 Tool 贡献者有一定认知要求

## 复审条件

- 当标准模块无法覆盖新角色需求时
- 当需要支持自定义模块组件时（Phase 2+）
