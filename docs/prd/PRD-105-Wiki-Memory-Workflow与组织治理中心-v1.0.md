## 1. 问题陈述

### 1.1 当前情况

数字员工要进入真实业务，不只需要会“回答”，还需要访问组织知识、积累经验、调用系统流程，并始终处在组织治理之下。

### 1.2 用户痛点

1. Wiki、Memory、RAG 概念混乱，团队容易把知识能力简化成“上传文档问答”。
2. 数字员工缺少长期经验沉淀机制。
3. 调用第三方系统时缺少统一权限、失败处理和审计模型。
4. 数字员工数量增长后，权限、质量、归档和评价治理会成为瓶颈。

### 1.3 业务影响

如果没有这套中心，数字员工只能做局部任务，无法形成组织级能力积累，也无法在规模化后保持可控。

---

## 2. 目标与方案

### 2.1 目标

建立数字员工的知识、记忆、流程接入和组织治理底座，为 Project 内任务执行和多数字员工协同提供持续能力。

### 2.2 方案概述

该中心由四个子域构成：

1. Wiki：组织显性知识。
2. Project Memory：项目执行中沉淀的公共经验、项目惯例和结果产物。
3. Personal Memory：个人偏好、通知偏好和个人视角下的关注记录。
4. Workflow：数字员工调用外部系统的流程连接层。
5. 组织治理：角色、权限、审计、评价、归档与风险控制。

### 2.3 成功指标

> [假设] 以下指标的数值目标基于同类产品经验和初步估算，尚未建立实际基线。试点阶段需采集真实数据修正目标值。

1. 知识引用可追溯率等于 100%。
2. Wiki 命中后被采纳比例持续提升。
3. 工作流调用成功率大于等于 85%。
4. 高风险操作审计覆盖率等于 100%。

## 3. 用户与场景

### 3.1 目标用户

| 用户 | 诉求 |
|---|---|
| 数字员工定义者 | 为原型配置可信知识和规则 |
| Project Member | 在项目任务中获得可信知识和系统执行能力 |
| 平台管理员 | 管理权限、审计、归档、风险矩阵 |
| 组织管理者 | 评估数字员工质量、价值和风险 |

### 3.2 关键场景

1. 为产品经理数字员工导入产品规范和模板库。
2. 在任务执行中记录项目惯例、项目复盘结论和个人偏好。
3. 数字员工通过工作流调用知识库、代码仓库、审批系统或 IM 系统。
4. 管理员追踪一次高风险工具调用的全链路审计记录。

## 4. 功能需求

### 4.1 Wiki 中心

1. 文档上传、链接导入、结构化分类。
2. 文档分段、向量化、检索测试。
3. 文档来源、版本、负责人记录。
4. 原型级、项目级和实例级知识绑定。

### 4.2 Memory 中心

1. 记录项目惯例、历史复盘结论、常用模式和用户偏好。
2. 区分短期上下文与长期记忆。
3. 支持 Project Memory 写入与检索。
4. Phase 1 支持 Personal Memory 作为项目成员的通用偏好层参与加载；项目特定偏好仅保留模型预留。
5. 支持记忆失效、清理与人工修正。

### 4.3 Workflow 中心

1. 定义外部系统接入节点。
2. 每个节点定义输入、输出、权限要求、失败处理、审计字段。
3. 支持研发、文档、审批、IM、知识库、代码仓库等高价值接入。
4. 支持工作流调用失败重试、人工接管和回退。

### 4.4 组织治理中心

1. 角色、业务域、负责人、编制、权限范围管理。
2. 原型、实例、Issue、协同、工作流、知识引用全链路审计。
3. 质量评价、使用反馈和归档规则。
4. 高风险工具、高风险知识源和高风险流程节点治理。
5. 归档、强制更新、回收和停用机制。

---

## 5. 设计要求

1. Wiki、Project Memory、Personal Memory、Workflow、组织治理五个概念必须在产品里被清晰区分。
2. 引用来源和记忆来源都必须可解释，不得混淆显示。
3. 治理能力优先做可追踪、可解释，不做过度复杂后台。

---

## 6. 技术需求

1. 依赖文档存储、向量检索、权限系统、审计系统、第三方连接器框架。
2. 需定义 Project Memory Item、Personal Memory Item、Workflow Action Record、Knowledge Source、Governance Policy 等对象模型。
3. 需支持引用追踪、权限拦截、失败回滚和审计查询。
4. 需支持与原型定义中心、实例中心、Issue 中心和协同中心的联动。

---

## 7. 实施计划

> PRD-105 覆盖四个子域（Wiki、Memory、Workflow、组织治理），以下按子域拆分独立节奏，每个子域内按里程碑推进。总体原则：Wiki 和 Memory 优先服务于主链路知识底座，Workflow 和治理在主链路稳定后逐步展开。

### 7.1 Wiki

| 阶段 | 交付内容 |
|---|---|
| M1 | Wiki 基础导入、分类、检索测试 |

### 7.2 Memory

| 阶段 | 交付内容 |
|---|---|
| M2 | Project Memory / Personal Memory 模型与读写 |

### 7.3 Workflow

| 阶段 | 交付内容 |
|---|---|
| M3 | Workflow 节点模型与首批连接器 |

### 7.4 组织治理

| 阶段 | 交付内容 |
|---|---|
| M4 | 组织治理策略、审计查询、归档与风险控制 |

资源建议：

1. 产品 1 人。
2. 后端 2 人（Wiki 存储与检索 + Memory 模型 + Workflow 节点引擎 + 治理审计）。
3. AI/平台 1 人（RAG 接入与 Memory 加载策略）。

---

## 8. 风险与缓解

| 风险 | 描述 | 缓解方式 |
|---|---|---|
| 把知识系统做成独立大工程 | 拖慢主链路验证 | Phase 1 先做基础 Wiki、Project Memory 和 Personal Memory 分层 |
| Memory 脏数据累积 | 影响数字员工判断 | 引入来源记录、过期和人工修正机制 |
| 工作流接入复杂度过高 | 平台陷入集成泥潭 | 先接入高价值少量系统，统一节点模型 |
| 治理规则过多影响效率 | 用户使用成本上升 | 风险分层治理，低风险自动化，高风险强管控 |

---

## 9. 验收标准

1. 任一知识引用都能追溯到文档来源与版本。
2. Project Memory、Personal Memory 与 Wiki 在数据模型和产品界面上必须区分。
3. 工作流调用必须具备权限校验、失败处理和审计记录。
4. 高风险操作必须可被审计、检索和归因。
