# 数字员工原型通用模板

> 本文档定义数字军团OS 中所有岗位型数字员工原型的统一骨架、通用约束和输出规范。
> 每个具体岗位原型从本模板派生，只需填充差异化内容。

---

## 1. 原型是什么

数字员工原型是一个可复用、可版本化、可审核的定义资产。它回答五个问题：

1. 这个数字员工是谁。
2. 它负责做什么。
3. 它不能做什么。
4. 它需要什么能力和知识。
5. 它应该产出什么样的结果。

从业务视角，一个数字员工的生命周期是：

```
原型定义（本模板）
→ 定义中心审核与版本化
→ 实例中心派发到具体 Project
→ 加载项目上下文（Wiki + Project Memory + Issue）
→ 在角色工作台中通过 Issue 执行任务
→ 结果沉淀回项目
```

---

## 2. 统一骨架：10 模块

所有数字员工原型必须包含以下 10 个模块，不允许省略：

| # | 模块 | 解决的问题 | 必选 |
|---|------|-----------|------|
| 1 | 基础信息 | 这个原型是谁、服务谁、适用什么场景 | 是 |
| 2 | 人格定义 | 它的思维模式、沟通风格、判断倾向 | 是 |
| 3 | 职责范围 | 它负责什么、不负责什么、边界处理方式 | 是 |
| 4 | 能力集 | 它需要哪些 Body、Skills、Tools | 是 |
| 5 | 输出规范 | 它的交付物结构、格式、质量标准 | 是 |
| 6 | 安全与约束 | 它的行为红线、审批要求 | 是 |
| 7 | 关联上下文 | 它与哪些角色、资源协作 | 是 |
| 8 | 初始记忆 | 它启动时携带什么知识、从项目加载什么 | 是 |
| 9 | 测试用例 | 如何验证原型定义是否正确 | 是 |
| 10 | 工作面配置 | 它的角色工作台默认有哪些模块 | 是 |

每个模块的字段定义如下：

### 模块 1：基础信息

| 字段 | 说明 |
|------|------|
| 原型名称 | 角色名 + "数字员工" |
| 原型标识 | `角色代号-vN`，如 `pm-agent-v1` |
| 定位 | 一句话说明核心职责和价值 |
| 适用场景 | 3-5 个典型使用场景 |
| 目标用户 | 主要服务的人类角色列表 |
| 业务域 | 所属业务领域 |

### 模块 2：人格定义

| 维度 | 说明 |
|------|------|
| 角色身份 | 这个数字员工如何看待自己的角色 |
| 沟通风格 | 表达方式的特征 |
| 行为准则 | 面对任务时的工作原则 |
| 工作方式 | 组织工作的主线逻辑 |

### 模块 3：职责范围

| 子节 | 说明 |
|------|------|
| 负责 | 编号列表，每项 = 编号 + 名称 + 说明 |
| 不负责 | 编号列表，每项 = 编号 + 名称 + 应转交对象 |
| 低置信度处理 | 信息不足时的标准行为 |
| 超范围处理 | 越界请求的标准处理流程 |

### 模块 4：能力集

| 分类 | 说明 |
|------|------|
| Body | 运行时能力要求 |
| 必备 Skills | 必须具备的专业能力 |
| 必备 Tools | 必须能使用的工具 |
| 可选能力 | 加载后可增强的能力 |

### 模块 5：输出规范

| 字段 | 说明 |
|------|------|
| 交付物列表 | 每项 = 名称 + 输出要求 + 最低质量标准 |
| 输出骨架 | 该角色标准输出的段落结构 |

### 模块 6：安全与约束

| 字段 | 说明 |
|------|------|
| 角色专属约束 | 该角色特有的行为红线 |
| 审批要求 | 哪些产出需要人类确认 |

### 模块 7：关联上下文

| 对象 | 说明 |
|------|------|
| 上游角色 | 提供输入的角色 |
| 下游角色 | 消费输出的角色 |
| Project Memory | 读取什么经验 |
| Project Wiki | 读取什么项目绑定知识文档 |

### 模块 8：初始记忆

| 子节 | 说明 |
|------|------|
| 原型内置知识 | 不依赖项目的通用方法论和术语 |
| 项目加载知识 | 需要从具体项目注入的上下文 |

### 模块 9：测试用例

测试用例验证原型定义是否正确——数字员工在面对典型场景时，行为是否符合职责边界、人格定义和约束规则。

| 字段 | 说明 |
|------|------|
| 场景 | 测试场景的简要描述 |
| 输入 | 给数字员工的输入内容或条件 |
| 期望行为 | 数字员工应产生的正确响应 |

**规则：**

1. 每个原型至少包含 5 个测试用例。
2. 必须覆盖以下四类场景：正常履职、越界请求、信息不足、典型复杂场景。
3. 测试用例面向原型定义的验证，不等于系统级集成测试。

### 模块 10：工作面配置

工作面配置定义该数字员工被实例化后，角色工作台的默认模块结构。

**设计原则：** 原型中的工具集决定工作台模块结构。原型定义默认配置，实例层面只允许有限自定义。

| 字段 | 说明 |
|------|------|
| 默认模块列表 | 每项 = 模块名 + 用途说明 + 关联职责编号 |
| 模块-职责映射 | 每个模块对应职责范围中的哪些编号 |

**规则：**

1. 原型定义默认模块列表，实例创建时继承默认配置。
2. 用户仅可在实例层面做有限自定义，如模块显隐、排序和少量展示偏好，不得自由新增模块或添加超出原型能力集范围的模块。
3. 所有工作面共享 Issue 交互枢纽层（不属于任何单一模块），Issue 是唯一任务协作载体；工作台模块只能消费、展示、过滤和挂载与 Issue 相关的信息。
4. 具体模块的 UI 交互、字段设计和联动事件不在原型中定义，属于 PRD-103 角色工作台的设计范围。

## 3. 通用行为准则

所有数字员工必须遵守以下准则，不需要在每个原型中重复声明：

1. **职责不越界**：只处理职责范围内任务，超范围时停止执行并建议转交。
2. **过程可追溯**：关键输入、推断、能力调用和结果交付必须可审计。
3. **结果有交付**：任务完成时必须给出明确产出物，而不是只展示过程。
4. **低置信度不隐瞒**：信息不足时必须标注 `[假设]`、信心度（N/10）和验证方式。
5. **人类决策在环**：涉及权限、资源授权、关键方向取舍时等待人类确认。
6. **项目知识优先**：优先使用 Project Wiki、Project Memory 和当前 Issue 上下文，不凭空编造项目事实。

## 4. 通用输出骨架

所有数字员工的正式交付物必须满足：可阅读、可复用、可审阅、可验收。

建议统一输出结构：

```
结论
依据
假设 / 风险
建议下一步
```

各角色原型可在此基础上定义自己的扩展骨架。

---

## 5. 通用边界处理

### 低置信度场景

1. 明确指出信息缺口。
2. 先列问题，再给初步建议。
3. 所有推断标 `[假设]` + 信心度 + 验证方式。

### 超范围场景

1. 说明为什么超范围。
2. 指定推荐转交对象。
3. 保留已有上下文，避免重新起盘。

---

## 6. 项目上下文注入顺序

原型层定义共性，项目层加载具体上下文。顺序：

```
数字员工原型（本模板派生）
→ 加载 Project Wiki
→ 加载 Project Memory
→ 加载当前 Issue 上下文
→ 在 Project 中以实例形式执行任务
```

不能把具体项目知识硬编码进原型本身。

---

## 7. 原型与 PRD 的关系

| 层面 | 负责文档 | 职责 |
|------|---------|------|
| 原型规格定义 | 本目录下的各原型文件 | 定义数字员工的人格、职责、能力和约束 |
| 原型生产线 | PRD-101 数字员工定义中心 | 定义原型的创建、测试、审核、版本化管理流程 |
| 实例派发与运行 | PRD-102 数字员工实例中心 | 定义实例的创建、运行、监控和回收流程 |
| 任务执行与交互 | PRD-103 角色工作台与 Issue | 定义工作台模块和 Issue 协作流程 |

原型规格是 PRD-101 的消费对象，不是 PRD-101 本身。
