## 1. 问题陈述

### 1.1 当前情况

很多智能体产品在使用层只有一个聊天页，用户虽然可以问问题，但无法把任务正式下发、跟踪、交付和沉淀。

### 1.2 用户痛点

1. Project Member 不知道如何在项目中用数字员工完成正式工作任务。
2. 不同角色的数字员工缺少差异化工作面。
3. 任务过程不可见，结果承接不正式。
4. 补充信息、越界、失败、转交等协作状态表达不清晰。

### 1.3 业务影响

如果工作台退化为聊天页，即便原型和实例都建立起来，用户仍无法在真实业务中稳定使用数字员工。

---

## 2. 目标与方案

### 2.1 目标

通过角色工作台和 Issue 协作中心，让数字员工成为 Project 中真正的“工作同事”而不是“对话工具”。

### 2.2 方案概述

工作台采用两层结构：

1. 角色工作面：由 Soul 工具集驱动的模块化工作区。
2. Issue 协议层：统一承载任务发起、执行、异常和结果交付。

两层之间必须存在明确联动：Issue 是任务状态源，角色工作台模块是任务上下文、执行对象和产物的专业呈现面。工作台模块不能只是只读挂件，必须根据 Issue 的结构化字段、状态事件和产物事件发生定位、刷新、提示或挂载。

### 2.3 成功指标

> [假设] 以下指标的数值目标基于同类产品经验和初步估算，尚未建立实际基线。试点阶段需采集真实数据修正目标值。

1. Project 内已派发实例周任务发起率持续提升。
2. Issue 创建成功率大于等于 85%。
3. 执行过程查看率大于等于 60%。
4. 结果采纳率大于等于 50%。

## 3. 用户与场景

### 3.1 目标用户

| 用户 | 诉求 |
|---|---|
| Project Member | 在项目中用数字员工完成正式任务 |
| 任务跟进人 | 跟踪项目内 Issue 状态与中间结果 |
| 项目负责人 / 管理者 | 查看项目任务结果、风险与转交记录 |

### 3.2 关键场景

1. 产品经理在 Project 工作台中发起 PRD 草拟任务。
2. 前端研发在 Project 工作台中发起组件实现与走查任务。
3. 用户查看 Issue 执行时间线和中间产出。
4. 因信息不足，系统向用户发起补充请求。
5. 因职责越界，系统拒绝执行并请求人类确认转交。
6. 前端研发执行“修改登录页”Issue 时，代码模块自动定位到相关仓库、分支、文件和变更区域。

## 4. 功能需求

### 4.1 角色工作台

1. 不同数字员工角色必须拥有不同模块组合。
2. 工作台至少展示工作区模块、知识上下文、运行状态、待办任务。
3. 支持实例层有限模块个性化调整。
4. Issue 入口嵌入工作台，但不能替代工作台。
5. 工作台模块必须订阅与自身相关的 Issue 事件，并基于任务上下文进行定位、过滤、刷新、锁定、提示或产物挂载。
6. 工作台模块必须能区分“当前 Issue 驱动状态”和“用户手动浏览状态”，避免任务执行过程覆盖用户主动查看内容。

### 4.2 Issue 与工作台模块联动

#### 4.2.1 联动原则

1. Issue 是 Project 内唯一任务协作载体，负责任务目标、状态、责任、过程和结果。
2. 工作台模块是角色化执行界面，负责呈现任务相关对象、上下文、产物和可操作入口。
3. Issue 不替代模块，模块也不绕过 Issue 创建独立任务。
4. 任一模块因任务产生的关键变更，必须回写到对应 Project Issue 的事件流或产物区。

#### 4.2.2 联动事件

Issue 至少需要向工作台模块输出以下事件：

| 事件 | 触发时机 | 模块响应 |
|---|---|---|
| `issue_created` | Issue 创建后 | 相关模块根据 structured brief 定位上下文 |
| `issue_started` | 数字员工开始执行 | 模块进入任务关联态，展示当前任务提示 |
| `context_resolved` | 系统识别到仓库、文档、需求、接口等对象 | 模块自动定位到相关对象 |
| `artifact_published` | 阶段性产物或最终产物生成 | 模块挂载产物并标记来源 Issue |
| `input_required` | 需要用户补充信息 | 相关模块高亮缺失字段或待确认对象 |
| `issue_completed` | Issue 完成 | 模块刷新最终状态并保留结果入口 |
| `issue_failed` | Issue 失败 | 模块展示失败原因和可重试入口 |

#### 4.2.3 典型模块联动

| 数字员工角色 | Issue 示例 | 被驱动模块 | 期望联动 |
|---|---|---|---|
| 产品经理 | 草拟登录页改版 PRD | 文档区、需求池、知识上下文 | 文档区创建草稿，需求池定位关联需求，知识上下文展示引用来源 |
| 前端研发 | 修改登录页交互 | 代码库视图、组件库、视觉走查 | 代码库定位相关文件，组件库定位登录组件，视觉走查挂载截图或差异结果 |
| 后端研发 | 新增登录接口字段 | API 定义、代码仓库、测试结果 | API 定位接口定义，代码仓库定位服务文件，测试模块展示自测结果 |
| 测试工程师 | 验证登录页回归 | 用例库、缺陷列表、测试结果 | 用例库定位相关用例，测试结果挂载报告，缺陷列表关联新问题 |

### 4.3 任务创建

1. 支持自然语言输入。
2. 系统自动提取 structured brief。
3. 用户确认后在当前 Project 中创建 Issue。
4. 支持附件、补充说明、优先级、时间要求。

### 4.4 Issue 状态机

#### 4.4.1 Phase 1 状态集（7 状态）

| 状态 | 类型 | 说明 |
|------|------|------|
| 待开始 | 初始态 | Issue 创建后等待人类确认发起执行 |
| 执行中 | 中间态 | 数字员工正在执行任务 |
| 等待补充信息 | 中间态 | 数字员工判定信息不足，等待人类补充 |
| 已完成 | 终态 | 数字员工执行完成并产出结果 |
| 执行失败 | 终态（条件性） | 执行异常。retry_count < 3 时可重试回到执行中；retry_count >= 3 后为终态 |
| 已拒绝 | 终态 | 数字员工判定任务越界，系统自动拒绝并给出原因和推荐可接手角色 |
| 已取消 | 终态 | Project Member 主动取消 |

> Phase 2 预留状态：待确认转交、已转交（见 PRD-104）。

#### 4.4.2 状态转换规则

| 从 | 到 | 触发者 | 触发条件 | 可逆 |
|---|---|---|---|---|
| 待开始 | 执行中 | 系统 | 人类确认 Issue 结构化内容后发起执行 | 否 |
| 待开始 | 已取消 | 人类 | Project Member 主动取消 | 否 |
| 执行中 | 已完成 | 系统 | 数字员工执行完成并产出结果 | 否 |
| 执行中 | 执行失败 | 系统 | 执行异常 | 是（retry_count < 3 时可回到执行中） |
| 执行中 | 等待补充信息 | 系统 | 数字员工判定信息不足 | 是（人类补充后回到执行中） |
| 执行中 | 已拒绝 | 系统 | 数字员工判定越界，自动拒绝 | 否 |
| 等待补充信息 | 执行中 | 系统 | 人类补充信息后恢复执行 | — |
| 等待补充信息 | 已取消 | 人类 | Project Member 主动取消 | 否 |

#### 4.4.3 执行页要求

1. 执行页必须展示任务信息、时间线、中间产出、异常与最终结果。
2. 工具调用信息分层展示。
3. 已完成后支持继续追问形成新 Issue 链。
4. Issue 执行过程中的上下文识别、工具调用和产物发布必须触发模块联动事件。
5. Phase 1 不引入任何自动超时机制，人类对自己的 Issue 负责。

### 4.5 异常处理

1. 缺信息时发起补充请求并在原 Issue 恢复。
2. 职责越界时停止执行并给出原因。
3. 推荐可接手实例，但高风险场景必须等待人类确认。
4. 执行失败后支持重试，重试次数上限为 3 次，由 Issue 对象的 retry_count 字段控制。
5. 执行失败状态下的 UI 表现：retry_count < 3 时展示"重试"按钮；retry_count >= 3 时无重试按钮，标记为终态。

### 4.6 最终交付

1. 正式结果区与过程日志分层。
2. 支持模板化结果输出，如 PRD、报告、代码、清单、方案对比等。
3. 展示结果摘要、正文、关键结论、引用材料和附件。
4. 最终结果必须同时进入 Issue 结果区，并按产物类型挂载到相关工作台模块。
5. 最终结果默认沉淀回 Project Output 或 Project Memory，不只保存在个人会话中。

## 5. 设计要求

1. 角色差异必须通过模块而不是仅通过头像或提示词表达。
2. 任务过程要以"可理解摘要"为主，不把系统噪声直接暴露给所有用户。
3. 最终结果区必须足够醒目，不能淹没在时间线中。
4. 补充信息态和越界态必须是明确的任务状态页，而不是普通弹窗。
5. 工作台模块的任务关联态必须可被用户识别，避免用户误以为模块内容是普通浏览结果。

### 5.1 关键页面设计交付清单

> 以下页面需由专业设计工具产出线框图/高保真原型，PRD 仅定义页面核心区域和要素。

| 页面 | 优先级 | 核心区域 | 设计要点 | 交付物 |
|------|--------|---------|---------|--------|
| 角色工作台首页 | P0 | Issue 列表/入口 + 工作台模块区 + Issue 交互枢纽 | 模块布局由 Soul 工具集决定；Issue 列表区与模块区的空间分配；视觉重心在模块区而非聊天 | 线框图 + 交互说明 |
| Issue 执行页 | P0 | 任务信息头 + 执行时间线 + 结果交付区 + 异常状态区 | 时间线分层展示；结果区醒目独立；等待补充信息/已拒绝/执行失败各有明确状态页 | 线框图 + 交互说明 |
| Issue 创建页 | P0 | structured brief 预览 + 确认/修改入口 | 自然语言输入 → 结构化预览 → 确认创建的三步流程 | 线框图 |
| 原型配置页（PRD-101） | P1 | 人格定义 + 职能范围 + 技能集 + 工具集 + 约束 + 测试 | 分步配置流程；必填/选填区分；实时校验反馈 | 线框图 |
| 实例管理页（PRD-102） | P1 | 实例列表 + 状态指示 + 更新/停止操作 | 实例运行状态可视化；批量操作支持 | 线框图 |

## 6. 技术需求

1. 依赖 TaskIssue、TaskEvent、TaskArtifact 等对象模型。
2. 依赖 runtime 事件回传协议。
3. 需支持 structured brief 校验、状态机、追问链和重试计数。
4. 需支持与实例运行状态联动。
5. 需定义 Issue 到工作台模块的事件协议，至少包括事件类型、关联 Issue、目标模块、上下文对象、产物引用和展示建议。
6. TaskIssue 必须包含 `project_id`、`agent_instance_id`、`created_by_member_id` 等项目归属字段。

## 7. 实施计划

| 阶段 | 交付内容 |
|---|---|
| M1 | 工作台框架、任务发起页 |
| M2 | Issue 状态机、执行页、结果区 |
| M3 | Issue 驱动模块定位、刷新和产物挂载 |
| M4 | 补充信息、失败重试、越界态 |
| M5 | 追问链、模板结果、多角色视图完善 |

资源建议：

1. 产品 1 人。
2. 前端 2 至 3 人（工作台模块化框架 + Issue 执行页 + 多模块联动）。
3. 后端 2 人（Issue 状态机 + 事件协议 + 模块挂载逻辑）。

## 8. 风险与缓解

| 风险 | 描述 | 缓解方式 |
|---|---|---|
| 工作台仍像聊天页 | 无法建立职业化体验 | 坚持模块化角色工作面设计 |
| 模块沦为只读挂件 | 用户无法在模块中感知任务推进 | 建立 Issue 到模块的事件驱动机制 |
| 过程展示过多 | 用户负担重 | 摘要优先、细节分层展开 |
| 状态过多用户看不懂 | 任务体验复杂 | 用清晰状态文案、图标和下一步动作提示 |
| 结果区不正式 | 无法沉淀成果 | 强制结果区和过程区分层 |

---

## 9. 验收标准

1. 至少支持三种角色工作台差异化模块布局。
2. Issue 执行页必须完整覆盖创建、执行、异常、结果四个阶段。
3. 越界场景不得自动继续执行。
4. 已完成任务上的继续追问必须形成新的 Issue 链接关系。
5. 至少三个核心模块必须能响应 Issue 事件并发生可见状态变化。
6. 前端研发“修改登录页”类 Issue 必须能驱动代码模块定位到相关代码对象或给出无法定位原因。
7. Issue 必须归属于一个明确 Project，结果必须可沉淀回 Project。
