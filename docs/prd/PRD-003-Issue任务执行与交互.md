## 1. 一句话结论

PRD-003 要解决的问题不是“让用户和 Agent 聊天”，而是把数字员工实例的任务协作正式收敛到 Issue 中，形成从任务发起、执行透明、结果交付到异常处理的完整闭环。

---

## 2. 为什么现在做

PRD-001 解决了数字员工怎么生产，PRD-002 解决了数字员工怎么订阅和派发，但产品目前只完成了“拥有数字员工”，还没有完成“真正使用数字员工”。

当前缺口主要有四个：

1. 用户不知道如何向数字员工下发任务。
2. 数字员工执行过程黑盒，用户无法判断进度和质量。
3. 结果没有正式交付位，过程与结果割裂。
4. 职责越界时没有清晰的人机协作机制。

如果 PRD-003 不成立，前两期能力无法形成真实业务闭环。

---

## 3. 目标用户与问题定义

### 3.1 目标用户

- 已订阅并派发数字员工的业务用户
- 任务发起人
- 任务跟进人
- 最终结果接收人
- 需要做任务协调的人类管理者

### 3.2 典型场景

用户围绕一个明确业务目标，把任务交给某个已派发数字员工处理，希望在执行过程中知道：

- 任务是否已开始
- 当前做到哪一步
- 是否需要补充信息
- 是否超出职责边界
- 最终结果在哪里

### 3.3 当前痛点

- 任务输入方式不清晰，用户表达成本高。
- 执行过程不可见，用户缺乏信任。
- 最终结果没有正式承接区。
- 越界时容易出现该拒绝的不拒绝、该上报的不汇报。

### 3.4 当前替代方式

如果继续靠聊天、IM、人工转述、文档协作承接，会导致：

- 过程分散
- 上下文不完整
- 状态不可追踪
- 责任边界不清
- 结果难归档

---

## 4. 产品目标

本期只做一件事：把“单 Agent、单任务、单 Issue”的主链路打通。

核心目标：

1. 用户可以低门槛地下发任务。
2. 用户可以看到任务执行过程，而不是只看最终黑盒结果。
3. 最终结果以正式交付形式沉淀。
4. 职责越界时系统明确拒绝，并进入“人类决策在环”的协调机制。

---

## 5. 成功标准

### 主指标

- 已派发数字员工的周任务发起率
- 任务完成率
- 结果被采纳率

### 辅助指标

- 任务创建成功率
- 结构化字段修正率
- 执行过程查看率
- 结果二次追问率

### 护栏指标

- 错误执行率
- 越权执行率
- 用户主动取消率
- 过程日志阅读放弃率

---

## 6. 范围边界

### 6.1 本次做

1. 基于 Issue 发起数字员工任务。
2. 支持自由输入 + 自动结构化提取 + 人工修正。
3. 支持任务状态流转。
4. 支持执行过程展示、工具调用摘要、阶段性产出展示。
5. 支持最终结果标准模板输出。
6. 支持补充信息请求与恢复执行。
7. 支持职责越界拒绝、推荐具体 Agent 实例，并汇报给人类确认。
8. 支持继续追问、重试、转交、取消等后续动作。

### 6.2 本次不做

1. 多 Agent 自动协同编排。
2. 复杂工作流配置器。
3. 跨 Issue 批量调度。
4. Agent 自主扩展职责边界。
5. 自动化质量评分系统。

### 6.3 边界原则

本期方案必须坚持“人类决策在环”。尤其在职责越界和任务转交场景下，系统只做识别、说明、推荐、汇报，不做自动拍板和自动编排。

---

## 7. 方案总览

整体方案是：把 Issue 定义为数字员工任务协作的唯一载体。

用户围绕一个 Issue 完成以下闭环：

1. 发起任务
2. 确认任务结构化信息
3. 跟踪执行过程
4. 接收中间反馈或补充请求
5. 接收最终结果
6. 在职责越界或失败时得到明确处理路径
7. 由人类决定是否协调、转交或重试

关键不是展示多少信息，而是确保用户始终知道：

- 当前发生了什么
- 系统为什么这么处理
- 下一步应该由谁做决定

---

## 8. 核心产品原则

1. Issue 是唯一任务载体。
2. 用户输入优先自然语言，系统负责结构化整理。
3. 执行过程默认透明，但展示以用户可理解摘要为主。
4. 工具调用信息按角色分层展示。
5. 最终结果必须与过程日志分层，并支持标准模板输出。
6. 职责越界必须明确拒绝，并汇报给人类确认，不允许系统自动转交。

---

## 9. 核心流程

### 9.1 主流程

1. 用户选择已派发数字员工实例。
2. 用户输入任务描述。
3. 系统自动提取结构化字段。
4. 用户确认后创建 Issue。
5. Agent 开始执行。
6. 用户在 Issue 中查看状态、过程和产出。
7. 任务进入以下分支之一：
   - 已完成
   - 等待补充信息
   - 已拒绝（职责越界）
   - 执行失败
   - 重试中
   - 已转交
8. 用户或管理者基于结果继续追问、协调、重试或关闭任务。

### 9.2 职责越界处理流程

1. 当前 Agent 识别任务越界。
2. 当前 Agent 停止执行并输出拒绝原因。
3. 系统推荐可接手的具体 Agent 实例。
4. 系统向人类汇报当前情况。
5. 由人类决定：
   - 不转交，结束当前任务
   - 转交给某个具体实例
   - 先协调后再决定
6. 若确认转交，任务进入“已转交”或“待人工协调后转交”链路。

### 9.3 补充信息流程

`待开始 -> 执行中 -> 等待补充信息 -> 执行中 -> 已完成/执行失败/已拒绝`

### 9.4 重试流程

`执行失败 -> 重试中 -> 执行中 -> 已完成/执行失败/已拒绝`

## 10. 页面结构

### 10.1 任务发起页

页面目标：让用户低门槛发起任务，同时把自然语言转换成可执行任务对象。

页面应包含：

- Agent 基本信息
- 自然语言输入框
- 自动提取的结构化字段
- 附件与补充信息区
- 创建任务 / 保存草稿按钮

关键规则：

- 自动提取结果必须允许编辑。
- 低置信字段必须提醒。
- 缺失核心目标不允许提交。

### 10.2 Issue执行主页面

页面目标：成为任务执行期间的统一工作台。

页面应包含：

- 顶部状态栏
- 左侧任务信息区
- 中部执行时间线
- 右侧结果 / 异常 / 待处理区

用户在此页应能直接知道：

- 当前任务内容
- 执行进度
- 是否需要补充信息
- 是否发生职责越界
- 最终结果在哪里

### 10.3 等待补充信息态

需要明确展示：

- 缺什么
- 为什么缺
- 如何补
- 补完后恢复执行

这是任务中断态，不是新任务入口。

### 10.4 职责越界态

这不是报错页，而是“拒绝 + 汇报 + 推荐 + 人类确认”的协作页。

页面应展示：

- 当前任务为什么越界
- 当前 Agent 为什么不处理
- 推荐接手的具体实例
- 汇报给人类的说明
- 人类可执行动作：确认转交 / 暂不转交 / 发起协调

### 10.5 最终结果区

最终结果必须从执行日志中被单独拎出来，形成正式交付区。

结果区至少包括：

- 结果摘要
- 正式正文
- 关键结论
- 附件 / 引用
- 模板类型
- 后续动作

## 11. 功能设计

### 11.1 任务创建

系统自动提取：

- 任务目标
- 输出要求
- 优先级
- 时间要求
- 风险提示

用户可修正后提交。核心要求不是“自动提取多聪明”，而是“结果可控、可改、可确认”。

### 11.2 状态管理

正式状态集：

- 待开始
- 执行中
- 等待补充信息
- 已完成
- 执行失败
- 已拒绝（职责越界）
- 待人工确认转交
- 已转交
- 重试中
- 已取消

要求：

- 所有状态变化都要有时间戳和原因。
- 用户能区分失败、越界、待确认、已转交、重试中。

### 11.3 执行过程展示

对用户可见的信息包括：

- 流式输出
- 中间步骤
- 工具调用摘要
- 阶段性产出

展示原则：

- 普通用户默认看摘要。
- 高权限角色可查看更多工具调用细节。
- 不直接把底层噪声日志暴露给所有人。

### 11.4 最终结果交付

最终结果必须支持标准模板输出，至少支持：

- PRD
- 报告
- 清单

结果内容包括：

- 标准模板正文
- 摘要
- 关键结论
- 引用材料
- 完成时间

### 11.5 补充信息交互

补充请求至少告诉用户：

- 缺什么
- 为什么需要
- 示例怎么填

补充后恢复原任务执行，不新建任务。

### 11.6 职责越界处理

一旦判断越界：

- 当前 Agent 停止执行
- 状态变为已拒绝（职责越界）
- 系统推荐具体 Agent 实例
- 系统向人类汇报
- 任务进入待人工确认转交
- 人类决定是否转交或协调

禁止系统自动直接转交。

### 11.7 后续动作

系统至少支持：

- 继续追问
- 取消任务
- 发起重试
- 确认转交
- 基于结果发起新任务

## 12. 数据对象与状态机草案

### 12.1 核心对象

建议核心对象：

- `TaskIssue`
- `TaskEvent`
- `TaskArtifact`
- `TaskBlocker`

### 12.2 TaskIssue 核心字段

- `id`
- `agent_instance_id`
- `title`
- `raw_prompt`
- `structured_brief`
- `status`
- `priority`
- `attachments`
- `created_by`
- `created_at`
- `updated_at`
- `due_at`
- `latest_result_id`
- `latest_blocker_id`
- `recommended_transfer_instance_ids`
- `human_decision_status`

### 12.3 structured_brief

- `goal`
- `expected_output_type`
- `constraints`
- `context_notes`
- `risk_notes`
- `confidence_map`

### 12.4 状态机定稿

状态集：

- `draft`
- `pending`
- `running`
- `waiting_for_input`
- `completed`
- `failed`
- `rejected_out_of_scope`
- `waiting_human_transfer_decision`
- `reassigned`
- `retrying`
- `cancelled`

关键流转：

- `draft -> pending`
- `pending -> running`
- `running -> waiting_for_input`
- `waiting_for_input -> running`
- `running -> completed`
- `running -> failed`
- `failed -> retrying`
- `retrying -> running`
- `running -> rejected_out_of_scope`
- `rejected_out_of_scope -> waiting_human_transfer_decision`
- `waiting_human_transfer_decision -> reassigned`
- `pending/running/waiting_for_input/retrying -> cancelled`

原则：

- 完成态不能回退为执行中。
- 越界后不能由系统自动继续执行。
- 已转交代表人类已做出明确转交决定。

## 13. 接口定稿原则

接口正式拆为两层：

### 13.1 前台接口

面向用户界面与业务系统，负责页面交互和状态查询：

- `CreateTaskIssue`
- `GetTaskIssueDetail`
- `ListTaskIssuesByAgent`
- `SaveTaskDraft`
- `GetTaskTimeline`
- `ReplyInputRequest`
- `ConfirmTaskTransfer`
- `RequestHumanCoordination`
- `RetryTaskIssue`
- `CancelTaskIssue`
- `GetFinalResultDetail`
- `CreateFollowupTask`

### 13.2 Runtime 内部协议

面向 Agent runtime 执行链路，负责事件、状态和产出回传：

- `StartTaskExecution`
- `UpdateTaskStatus`
- `EmitTaskEvent`
- `CreateInputRequest`
- `RejectTaskOutOfScope`
- `RecommendTransferInstances`
- `PublishStageArtifact`
- `PublishFinalResult`
- `ReportExecutionFailure`

原则：

- 前台接口只暴露业务需要。
- Runtime 内部协议承接执行细节和系统协同。

## 15. 风险与判断

### 主要风险

1. 过程展示过多，噪声压过结果。
2. 结构化提取不准，增加修正成本。
3. 页面信息量过大，导致理解门槛上升。
4. 人工确认链路若过重，会影响转交效率。
5. 模板结果输出如果约束过死，可能影响不同任务类型适配。

### 缓解思路

- 默认展示摘要，细节按角色分层展开。
- 对低置信字段显式提醒。
- 统一时间线承载执行过程。
- 人工确认只卡越界转交，不卡正常执行。
- 模板输出支持通用框架 + 类型化扩展。

### 当前判断

这期方案成立的关键不是能力炫技，而是边界清楚、流程顺畅、结果可消费、人类责任明确。

  信心度：8/10  
  验证方式：跟踪自由输入使用率和字段修正率。

  信心度：9/10  
  验证方式：跟踪执行页查看率和停留时长。

- [假设] 越界时“推荐实例 + 人类确认”比自动转交更符合真实协作场景。

## 17. 定稿结论

PRD-003 到这里已经完成定稿，当前版本的核心决策点如下：

1. Issue 是唯一任务载体。
2. 输入方式采用自由描述 + 自动提取 + 人工修正。
3. 执行过程默认透明。
4. 工具调用信息按角色分层展示。
5. 最终结果支持标准模板输出。
6. 职责越界时推荐具体实例，但必须由人类确认是否转交。
7. 状态机新增已转交、重试中、待人工确认转交等状态。
8. 接口拆为前台接口和 runtime 内部协议两层。

这版可以作为 PRD-003 的正式定稿进入评审和后续执行拆解。
