# PRD-001：Soul 可视化编排与数字员工原型管理

版本：v1.1 产品侧定稿  
产品：数字军团OS + 数字员工Agent
范围：Phase 1  
状态：最终版  
更新时间：2026-05-13

## 1. 背景与目标

### 1.1 背景

数字军团OS 的核心模型已确认为 Body / Soul / Issue：

- Body：能运行的通用智能体空壳，例如 Hermes Agent 或其他 Agent 框架。
- Soul：赋予 Body 特定领域思维模式、专业技能、职责边界、工具能力、交互上下文和初始记忆的配置方案。
- Issue：数字员工接收、拆解、执行和反馈任务的载体。

当前产品策略是先服务鸿合内部，为内部业务部门和产研团队提供数字员工能力；内部验证成熟后，再规划对外 SaaS 商业化。Phase 1 的首要任务不是直接做完整市场和商业化体系，而是先把“可复用数字员工原型”的生产、测试、审核和版本管理跑通。

如果没有 Soul 原型管理能力，会出现以下问题：

- Agent 能力依赖个人 prompt、脚本或零散配置，无法沉淀为平台资产。
- 通用 Agent 缺少领域人格、职责边界、专业知识和工具链，输出质量不可控。
- 后续市场上架、用户申请、实例派发、版本更新都缺少统一原型来源。
- 核心管理员和业务专家无法把“优秀数字员工的工作方式”沉淀成可复用标准。

### 1.2 战略目标

建立数字员工的“原型生产线”：让核心管理员和授权业务专家能够通过可视化方式定义 Soul，绑定 Body，配置能力与初始记忆，完成测试和审核，形成可上架、可派发、可版本化的数字员工原型。

PRD-001 解决的问题是：如何生产和治理一个合格的数字员工原型。市场订阅、实例派发和 Issue 执行分别进入后续 PRD。

### 1.3 成功指标

| 指标 | 当前值 | 目标值 | 衡量周期 |
|------|--------|--------|----------|
| 原型创建完成率 | 0 | 授权创作者创建 Soul 原型成功率 >= 80% | 上线后 4 周 |
| 原型配置耗时 | 无标准流程 | 完成一个基础 Soul 原型配置 <= 30 分钟 | 上线后 4 周 |
| 原型测试通过率 | 0 | 提交审核原型的基础测试通过率 >= 70% | 上线后 4 周 |
| 原型复用数量 | 0 | 至少沉淀 3 个可复用数字员工原型 | 上线后 6 周 |
| 配置错误拦截率 | 0 | 依赖缺失、权限缺失、运行时不兼容等问题发布前拦截率 >= 90% | 上线后 6 周 |
| 审核有效性 | 0 | 上架后因配置问题被下架/回退的原型 <= 10% | 上线后 8 周 |

## 2. 用户与场景

### 2.1 目标用户

| 用户群 | 描述 | 权限定位 |
|--------|------|----------|
| 核心管理员 | 负责平台级治理、Body/能力管理、审核、上架、归档 | 全局管理权限 |
| 授权业务专家 | 负责特定业务域 Soul 原型创建、知识沉淀、测试和提交审核 | 业务域内创建与维护权限 |
| 审核人 | 核心管理员 + 授权业务专家，负责从“待审核/待上架”到“已上架”的人工审核 | 审核权限 |
| 产研使用者 | 后续通过市场申请数字员工，本 PRD 中只作为原型目标用户被建模 | 只读或后续市场使用权限 |

### 2.2 核心场景

场景 1：创建产品经理数字员工原型

- 作为授权业务专家
- 我希望通过可视化界面定义“产品经理 Agent”的人格、职责、能力、工具和初始记忆
- 以便沉淀一个可复用的 PM Soul 原型，后续上架到内部市场

场景 2：配置基础 RAG 初始记忆

- 作为授权业务专家
- 我希望上传或导入业务文档、规范、方法论和案例，并完成向量化检索测试
- 以便 Soul 在执行任务时能基于可信领域知识回答和产出

场景 3：绑定 Body 与能力集

- 作为核心管理员或授权业务专家
- 我希望选择可用 Body，并绑定 Skills、MCP、Function Calling、Tools
- 以便明确该 Soul 能在哪些运行时环境中调用哪些能力

场景 4：测试职责边界与输出质量

- 作为创作者
- 我希望用职责内、职责外、工具调用、RAG 检索任务测试 Soul
- 以便在上架前发现职责模糊、依赖缺失、知识来源错误等问题

场景 5：审核并上架原型

- 作为审核人
- 我希望检查 Soul 的职责、能力、初始记忆、测试结果和风险项
- 以便只允许质量可控、风险可接受的数字员工原型进入市场

### 2.3 用户旅程

```text
进入原型管理
→ 新建 Soul 原型
→ 配置基础信息 / 人格 / 职责边界
→ 绑定 Body
→ 配置能力集
→ 配置关联上下文对象
→ 配置初始记忆与基础 RAG
→ 运行完整性、依赖、权限、兼容性校验
→ 测试沙箱验证
→ 保存版本并提交待审核/待上架
→ 审核通过后已上架
→ 审核驳回后返回草稿或测试中修改
```

### 3.2 版本号规则与变更分级

Soul 原型采用 Semantic Versioning（`MAJOR.MINOR.PATCH`），语义适配 Soul 原型场景。

#### 版本号规则

| 级别 | 版本号变化 | 触发条件 | 对已派发实例的影响 |
|------|-----------|---------|-------------------|
| Major（大版本） | x.0.0 → (x+1).0.0 | 职责范围变更、人格定义重写、输出规范根本性调整、安全约束收紧或放宽 | 需重审才能更新（对应 PRD-002 待重审更新） |
| Minor（小版本） | x.y.0 → x.(y+1).0 | 新增能力/Skill/MCP、新增初始记忆文档、能力集模块优化、RAG 知识库更新 | 用户可确认更新或暂缓 |
| Patch（补丁） | x.y.z → x.y.(z+1) | 错误修正、元数据描述修正、展示信息调整、非功能性优化 | 用户一键确认后直接更新，无需重审 |

#### 变更分级判定

创作者提交新版本时，系统根据变更内容自动建议版本号升级级别：

- 变更涉及「职责范围」「人格定义」「安全与约束」「输出规范」核心字段 → 自动建议 Major
- 变更涉及「能力集」「初始记忆/RAG」「关联上下文」模块字段 → 自动建议 Minor
- 变更仅涉及「基础信息」「展示信息」「描述备注」元数据 → 自动建议 Patch
- 创作者可手动上调版本号级别（保守方向），不可下调（不能把 Major 变更标为 Patch）

[假设] Phase 1 内部使用阶段，变更频率低且创作者数量少，自动建议 + 人工确认足够，不需要复杂的 diff 算法。
信心度：8/10
验证方式：上线后跟踪自动建议被创作者修正的比例，如果 > 30% 说明判定规则需要调优。

#### 快照机制

- 快照生成时机：每次版本从「待审核/待上架」进入「已上架」时，系统自动生成完整 Soul 配置快照。
- 快照内容：Soul 全量配置 + 绑定的 Body 信息 + 能力集版本 + 初始记忆版本索引。
- 回滚粒度：回滚到指定已上架版本的完整快照，不做字段级回滚。

### 3.3 Soul 原型结构

```text
Soul = {
  基础信息,
  人格定义,
  职责范围,
  能力集: {
    Skills,
    MCP,
    Function Calling,
    Tools
  },
  关联上下文对象,
  初始记忆与基础 RAG,
  输出规范,
  安全与约束,
  测试用例,
  审核记录,
  版本信息
}
```

### 3.4 权限模型

Soul 原型创建权限归属于：核心管理员 + 授权业务专家。

| 角色 | 权限 |
|------|------|
| 核心管理员 | 创建、编辑、测试、提交审核、审核、上架、下架、归档所有 Soul 原型；管理 Body、能力注册项、业务域授权 |
| 授权业务专家 | 在被授权业务域内创建、编辑、测试、提交审核 Soul 原型；可参与该业务域原型审核 |
| 审核人 | 由核心管理员和授权业务专家组成，对待审核原型进行通过或驳回 |
| 只读用户 | 查看已上架或可申请的原型摘要，不可修改配置 |

权限原则：业务专家必须先被核心管理员授权到具体业务域，不能默认创建任意类型 Soul 原型。所有创建、编辑、测试、提交、审核、上架、归档操作都必须进入审计日志。

### 3.5 状态流转

```text
草稿
→ 测试中
→ 待审核/待上架
→ 已上架
→ 已归档
```

驳回路径：

```text
待审核/待上架 → 审核驳回 → 返回草稿或测试中
```

状态规则：

- 草稿：可编辑，可保存，不可被市场使用。
- 测试中：可运行测试沙箱，不可上架。
- 待审核/待上架：配置冻结，等待审核人审核。
- 已上架：可被 PRD-002 的市场模块展示、申请、订阅和派发。
- 已归档：不可新申请。已派发实例的核心 Soul 被回收重置为空白状态，用户收到通知需尽快保存工作内容并重新申请其他数字员工。详细规则见 PRD-002「3.10 原型下架影响」。

### 3.6 初始记忆与基础 RAG

一期需要支持基础向量检索 / RAG，作为 Soul 的领域知识底座。

一期做：

- 文档上传或链接导入。
- 文档解析与分段。
- 向量化入库。
- 知识来源分类：领域知识、规范、方法论、模板、案例。
- 检索测试：输入测试 Query，展示命中文档片段。
- 引用来源展示：Agent 输出或测试结果中展示主要来源。
- 知识版本记录：记录文档版本、导入时间、负责人。

一期不做：

- 复杂知识图谱。
- 自动知识治理。
- 多源知识自动冲突解决。
- 模型权重训练 / Fine-tuning 管理。

### 3.7 审核机制

从“待审核/待上架”到“已上架”必须人工审核。审核人是核心管理员和授权业务专家。

审核重点：

- 职责边界是否清晰。
- 输出规范是否明确。
- Body 与能力依赖是否完整。
- PC / Linux 运行时是否兼容。
- 初始记忆和 RAG 来源是否可信。
- 测试任务是否覆盖职责内、职责外、工具调用、RAG 检索。
- 是否存在越权工具、敏感数据、错误知识来源等风险。
- 是否有版本号、负责人、变更说明和适用范围。

审核结果：

- 通过：进入已上架。
- 驳回：返回草稿或测试中，并要求填写驳回原因。

### 3.8 Not in Scope

本 PRD 不做：

- 数字员工市场的浏览、搜索、申请、订阅、派发流程，这部分进入 PRD-002。
- Issue 任务创建、执行、反馈完整流程，这部分进入 PRD-003。
- 移动端、iOS、Android、大屏运行时适配，一期只考虑 PC + Linux 服务器。
- Token 计费、充值、套餐、账单。
- 多 Agent 自动协同编排。
- Soul 继承机制完整产品化。
- 模型权重训练和 Fine-tuning 管理。
- 第三方开发者开放平台。
- 对外 SaaS 商业化入口。

## 4. 策略设计

### 4.1 策略目标

PRD-001 的策略核心是配置质量控制与上架治理：确保 Soul 原型在进入市场前定义完整、依赖可运行、知识来源可信、职责边界清晰、测试结果可追踪、审核责任明确。

### 4.2 输入信号

| 信号类型 | 来源 | 实时/离线 | 说明 |
|----------|------|-----------|------|
| Soul 基础配置 | 创作者输入 | 实时 | 名称、角色、职责、输出规范等 |
| 能力元数据 | 能力注册中心 | 实时 | Skills/MCP/Function/Tools 的接口、权限、依赖、版本 |
| Body 元数据 | Body 管理模块 | 实时 | Body 类型、支持运行时、能力兼容性 |
| 初始记忆文档 | 文档/知识库 | 离线为主 | 领域知识、规范、方法论、案例 |
| RAG 检索结果 | 向量检索服务 | 实时 | 测试 Query 的命中片段、来源、相似度 |
| 测试任务 | 创作者配置 | 实时 | 职责内、职责外、工具调用、RAG 检索测试 case |
| 审核记录 | 审核人输入 | 实时 | 通过/驳回、意见、风险项 |

### 4.3 策略逻辑

PRD-001 负责原型层校验（L1 配置完整性 + L2 依赖兼容性），确保原型本身合格后才能上架。实例派发时的实例级校验（L3）由 PRD-002 负责，三者职责不重叠。

#### L1 配置完整性校验

必须满足：

- 基础信息完整。
- 至少定义一个职责范围。
- 至少绑定一个 Body。
- 存在输出规范。
- 配置职责外处理策略。
- 配置至少一组测试任务。

兜底规则：未通过完整性校验的原型只能保存草稿，不能进入测试中或待审核/待上架。

#### L2 依赖兼容性校验

必须校验：

- 绑定能力是否存在。
- 能力版本是否可用。
- Body 是否支持该能力。
- PC / Linux 运行时是否支持该能力。
- 权限与鉴权配置是否完整。

兜底规则：发现阻塞项时允许保存，但不能提交审核。

说明：L1/L2 校验通过后结果缓存，PRD-002 派发实例时不再重复执行原型层校验，只做实例级校验（L3）。

#### RAG 质量校验

必须支持：

- 检索测试 Query。
- 展示命中文档片段和来源。
- 标记无命中、低相关、来源缺失等问题。

兜底规则：RAG 检索不可用时，该 Soul 仍可保存草稿，但不能进入已上架；如果该 Soul 不依赖 RAG，需要明确标记“不使用初始记忆检索”。

#### 职责边界测试

每个 Soul 至少配置：

- 1 个职责内任务。
- 1 个职责外任务。
- 1 个工具调用或 RAG 检索任务。

兜底规则：未通过基础测试时，不能进入待审核/待上架。

#### 发布门禁

进入已上架必须满足：

- 完整性校验通过。
- 依赖与兼容性校验无阻塞项。
- RAG 来源可信且检索测试通过，或明确声明该 Soul 不使用 RAG。
- 基础测试任务通过。
- 有版本号、负责人、适用范围和变更说明。
- 核心管理员或授权业务专家人工审核通过。

### 4.4 冷启动方案

一期提供 3 个内置原型模板：

- 产品经理 Agent：需求澄清、PRD/MRD、任务拆解。
- 前端研发 Agent：前端代码实现、组件开发、前端问题分析。
- 后端研发 Agent：API、数据结构、服务逻辑、后端问题分析。

每个模板预置：基础人格、职责范围、输出规范、职责外处理策略、示例测试任务、初始记忆分类示例。能力集先以最小可用集合为准，后续由核心管理员和业务专家逐步扩展。

### 4.5 评估方案

一期不做严格流量 A/B，采用内部试运行对比。

| 分组 | 对象 | 策略描述 | 核心指标 |
|------|------|----------|----------|
| 对照组 | 手工 prompt / 手工配置方式 | 继续用非标准化方式创建 Agent | 创建耗时、可复用性、错误率 |
| 实验组 | PRD-001 编排方式 | 使用 Soul 可视化编排创建原型 | 创建耗时、测试通过率、复用数量、审核通过率 |

### 5.1 数据需求

- Soul 原型配置数据。
- Body 元数据。
- 能力元数据。
- 初始记忆文档、分段、向量索引和来源信息。
- 测试任务和测试结果。
- RAG 检索测试记录。
- 版本记录和变更说明。
- 审核记录和驳回原因。
- 操作审计日志。

### 5.2 性能要求

- 原型列表加载：P95 <= 2 秒。
- 单个原型配置保存：P95 <= 1 秒。
- 配置校验返回：P95 <= 5 秒。
- 文档导入后进入可检索状态：基础文档 P95 <= 3 分钟。
- 检索测试返回：P95 <= 5 秒。
- 测试任务启动：P95 <= 10 秒。
- 基础测试任务结果返回：<= 60 秒。

### 5.3 安全与合规要求

- 初始记忆文档必须记录来源、上传人、时间和版本。
- 敏感文档应支持权限控制，未授权 Soul 不得检索。
- 工具调用必须有权限边界，不允许业务专家绕过授权绑定高风险工具。
- 审核记录不可删除，只允许追加修订。
- 已上架版本不可直接修改，只能发布新版本。

## 6. 风险与降级

| 风险 | 概率 | 影响 | 降级方案 |
|------|------|------|----------|
| 可视化编排范围过大，拖慢一期交付 | 高 | 高 | 一期采用分步表单 + 模块配置，不做自由画布 |
| RAG 做深后变成独立知识工程项目 | 中 | 高 | 一期只做基础 RAG：导入、分段、向量化、检索测试、来源展示 |
| Skills/MCP/Function/Tools 抽象不统一 | 中 | 高 | 先定义统一能力元数据 schema，少量能力接入验证后扩展 |
| Soul 职责边界定义模糊 | 中 | 高 | 强制职责内/职责外测试任务，未通过不能提交审核 |
| 初始记忆质量差，影响 Agent 输出 | 中 | 中 | 审核检查知识来源，测试沙箱展示检索命中和引用来源 |
| 审核流于形式 | 中 | 中 | 审核必须填写结果和意见，驳回必须填写原因，全部进入审计日志 |
| Body 与运行时兼容性复杂 | 中 | 中 | 一期只支持 PC + Linux，并在校验阶段阻断不兼容项 |
| 业务专家配置复杂能力出错 | 中 | 中 | 通过模板、权限边界、校验和审核降低错误进入市场的概率 |

## 8. 明确结论

1. PRD-001 只负责 Soul 原型创建、配置、测试、版本、审核、上架前治理，不负责市场订阅和实例派发。
2. 一期可视化编排采用“分步表单 + 模块化配置”，暂不做自由画布。
3. Soul 原型创建权限属于核心管理员和授权业务专家。
4. 初始记忆一期支持基础向量检索 / RAG。
5. 原型从“待审核/待上架”到“已上架”必须人工审核，审核人为核心管理员和授权业务专家。
6. 一期运行时优先支持 PC + Linux 服务器，移动端和大屏后续处理。
7. 三个冷启动模板为产品经理 Agent、前端研发 Agent、后端研发 Agent。
