## 1. 一句话结论

数字军团OS 的核心模型不应再被定义为 `Body / Soul / Issue`，而应升级为：

```text
Project / Soul Prototype / Agent Instance / Issue / Runtime
```

其中最关键的变化是：

**Project 是一级实体，数字员工实例优先归属于项目，不直接归属于个人。**

人通过参与项目来使用数字员工，Issue 也必须在项目上下文中发起、执行和沉淀。

---

## 2. 为什么要重写核心概念模型

现有 PRD-001/002/003 已经分别定义了：

- 如何生产一个可复用的 Soul 原型
- 如何在市场中申请和派发数字员工实例
- 如何通过 Issue 与数字员工协作

但三份文档仍然默认了一个隐含前提：

```text
用户 → 订阅数字员工 → 获得个人实例 → 通过 Issue 协作
```

这个前提不符合当前真实业务组织方式。

当前更符合业务现实的模式是：

```text
项目 → 获得数字员工实例 → 项目成员通过 Issue 协作 → 结果沉淀到项目
```

因此需要一份上位文档，统一回答以下问题：

1. 数字军团OS 中最核心的一级实体到底有哪些。
2. 这些实体之间是什么关系。
3. 每个实体的归属边界、生命周期和职责边界是什么。
4. PRD-001/002/003 中哪些定义可直接沿用，哪些需要被修订。

---

## 3. 建模目标与边界

### 3.1 建模目标

本模型用于统一产品、架构、研发和管理层的认知，作为后续 PRD 修订和系统设计的基础。

本次重点解决：

1. 明确 Project 的一级实体地位。
2. 明确 Soul 原型、项目实例、Issue 三层关系。
3. 明确平台资产与项目资产的边界。
4. 明确“谁拥有数字员工”这个核心归属问题。
5. 为后续项目管理、市场重构、任务中心重构提供统一基础。

### 3.2 本次不解决

1. 不展开具体页面交互设计。
2. 不展开数据库表结构。
3. 不展开多 Agent 自动编排细节。
4. 不定义商业化计费模型。

---

## 4. 建模原则

### 4.1 项目优先，不以个人为中心

数字员工服务的对象首先是项目目标，而不是某一个人的临时会话。

### 4.2 原型与实例分离

Soul 原型是平台资产，Agent Instance 是项目运行资产，两者必须分层治理。

### 4.3 任务必须有上下文容器

Issue 不是孤立任务单，而是项目业务主线中的执行单元。

### 4.4 资产归属清晰

- 平台负责管理通用资产：Soul、Body、Capability、Runtime 注册信息。
- 项目负责管理业务资产：项目成员、项目记忆、项目资源、项目实例、项目 Issue。

### 4.5 人类决策在环

数字员工可以执行、建议、汇报，但项目目标、权限边界、资源授权、关键决策仍由人类负责。

## 5. 核心概念全景

### 5.1 一级实体

本版本定义 8 个核心实体：

| 实体 | 类型 | 说明 |
|------|------|------|
| Project | 业务实体 | 业务协作和数字员工使用的一级容器 |
| Member | 参与者实体 | 进入项目的人类成员 |
| Soul Prototype | 平台资产 | 可被生产、审核、上架、版本化的数字员工原型 |
| Agent Instance | 运行实体 | 某个项目中实际运行的数字员工实例 |
| Issue | 任务实体 | 项目成员向数字员工发起任务协作的唯一载体 |
| Runtime | 基础设施实体 | 承载实例运行的环境、节点或容器 |
| Body | 执行载体实体 | 可运行的通用智能体空壳 |
| Capability | 能力实体 | Skills、MCP、Tools、Functions 等能力单元 |

### 5.2 关键二级概念

| 概念 | 归属 | 说明 |
|------|------|------|
| Project Memory | Project | 项目公共知识、文档、规范、沉淀结果 |
| Project Resource | Project | 仓库、链接、工具链、配置项、外部系统入口 |
| Project Workflow | Project | 项目主线、阶段、关键里程碑、任务脉络 |
| Market Agent | Soul Prototype 的市场视图 | 面向订阅与派发的展示和治理包装层 |
| Version Snapshot | Soul Prototype / Agent Instance | 用于追溯和更新比较的版本快照 |

## 6. 新的核心关系模型

### 6.1 核心关系图

```text
数字军团OS 平台
│
├── Soul Prototype
│   ├── 绑定 Body
│   ├── 依赖 Capability
│   ├── 包含初始记忆
│   └── 通过审核后进入 Market Agent
│
├── Project
│   ├── Member
│   ├── Project Memory
│   ├── Project Resource
│   ├── Project Workflow
│   └── Agent Instance
│       ├── 来源于 Soul Prototype
│       ├── 运行在 Runtime
│       ├── 服务于当前 Project
│       └── 承载多个 Issue
│           ├── 由 Member 发起
│           ├── 在 Project 上下文中执行
│           └── 结果回写 Project
│
└── Runtime
    └── 提供 Agent Instance 的运行环境
```

### 6.2 核心结论

1. **Soul Prototype 不直接服务最终任务，它只定义“这个数字员工是什么”。**
2. **Agent Instance 才是实际工作的执行主体。**
3. **Project 是 Agent Instance 的归属容器。**
4. **Issue 是 Project 内部的人机协作载体，不是平台级孤立对象。**
5. **Runtime 与 Body 决定“能不能跑”，Soul 决定“像谁、会什么、守什么边界”。**

## 7. 实体定义

### 7.1 Project

#### 定义

Project 是数字军团OS中的一级业务实体，是人、任务、知识、资源和数字员工协同发生的统一容器。

#### 为什么必须是一级实体

因为真实业务不是“一个人单独拥有一个数字员工”，而是“一个项目需要若干数字员工协助推进目标”。

如果没有 Project 这个一级实体，会导致：

- 实例归属不清，容易退化为个人玩具。
- 项目知识无法沉淀为公共上下文。
- 成员协作、权限、配额、资源授权无法统一管理。
- Issue 无法挂载到业务主线上，只能成为零散会话。

#### 核心属性

| 属性 | 说明 |
|------|------|
| project_id | 项目唯一标识 |
| name | 项目名称 |
| objective | 项目目标 |
| owner | 项目负责人 |
| members | 项目成员与项目内角色 |
|| status | 项目状态：筹备中、进行中、已暂停、已归档（详见 PRD-100 §5.3 Project 状态机） |
| memory_space | 项目公共知识空间 |
| resource_set | 项目资源集合 |
| workflow | 项目阶段和主线任务结构 |
| agent_instances | 已分配的数字员工实例集合 |

#### 生命周期

```text
筹备中 → 进行中 ⇄ 已暂停 → 已归档
筹备中 → 已归档
```

#### 核心职责

1. 承载项目成员协作关系。
2. 承载项目公共记忆与公共资源。
3. 成为数字员工实例的默认归属单位。
4. 成为 Issue 的上位上下文容器。
5. 成为结果沉淀和过程追踪的归档单位。

### 7.2 Member

#### 定义

Member 是参与某个 Project 的人类成员，不等于平台用户的全局身份，而是“平台用户在项目中的角色化投影”。

#### 核心属性

| 属性 | 说明 |
|------|------|
| member_id | 成员唯一标识 |
| user_id | 对应的平台用户 |
| project_role | 项目内角色，如经营管理者、产品经理、架构师 |
| permissions | 在该项目内的权限集合 |
| joined_at | 加入项目时间 |

#### 核心职责

1. 发起和跟进 Issue。
2. 管理项目内资源和知识。
3. 使用被分配到项目的数字员工实例。
4. 对关键决策和关键授权负责。

### 7.3 Soul Prototype

#### 定义

Soul Prototype 是平台层的数字员工原型资产，定义一个数字员工的身份、职责、能力边界、输出规范和初始记忆。

#### 核心属性

| 属性 | 说明 |
|------|------|
| soul_id | 原型唯一标识 |
| version | 语义化版本号 |
| persona | 人格和角色设定 |
| responsibility_scope | 职责范围 |
| constraints | 安全约束和行为红线 |
| capabilities | 依赖的能力集 |
| body_binding | 绑定的 Body |
| initial_memory | 初始知识和默认上下文 |
| review_status | 草稿、待审核、已上架、已归档 |

#### 核心职责

1. 定义“数字员工是谁”。
2. 约束实例可做和不可做的事情。
3. 成为市场分发和项目实例化的源头。
4. 为项目实例更新提供版本比较基线。

### 7.4 Agent Instance

#### 定义

Agent Instance 是由 Soul Prototype 派生出来、实际归属于某个 Project 的运行中数字员工实例。

它不是原型，也不是市场商品，而是项目里的真实执行单元。

#### 核心属性

| 属性 | 说明 |
|------|------|
| instance_id | 实例唯一标识 |
| source_soul_id | 来源原型 |
| source_version | 派发时使用的原型版本 |
| project_id | 所属项目 |
| runtime_id | 所在运行环境 |
| status | 运行状态 |
| project_context | 绑定的项目上下文 |
| custom_overrides | 允许的项目级有限定制 |
| issue_count | 已承载任务数量 |

#### 生命周期

```text
待派发 → 运行中 → 暂停 → 更新中 → 已回收 / 已删除
```

#### 核心职责

1. 在项目上下文中执行任务。
2. 继承 Soul 原型定义，同时加载项目知识和项目资源。
3. 为多个 Issue 提供连续服务。
4. 作为项目内可被分配、启停、更新、回收的运行资产。

#### 关键约束

1. 一个实例必须且只能归属于一个 Project。
2. 一个实例必须来源于一个明确版本的 Soul Prototype。
3. 一个实例必须运行在一个可用 Runtime 上。
4. 一个实例可以被多个项目成员共同使用，但所有行为都需审计。

### 7.5 Issue

#### 定义

Issue 是项目成员与 Agent Instance 协作的唯一任务载体。

它不是聊天记录，而是带状态、带上下文、带交付结果的项目任务单。

#### 核心属性

| 属性 | 说明 |
|------|------|
| issue_id | 任务唯一标识 |
| project_id | 所属项目 |
| instance_id | 被指派的数字员工实例 |
| creator_id | 发起成员 |
| goal | 任务目标 |
| structured_brief | 结构化任务说明 |
| status | 任务状态 |
| outputs | 阶段产出和最终结果 |
| audit_trail | 过程记录 |

#### 生命周期

```text
草稿 → 待确认 → 运行中 → 等待补充 → 已完成 / 已取消 / 已失败
```

#### 核心职责

1. 承载任务输入、执行过程和结果交付。
2. 把项目上下文、实例能力和用户目标绑定到一次具体协作中。
3. 形成可追踪、可审计、可追问的项目执行记录。

#### 关键约束

1. Issue 必须归属于一个 Project。
2. Issue 必须挂载到一个明确的 Agent Instance。
3. 超出 Soul 职责边界时，Issue 不能自动推进执行。
4. Issue 的结果默认沉淀回 Project，而不是仅保存在个人会话中。

### 7.6 Runtime

#### 定义

Runtime 是承载 Agent Instance 运行的基础环境，可以是 PC、Linux 节点、容器或后续云端执行环境。

#### 核心属性

| 属性 | 说明 |
|------|------|
| runtime_id | 运行环境唯一标识 |
| runtime_type | 环境类型 |
| status | 可用、繁忙、异常、下线 |
| capacity | 资源容量 |
| compatibility | 支持的 Body / Capability 范围 |

#### 核心职责

1. 提供实例运行资源。
2. 提供兼容性判断基础。
3. 提供容量、健康、异常监控。

### 7.7 Body

#### 定义

Body 是可承载 Soul 的通用智能体执行壳，是数字员工得以运行的基础技术载体。

#### 核心职责

1. 提供基础推理与执行框架。
2. 决定可支持的 Runtime 范围。
3. 决定对 Capability 的兼容边界。

### 7.8 Capability

#### 定义

Capability 是数字员工可调用的能力单元，包括 Skills、MCP、Functions、Tools 等。

#### 核心职责

1. 决定数字员工“会做什么”。
2. 决定依赖关系、权限要求和版本兼容性。
3. 作为 Soul 编排和实例执行的重要依赖层。

## 8. 三层资产边界

### 8.1 平台资产

由平台统一生产和治理：

- Soul Prototype
- Body 注册信息
- Capability 注册信息
- Runtime 注册信息
- 市场展示规则
- 审核规则

### 8.2 项目资产

由项目运行过程沉淀和维护：

- Project 本身
- Project Memory
- Project Resource
- Agent Instance
- Issue
- 项目内结果产出

### 8.3 个人资产

仅作为辅助层存在，不应成为系统主模型中心：

- 个人偏好
- 个人通知
- 个人待办
- 个人视角下的关注 Issue

核心原则：**个人只能作为使用入口，不能作为数字员工归属中心。**

## 9. 关键关系约束

### 9.1 归属关系

```text
Soul Prototype 属于平台
Agent Instance 属于项目
Issue 属于项目
Member 属于项目
Runtime 属于平台基础设施
```

### 9.2 派发关系

```text
一个 Soul Prototype
→ 可派生多个 Agent Instance
→ 每个 Agent Instance 只能归属于一个 Project
→ 一个 Project 可以拥有多个 Agent Instance
```

### 9.3 执行关系

```text
一个 Project
→ 包含多个 Issue
→ 每个 Issue 在任一时刻只绑定一个主执行 Agent Instance
→ 一个 Agent Instance 可以持续处理多个 Issue
```

### 9.4 上下文关系

```text
Soul Prototype 提供原型级初始记忆
Project 提供项目级公共上下文
Issue 提供任务级临时上下文
```

这三层上下文不能混淆。

## 10. 核心业务链路

### 10.1 原型生产链路

```text
授权创作者 / 核心管理员
→ 创建 Soul Prototype
→ 绑定 Body 与 Capability
→ 配置初始记忆
→ 测试与审核
→ 上架为可订阅 Market Agent
```

### 10.2 项目启用链路

```text
创建 Project
→ 配置成员、资源、记忆、主线
→ 从市场选择合适原型
→ 派发为 Project 级 Agent Instance
→ 加载项目上下文
→ 开始服务项目
```

### 10.3 任务执行链路

```text
Project Member 发起 Issue
→ 选择目标 Agent Instance
→ 系统做职责与约束校验
→ Agent Instance 在 Project 上下文中执行
→ 输出过程和结果
→ 结果沉淀回 Project
```

### 10.4 版本更新链路

```text
Soul Prototype 发布新版本
→ 系统识别受影响 Project Instance
→ 判断兼容性与是否需要重审
→ 由项目负责人或授权角色确认更新
→ Instance 更新到新版本
```

## 11. 与现有 PRD 的关系

### 11.1 可直接沿用的部分

#### PRD-001

PRD-001 对 Soul Prototype 的定义总体成立，可作为平台原型生产层继续沿用。

#### PRD-003

PRD-003 对 Issue 作为任务载体的定义总体成立，但需要补充其项目归属语义。

### 11.2 需要修订的部分

#### PRD-000

需要新增或修订以下统一术语：

- Project
- Project Memory
- Project Resource
- Project Workflow
- Member

并修正“数字员工实例”的定义，从“用户订阅并派发”改为“项目订阅并派发，成员在项目中使用”。

#### PRD-002

PRD-002 需要做结构性修订，核心变化如下：

1. 订阅主体从个人改为 Project。
2. 实例归属从个人改为 Project。
3. 配额模型从单用户优先改为项目优先。
4. 审批对象从“某人是否能拿到实例”改为“某项目是否可以引入该实例”。
5. 实例上下文从个人上下文改为项目上下文 + 个人操作审计。

#### PRD-003

PRD-003 需要补充：

1. Issue 必须归属于 Project。
2. Issue 列表和看板应优先按 Project 组织。
3. Issue 结果默认沉淀到 Project Memory 或 Project Output 中。

## 12. v1.0 的关键决策

### 12.1 明确的决策

1. Project 是一级实体，不是标签或分组。
2. 数字员工实例先分配给 Project，再由成员在项目内使用。
3. Soul Prototype 是平台资产，不直接承担最终任务执行。
4. Issue 是项目内任务协作载体，不是私聊会话。
5. 项目知识必须独立于 Soul 初始记忆存在。
6. Project、Agent Instance、Issue 构成数字军团OS的主业务闭环。

### 12.2 暂不在 v1.0 定死的事项

1. Project 是否成为独立一级导航模块。
2. 一个 Issue 后续是否允许多 Agent 协同。
3. Project Workflow 是否要在 Phase 1 产品化为工作流编排器。
4. 项目级记忆与原型级 RAG 在技术实现层如何解耦。

## 14. 总结

核心概念模型 v1.0 的本质不是给现有 PRD 做一个术语补丁，而是明确数字军团OS的真实业务骨架：

```text
平台生产数字员工原型
→ 项目引入数字员工实例
→ 项目成员通过 Issue 驱动执行
→ 结果沉淀回项目
```

这个模型一旦成立，后续产品结构、权限设计、实例分发、任务执行、知识管理都会变得更一致。

反过来，如果继续沿用“个人订阅个人实例”的隐含前提，后续所有项目协同、权限治理和知识沉淀都会越来越别扭。

因此，本文件建议作为数字军团OS后续 PRD 修订和架构设计的统一上位模型。
