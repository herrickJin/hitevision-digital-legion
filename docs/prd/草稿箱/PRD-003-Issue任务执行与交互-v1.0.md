## 1. 一句话结论

PRD-003 要解决的问题不是“让用户和 Agent 聊天”，而是把数字员工实例的任务协作正式收敛到 Issue 中，形成从任务发起、执行透明、结果交付到异常处理的完整闭环。

---

## 2. 为什么现在做

PRD-001 解决了数字员工怎么生产，PRD-002 解决了数字员工怎么订阅和派发，但产品目前只完成了“拥有数字员工”，还没有完成“真正使用数字员工”。

当前缺口主要有四个：

1. 用户不知道如何向数字员工下发任务。
2. 数字员工执行过程黑盒，用户无法判断进度和质量。
3. 结果没有正式交付位，过程与结果割裂。
4. 职责越界时没有清晰的人机协作机制。

如果 PRD-003 不成立，前两期能力无法形成真实业务闭环。

---

## 3. 目标用户与问题定义

### 3.1 目标用户

- 已订阅并派发数字员工的业务用户
- 任务发起人
- 任务跟进人
- 最终结果接收人
- 需要做任务协调的人类管理者

### 3.2 典型场景

用户围绕一个明确业务目标，把任务交给某个已派发数字员工处理，希望在执行过程中知道：

- 任务是否已开始
- 当前做到哪一步
- 是否需要补充信息
- 是否超出职责边界
- 最终结果在哪里

### 3.3 当前痛点

- 任务输入方式不清晰，用户表达成本高。
- 执行过程不可见，用户缺乏信任。
- 最终结果没有正式承接区。
- 越界时容易出现该拒绝的不拒绝、该上报的不汇报。

### 3.4 当前替代方式

如果继续靠聊天、IM、人工转述、文档协作承接，会导致：

- 过程分散
- 上下文不完整
- 状态不可追踪
- 责任边界不清
- 结果难归档

## 4. 产品目标

本期只做一件事：把“单 Agent、单任务、单 Issue”的主链路打通。

核心目标：

1. 用户可以低门槛地下发任务。
2. 用户可以看到任务执行过程，而不是只看最终黑盒结果。
3. 最终结果以正式交付形式沉淀。
4. 职责越界时系统明确拒绝，并进入“人类决策在环”的协调机制。

---

## 5. 成功标准

### 主指标

- 已派发数字员工的周任务发起率
- 任务完成率
- 结果被采纳率

### 辅助指标

- 任务创建成功率
- 结构化字段修正率
- 执行过程查看率
- 结果二次追问率

### 护栏指标

- 错误执行率
- 越权执行率
- 用户主动取消率
- 过程日志阅读放弃率

## 6. 范围边界

### 6.1 本次做

1. 基于 Issue 发起数字员工任务。
2. 支持自由输入 + 自动结构化提取 + 人工修正。
3. 支持任务状态流转。
4. 支持执行过程展示、工具调用摘要、阶段性产出展示。
5. 支持最终结果标准模板输出。
6. 支持补充信息请求与恢复执行。
7. 支持职责越界拒绝、推荐具体 Agent 实例，并汇报给人类确认。
8. 支持继续追问、重试、转交、取消等后续动作。

### 6.2 本次不做

1. 多 Agent 自动协同编排。
2. 复杂工作流配置器。
3. 跨 Issue 批量调度。
4. Agent 自主扩展职责边界。
5. 自动化质量评分系统。

### 6.3 边界原则

本期方案必须坚持“人类决策在环”。尤其在职责越界和任务转交场景下，系统只做识别、说明、推荐、汇报，不做自动拍板和自动编排。

---

## 7. 方案总览

整体方案是：把 Issue 定义为数字员工任务协作的唯一载体。

用户围绕一个 Issue 完成以下闭环：

1. 发起任务
2. 确认任务结构化信息
3. 跟踪执行过程
4. 接收中间反馈或补充请求
5. 接收最终结果
6. 在职责越界或失败时得到明确处理路径
7. 由人类决定是否协调、转交或重试

关键不是展示多少信息，而是确保用户始终知道：

- 当前发生了什么
- 系统为什么这么处理
- 下一步应该由谁做决定

---

## 8. 核心产品原则

1. Issue 是唯一任务载体。
2. 用户输入优先自然语言，系统负责结构化整理。
3. 执行过程默认透明，但展示以用户可理解摘要为主。
4. 工具调用信息按角色分层展示。
5. 最终结果必须与过程日志分层，并支持标准模板输出。
6. 职责越界必须明确拒绝，并汇报给人类确认，不允许系统自动转交。

---

## 9. 核心流程

### 9.1 主流程

1. 用户选择已派发数字员工实例。
2. 用户输入任务描述。
3. 系统自动提取结构化字段。
4. 用户确认后创建 Issue。
5. Agent 开始执行。
6. 用户在 Issue 中查看状态、过程和产出。
7. 任务进入以下分支之一：
   - 已完成
   - 等待补充信息
   - 已拒绝（职责越界）
   - 执行失败
   - 重试中
   - 已转交
8. 用户或管理者基于结果继续追问、协调、重试或关闭任务。

### 9.2 职责越界处理流程

1. 当前 Agent 识别任务越界。
2. 当前 Agent 停止执行并输出拒绝原因。
3. 系统推荐可接手的具体 Agent 实例。
4. 系统向人类汇报当前情况。
5. 由人类决定：
   - 不转交，结束当前任务
   - 转交给某个具体实例
   - 先协调后再决定
6. 若确认转交，任务进入“已转交”或“待人工协调后转交”链路。

### 9.3 补充信息流程

`待开始 -> 执行中 -> 等待补充信息 -> 执行中 -> 已完成/执行失败/已拒绝`

### 9.4 重试流程

`执行失败 -> 重试中 -> 执行中 -> 已完成/执行失败/已拒绝`

## 10. 页面结构

### 10.1 任务发起页

页面目标：让用户低门槛发起任务，同时把自然语言转换成可执行任务对象。

页面应包含：

- Agent 基本信息
- 自然语言输入框
- 自动提取的结构化字段
- 附件与补充信息区
- 创建任务 / 保存草稿按钮

关键规则：

- 自动提取结果必须允许编辑。
- 低置信字段必须提醒。
- 缺失核心目标不允许提交。

### 10.2 Issue执行主页面

页面目标：成为任务执行期间的统一工作台。

页面应包含：

- 顶部状态栏
- 左侧任务信息区
- 中部执行时间线
- 右侧结果 / 异常 / 待处理区

用户在此页应能直接知道：

- 当前任务内容
- 执行进度
- 是否需要补充信息
- 是否发生职责越界
- 最终结果在哪里

### 10.3 等待补充信息态

需要明确展示：

- 缺什么
- 为什么缺
- 如何补
- 补完后恢复执行

这是任务中断态，不是新任务入口。

### 10.4 职责越界态

这不是报错页，而是“拒绝 + 汇报 + 推荐 + 人类确认”的协作页。

页面应展示：

- 当前任务为什么越界
- 当前 Agent 为什么不处理
- 推荐接手的具体实例
- 汇报给人类的说明
- 人类可执行动作：确认转交 / 暂不转交 / 发起协调

### 10.5 最终结果区

最终结果必须从执行日志中被单独拎出来，形成正式交付区。

结果区至少包括：

- 结果摘要
- 正式正文
- 关键结论
- 附件 / 引用
- 模板类型
- 后续动作

## 11. 功能设计

### 11.1 任务创建

系统自动提取：

- 任务目标
- 输出要求
- 优先级
- 时间要求
- 风险提示

用户可修正后提交。核心要求不是"自动提取多聪明"，而是"结果可控、可改、可确认"。

### 11.2 structured_brief 与 Soul 约束映射

系统自动提取结构化字段后，提交用户确认前，需将各字段与 Soul 原型定义（PRD-001 3.3）进行约束校验。

#### 映射与校验规则

| structured_brief 字段 | 映射到 Soul 原型定义（PRD-001 3.3） | 校验规则 |
|----------------------|-----------------------------------|---------|
| `goal` | 职责范围（负责什么/不负责什么） | goal 不得超出 Soul 职责范围；超出时走职责越界流程（11.9） |
| `expected_output_type` | 输出规范（支持的输出格式和模板类型） | 提取的输出类型必须在 Soul 输出规范支持范围内；不在范围内时提示用户修正 |
| `constraints` | 安全与约束（操作红线、数据访问限制） | 用户约束不得与 Soul 安全约束冲突；冲突时以 Soul 约束为准，并告知用户 |
| `risk_notes` | 安全与约束 + 职责范围的低置信度处理策略 | 自动匹配 Soul 风险等级定义，高置信直接执行，低置信标记后执行 |
| `context_notes` | 关联上下文对象 + 初始记忆/RAG | 检查用户引用的上下文是否在该实例已绑定的范围内 |

#### 校验时机

任务创建时，结构化提取完成后、用户确认提交前。

#### 校验失败处理

- **一般冲突**（输出类型不匹配、上下文超出范围、约束冲突）：不阻止创建，标记冲突项并要求用户确认。
- **严重冲突**（goal 超出 Soul 职责范围）：直接触发职责越界流程（11.9），不进入执行。

### 11.3 状态管理

正式状态集：

- 待开始
- 执行中
- 等待补充信息
- 已完成
- 执行失败
- 已拒绝（职责越界）
- 待人工确认转交
- 已转交
- 重试中
- 已取消

要求：

- 所有状态变化都要有时间戳和原因。
- 用户能区分失败、越界、待确认、已转交、重试中。

### 11.4 实例状态联动

Issue 的执行依赖 PRD-002 中数字员工实例的运行状态。当实例状态变更时，Issue 自动触发对应流转。

#### 联动规则

| 实例状态变更（PRD-002） | 对正在执行 Issue 的影响 | 对新 Issue 创建 |
|------------------------|----------------------|----------------|
| 运行中（正常） | 无影响 | 允许创建 |
| 已停止 | 正在执行 Issue 暂停，状态进入 `waiting_for_input`，原因标记「实例已停止」 | 禁止创建 |
| 更新中 | 正在执行 Issue 暂停，更新完成后自动恢复 | 禁止创建 |
| 更新失败（回滚后） | 恢复执行 | 允许创建 |
| 原型已归档（Soul 回收中） | 所有进行中 Issue 进入 `failed`，原因标记「实例 Soul 已回收」 | 禁止创建 |

#### 恢复规则

- 实例从「已停止」恢复为「运行中」时，暂停的 Issue 自动恢复为 `running`。
- 实例从「更新中」完成更新后，暂停的 Issue 自动恢复为 `running`。
- 实例进入「原型已归档」后不可恢复，关联 Issue 终态不可逆。

#### 新增流转

- `running -> waiting_for_input`（原因：instance_paused）
- `waiting_for_input -> running`（原因：instance_resumed，自动触发）
- `running -> failed`（原因：instance_soul_recycled，不可逆）

### 11.5 Issue 超时规则

| 场景 | 超时阈值 | 超时后处理 |
|------|---------|-----------|
| 执行中无事件产出 | 30 分钟 | 状态进入 `failed`，原因 `execution_timeout` |
| 等待补充信息无响应 | 72 小时 | 状态进入 `cancelled`，原因 `input_timeout` |
| 待人工确认转交无响应 | 7 天 | 状态保持不变，系统发送催办通知 |
| 草稿未提交 | 30 天 | 自动清理，进入 `cancelled` |

[假设] 内部使用阶段 30 分钟无事件产出通常意味着 Agent 执行异常。信心度：7/10。验证方式：上线后跟踪 execution_timeout 事件占比，如 > 5% 需要重新评估阈值。

### 11.6 执行过程展示

对用户可见的信息包括：

- 流式输出
- 中间步骤
- 工具调用摘要
- 阶段性产出

展示原则：

- 普通用户默认看摘要。
- 高权限角色可查看更多工具调用细节。
- 不直接把底层噪声日志暴露给所有人。

### 11.7 最终结果交付

最终结果必须支持标准模板输出，采用「内置类型 + 可扩展自定义类型」机制。

#### 内置模板类型

| 模板类型 | 说明 | 典型场景 |
|---------|------|---------|
| PRD | 产品需求文档 | 产品规划任务 |
| 报告 | 分析/调研报告 | 调研、竞品分析 |
| 清单 | 检查/待办清单 | 评审、部署前检查 |
| 代码 | 代码片段/文件 | 开发任务 |
| 数据查询结果 | 结构化数据 | 查询、统计任务 |
| 方案对比 | 多方案对比表 | 决策支持任务 |

#### 自定义模板类型

Soul 原型在 PRD-001 能力配置时可定义专属输出模板，PRD-003 在结果交付时按原型配置渲染。自定义模板需包含：模板名称、字段定义、渲染格式。

#### 结果内容包括：

- 标准模板正文
- 摘要
- 关键结论
- 引用材料
- 完成时间

### 11.8 补充信息交互

补充请求至少告诉用户：

- 缺什么
- 为什么需要
- 示例怎么填

补充后恢复原任务执行，不新建任务。

### 11.9 职责越界处理

一旦判断越界：

- 当前 Agent 停止执行
- 状态变为已拒绝（职责越界）
- 系统推荐具体 Agent 实例
- 系统向人类汇报
- 任务进入待人工确认转交
- 人类决定是否转交或协调

禁止系统自动直接转交。

### 11.10 追问链机制

用户在已完成 Issue 上继续追问时，系统不回退 `completed` 状态，而是创建新 Issue 形成追问链。

规则：

- 用户在 `completed` 的 Issue 上追问，系统自动创建新 Issue，标记 `parent_issue_id`。
- 新 Issue 自动继承原 Issue 的 `agent_instance_id` 和 `context_notes`。
- 原 Issue 状态保持 `completed` 不变，关系标记为 `followed_by`。
- 追问链深度不限，但单链超过 5 个 Issue 时系统提示建议发起新的独立任务。

### 11.11 重试限制

`failed -> retrying -> running -> failed` 循环最多 3 次。

- 重试次数记录在 `TaskIssue.retry_count` 字段。
- 第 3 次失败后，状态保持 `failed` 且不再允许重试。
- 系统提示用户：补充信息、更换任务描述或联系平台管理员。

建议核心对象：

### 12.2 TaskIssue 核心字段

- `goal`
- `expected_output_type`
- `constraints`
- `context_notes`
- `risk_notes`
- `confidence_map`

### 12.4 状态机定稿

状态集：

- `draft`
- `pending`
- `running`
- `waiting_for_input`
- `completed`
- `failed`
- `rejected_out_of_scope`
- `waiting_human_transfer_decision`
- `reassigned`
- `retrying`
- `cancelled`

关键流转：

- `draft -> pending`
- `pending -> running`
- `running -> waiting_for_input`
- `waiting_for_input -> running`
- `running -> completed`
- `running -> failed`
- `failed -> retrying`（最多 3 次，见 11.11）
- `retrying -> running`
- `running -> rejected_out_of_scope`
- `rejected_out_of_scope -> waiting_human_transfer_decision`
- `waiting_human_transfer_decision -> reassigned`
- `pending/running/waiting_for_input/retrying -> cancelled`
- `running -> waiting_for_input`（原因：instance_paused，见 11.4）
- `waiting_for_input -> running`（原因：instance_resumed，自动触发）
- `running -> failed`（原因：instance_soul_recycled / execution_timeout，不可逆）

原则：

- 完成态不能回退为执行中。追问走追问链，见 11.10。
- 越界后不能由系统自动继续执行。
- 已转交代表人类已做出明确转交决定。
- 重试上限 3 次，超出后终态不可逆。

## 13. 接口定稿原则

接口正式拆为两层：

### 13.1 前台接口

面向用户界面与业务系统，负责页面交互和状态查询：

- `CreateTaskIssue`
- `GetTaskIssueDetail`
- `ListTaskIssuesByAgent`
- `SaveTaskDraft`
- `GetTaskTimeline`
- `ReplyInputRequest`
- `ConfirmTaskTransfer`
- `RequestHumanCoordination`
- `RetryTaskIssue`
- `CancelTaskIssue`
- `GetFinalResultDetail`
- `CreateFollowupTask`

### 13.2 Runtime 内部协议

面向 Agent runtime 执行链路，负责事件、状态和产出回传：

- `StartTaskExecution`
- `UpdateTaskStatus`
- `EmitTaskEvent`
- `CreateInputRequest`
- `RejectTaskOutOfScope`
- `RecommendTransferInstances`
- `PublishStageArtifact`
- `PublishFinalResult`
- `ReportExecutionFailure`

原则：

- 前台接口只暴露业务需要。
- Runtime 内部协议承接执行细节和系统协同。

## 15. 风险与判断

### 主要风险

1. 过程展示过多，噪声压过结果。
2. 结构化提取不准，增加修正成本。
3. 页面信息量过大，导致理解门槛上升。
4. 人工确认链路若过重，会影响转交效率。
5. 模板结果输出如果约束过死，可能影响不同任务类型适配。

### 缓解思路

- 默认展示摘要，细节按角色分层展开。
- 对低置信字段显式提醒。
- 统一时间线承载执行过程。
- 人工确认只卡越界转交，不卡正常执行。
- 模板输出支持通用框架 + 类型化扩展。

### 当前判断

这期方案成立的关键不是能力炫技，而是边界清楚、流程顺畅、结果可消费、人类责任明确。

## 17. 定稿结论

PRD-003 到这里已经完成定稿，当前版本的核心决策点如下：

1. Issue 是唯一任务载体。
2. 输入方式采用自由描述 + 自动提取 + 人工修正。
3. 执行过程默认透明。
4. 工具调用信息按角色分层展示。
5. 最终结果支持标准模板输出。
6. 职责越界时推荐具体实例，但必须由人类确认是否转交。
7. 状态机新增已转交、重试中、待人工确认转交等状态。
8. 接口拆为前台接口和 runtime 内部协议两层。

这版可以作为 PRD-003 的正式定稿进入评审和后续执行拆解。
