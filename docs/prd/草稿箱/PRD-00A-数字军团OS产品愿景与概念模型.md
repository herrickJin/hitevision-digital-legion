## 1. 当前判断

数字军团OS 值得继续推进，但现有 PRD 对它的定位偏窄：当前文档更像在描述“Agent 原型管理 + 市场派发 + Issue 执行”，还没有完整表达“统一定义数字员工、分布式运行 Agent 实例、以人机工作台驱动研发组织协同与企业落地”的 OS 级方案。

本文件的目标不是替代 PRD，也不是直接给出技术架构，而是先回答四个产品层问题：

1. 数字军团OS 到底是什么，不是什么。
2. 数字员工在组织中扮演什么角色。
3. Body / Soul / 实例 / Issue / 工作台 / Wiki / Memory / 工作流 / 设备之间是什么关系。
4. 后续 PRD 应该围绕哪条主线重写叙事和范围。

## 2. 产品愿景

### 2.1 一句话定位

数字军团OS 是一套面向企业产研组织的 AI 组织操作系统：统一定义数字员工，分布式运行 Agent 实例，并通过人机工作台、知识记忆、流程接入和组织治理，让人类员工与数字员工共同完成研发、产品、交付和企业落地任务。

### 2.2 核心目标

数字军团OS 的核心目标不是“生产更多 Agent”，而是提高产研一体化效率，用更少的人力完成更多可验收、可追踪、可复用的任务。

更具体地说，数字军团OS 要让企业具备以下能力：

1. 把优秀员工的工作方式沉淀为可复用的数字员工定义。
2. 让数字员工以可治理、可审计、可派发的实例形式进入真实工作场景。
3. 让人类通过统一工作台向数字员工下发任务、跟踪过程、接收结果、处理越界。
4. 让数字员工持续使用企业 Wiki、项目上下文、历史 Memory 和第三方系统能力。
5. 让鸿合自有软件、硬件、集控平台与数字员工形成联动，但不把硬件联动作为第一阶段主链路。

### 2.3 价值判断

如果只做 Soul 编排、市场上架和订阅派发，产品价值会停留在“Agent 管理工具”；只有当数字员工进入组织工作台、承接真实任务、产生可验证结果、持续积累组织知识时，数字军团OS 才成立。

## 3. 问题定义

- 目标用户：鸿合内部产研组织、业务专家、平台治理人员，以及后续企业客户中的研发、产品、交付、运营和 IT 管理者。
- 使用场景：人类员工需要把产品需求、研发任务、项目交付、知识查询、流程执行、设备联动等任务交给数字员工协同处理。
- 核心痛点：当前 Agent 能力容易停留在 prompt、脚本或单点工具层面，无法形成组织级定义、运行、协同、治理、知识沉淀和结果验收闭环。
- 当前替代方案：人工沟通、IM 聊天、零散 Agent、单独的自动化脚本、知识库检索、项目管理工具和人工审批流程。
- 为什么现在做：大模型和 Agent runtime 已经具备基础执行能力，但企业落地的瓶颈从“能不能调用模型”转向“能不能把 AI 员工纳入组织协同和治理体系”。

## 4. 概念边界

### 4.1 数字军团OS 是什么

数字军团OS 是一个组织级 AI 协同系统，包含六个核心能力域：

| 能力域 | 产品定义 | 解决的问题 | 与现有 PRD 的关系 |
|---|---|---|---|
| 数字员工定义与运行生命周期 | 定义、测试、审核、版本化 Soul，绑定 Body 与能力集，并将数字员工派发到 PC、Linux、云端或企业运行环境 | 数字员工从哪里来、如何保证质量、在哪里运行、如何管理生命周期 | PRD-001 已覆盖定义生产，PRD-002 已覆盖派发，但需要补充“定义 + 分布式运行”的 OS 视角 |
| AI 组织治理 | 管理数字员工角色、权限、编制、职责边界、审计、评价和风险 | 数字员工如何进入组织而不失控 | 现有 PRD 仅有审核/审批，需要独立强化 |
| 人机交互工作台 | 由 Soul 身份驱动的角色工作面，不同数字员工拥有不同工作面模块；Issue 作为跨工作面的任务通信枢纽 | 用户如何真正使用数字员工 | PRD-003 有 Issue 主链路，但缺少工作台两层架构和角色工作面定义 |
| 企业级 LLM Wiki + Memory | 为数字员工提供组织知识、项目上下文、长期记忆和经验沉淀 | 数字员工如何理解企业并持续变强 | PRD-001 的基础 RAG 只是起点 |
| 第三方平台工作流接入 | 将研发、项目、IM、知识库、代码、办公、审批等系统流程化接入 | 数字员工如何执行真实业务流程 | PRD-003 有任务执行入口，但缺少工作流连接层 |
| 鸿合软硬件一体联动 | 连接大屏、自研白板、录播、集控平台等鸿合软硬件能力 | 数字员工如何进入鸿合特有场景 | 概念上必须保留，阶段实现优先级可低 |

说明：前五个能力域是 OS 成立的基础；鸿合软硬件一体联动是鸿合差异化能力域，短期不应阻塞主链路，但不能从概念模型中删除。

### 4.2 数字军团OS 不是什么

数字军团OS 不是单纯的：

1. Prompt 管理工具。
2. Agent 应用市场。
3. 自动化脚本平台。
4. 企业知识库问答系统。
5. 多 Agent 聊天室。
6. 硬件控制平台。

这些都可能是数字军团OS 的局部能力，但任何一个单点能力都不能代表数字军团OS。

## 5. 核心概念模型

### 5.1 总体模型

```text
企业组织目标
  ↓
AI 组织治理
  ↓
数字员工定义层：Body + Soul（人格 + 职能范围 + 技能集 + 工具集 + 约束 + 初始记忆）
  ↓
数字员工运行层：实例 + 运行环境 + 权限 + 上下文 + 状态
  ↓
人机协作层：角色工作台（由 Soul 工具集驱动）+ Issue（跨工作面枢纽）+ 过程透明 + 结果交付 + 人类决策在环
  ↓
知识与流程层：Wiki + Memory + 第三方平台工作流 + 鸿合软硬件联动
  ↓
可验收的业务结果
```

### 5.2 核心对象关系

```text
Body 是可运行的通用智能体空壳
Soul 是让 Body 成为某类数字员工的领域灵魂
  Soul 包含：人格定义 + 职能范围 + 技能 + 工具集 + 约束 + 初始记忆
  Soul 中的工具集决定了数字员工工作台的工作面模块结构
Soul 原型是可审核、可版本化、可复用的数字员工定义
数字员工实例是 Soul 原型在某个运行环境和用户上下文中的运行体
工作台是由 Soul 身份驱动的角色工作面，不是 Issue 的 UI 壳
  工作台包含两层：交互枢纽层（Issue）+ 角色工作面（Workstation Surface）
  角色工作面的模块结构由 Soul 原型中的工具集决定
  用户可在实例层面自由组合、增减工作面模块
Issue 是人类 ↔ Agent、Agent ↔ Agent 之间的任务通信枢纽
  Issue 是跨工作面的统一协议层
  转交的 Issue 在源工作面显示"已转交"状态，在目标工作面成为待执行任务
Wiki 是企业显性知识系统
Memory 是数字员工和组织在任务执行中沉淀的长期经验
Workflow 是数字员工调用第三方平台完成真实业务动作的流程连接
Device / Hardware 是鸿合软硬件场景中可被感知、展示、操作或编排的对象
```

### 5.3 Body、Soul 与数字员工

Body 解决"能不能运行"的问题；Soul 解决"像谁工作、负责什么、如何判断、如何输出、使用什么工具"的问题；数字员工实例解决"这个数字员工在谁的上下文中、在哪个环境里、以什么权限工作"的问题。

Soul 的完整结构：

| Soul 组成部分 | 解决的问题 | 与工作台的关系 |
|---|---|---|
| 人格定义 | 这个数字员工的思维模式、沟通风格、判断倾向 | 决定工作台中交互对话的风格 |
| 职能范围 | 这个数字员工负责什么领域、不负责什么 | 决定工作台的模块边界 |
| 技能集 | 这个数字员工能执行哪些类型的任务 | 决定工作台中可触发的动作类型 |
| 工具集 | 这个数字员工需要使用哪些工具 | **直接决定工作台的工作面模块构成** |
| 约束 | 这个数字员工的权限边界、越界规则、审批要求 | 决定工作台中的护栏机制 |
| 初始记忆 | 这个数字员工启动时携带的上下文和知识 | 决定工作台初始状态中的预设数据 |

**关键决策：工具集 → 工作面模块的映射**

Soul 原型中定义的工具集，直接决定该数字员工工作台的工作面模块结构。例如：

- 产品经理 Soul 的工具集包含「需求管理工具、PRD 编辑器、优先级排序工具、进度看板」→ 工作面预置需求池、PRD 文档区、优先级排序、需求进度追踪
- 前端研发 Soul 的工具集包含「代码编辑器、组件库、接口调试工具、视觉走查工具」→ 工作面预置代码视图、组件库、接口文档对照、视觉走查
- 后端研发 Soul 的工具集包含「代码编辑器、API 定义工具、测试运行器、部署工具」→ 工作面预置代码仓库视图、API 定义、测试覆盖、部署状态

用户在实例层面可以自由组合、增减工作面模块——Soul 定义默认结构，实例允许个性化调整。

因此，数字员工不应被定义为"一个上架商品"。更准确的定义是：

> 数字员工是由 Soul 定义专业身份、职责边界和工具集，由 Body 提供运行能力，由实例承接具体用户上下文，通过角色工作面参与组织协同，并以 Issue 作为跨工作面任务通信枢纽的 AI 同事。

### 5.4 工作台：两层架构

工作台不是 Issue 的 UI 壳，也不是一个通用的聊天页。工作台是由数字员工的 Soul 身份驱动的角色工作面，不同角色的数字员工拥有完全不同的工作面模块和视图。

工作台包含两层：

**第一层：交互枢纽层（Issue）**

Issue 是人类 ↔ Agent、Agent ↔ Agent 之间的任务通信枢纽。它解决的是"谁在什么上下文中，对谁，说了什么，要求做什么，结果是什么"的协议问题。

- Issue 是跨角色、跨实例的统一协议层，所有角色共用。
- Issue 不属于任何一个工作面，但每个工作面都可以看到与自己相关的 Issue。

**第二层：角色工作面（Workstation Surface）**

角色工作面由 Soul 原型中的工具集决定模块构成。不同角色的数字员工，工作面完全不同：

| 数字员工角色 | 工作面核心模块 | Issue 在其中的位置 |
|---|---|---|
| 产品经理 | 需求池看板、PRD 文档区、优先级排序、需求进度追踪、竞品/市场数据 | 需求澄清对话、方案讨论、验收反馈 |
| 前端研发 | 代码视图、组件库、接口文档对照、构建状态、视觉走查 | 任务拆解、实现讨论、Code Review 反馈 |
| 后端研发 | 代码仓库视图、API 定义、测试覆盖、部署状态、性能监控 | 功能实现、Bug 修复、架构决策讨论 |
| 项目经理 | 项目甘特图、里程碑、资源分配、风险看板、交付追踪 | 任务分派、进度确认、阻塞升级 |

**跨工作面协作：Issue 转交机制**

当产品经理 Agent 完成需求定义，需要把任务交给前端研发 Agent 时：
- 产品经理的工作面内可以直接看到"已转交"的状态
- 具体执行在前端研发的工作面中进行
- Issue 作为跨工作面的唯一枢纽，承载上下文传递

这意味着：各自工作面独立，通过 Issue 作为跨工作面的唯一协议层。Phase 1 不需要跨工作面的"指挥台"视图。

PRD-003 的"单 Agent、单任务、单 Issue"仍是正确的第一阶段主链路，但必须放在"角色工作面"叙事中——Issue 是工作面中的一个交互通道，不是工作台的全部。

### 5.5 Wiki 与 Memory

Wiki 和 Memory 不能混为一谈：

| 概念 | 定义 | 示例 | 主要责任 |
|---|---|---|---|
| Wiki | 企业显性知识、规范、文档、流程和事实来源 | 产品规范、研发规范、项目资料、FAQ | 提供可信知识来源 |
| Memory | 数字员工在执行任务中形成的长期经验、用户偏好、项目惯例和历史上下文 | 某项目常用技术栈、某用户偏好的 PRD 风格、某类任务的复盘结论 | 提供持续个性化和经验积累 |
| RAG | 从 Wiki 或资料中检索相关内容供模型使用的技术路径 | 文档切分、向量检索、引用来源 | 是实现手段，不是完整产品概念 |

PRD-001 中的“初始记忆与基础 RAG”只适合作为 Phase 1 起点；长期概念应升级为“企业级 LLM Wiki + Memory”。

### 5.6 工作流与第三方平台

数字员工要产生真实业务价值，必须能进入企业已有工作流，而不是只在自身系统内回答问题。

第三方平台工作流接入包含：

1. 研发工具：代码仓库、Issue 系统、CI/CD、测试平台。
2. 项目协作：项目管理、文档、IM、日程、审批。
3. 企业系统：权限、组织、知识库、数据平台。
4. 鸿合内部系统：自研白板、集控平台、设备管理平台等。

产品边界上，应优先定义“可编排的流程节点、权限边界、审计记录和失败处理”，具体 API 和集成方式由技术方案后续确定。

### 5.7 鸿合软硬件一体联动

鸿合软硬件联动是差异化能力，但当前阶段不应成为主路径阻塞项。

概念上需要保留三类联动：

1. 输入联动：数字员工接收来自大屏、白板、录播、集控平台等设备或软件的上下文输入。
2. 输出联动：数字员工的产出可以展示、分发或部署到鸿合设备与软件环境。
3. 操作联动：在授权范围内，数字员工可触发设备级、集控级或软件级操作。

阶段判断：Phase 1 只需要在概念、权限和接口边界上预留，不建议把具体硬件控制作为 P0。

## 6. 产品主线重述

后续 PRD 的叙事主线应从“Agent 原型如何上架”调整为“数字员工如何进入组织并完成任务”。

建议主线如下：

```text
定义数字员工（Soul：人格 + 职能范围 + 技能集 + 工具集 + 约束 + 初始记忆）
→ 定义工作面（由 Soul 工具集映射为角色工作台模块）
→ 治理数字员工
→ 派发数字员工实例
→ 在角色工作台中使用数字员工
→ 通过 Issue 完成任务闭环（Issue 是跨工作面的通信枢纽）
→ 使用 Wiki / Memory / Workflow 提升持续能力
→ 在鸿合软硬件场景中形成差异化落地
```

对应到现有 PRD：

| 文档 | 当前定位 | 建议修正后的定位 |
|---|---|---|
| PRD-000 | 术语表与跨文档映射 | 补充 OS 级术语：工作台、AI 组织治理、Wiki、Memory、Workflow、Device |
| PRD-001 | Soul 可视化编排与原型管理 | 数字员工定义、培养、测试和治理的生产线 |
| PRD-002 | 数字员工市场 | 数字员工实例派发与运行生命周期管理，不应只强调市场商品 |
| PRD-003 | Issue任务执行与交互 | 人机工作台中的首个任务闭环，不应被理解为聊天页 |
| 后续新增 | 暂无 | AI 组织治理、企业 Wiki + Memory、工作流接入、鸿合软硬件联动 |

## 7. 成功标准

### 7.1 主指标

- 产研任务中由数字员工参与完成的任务占比。
- 数字员工任务完成率。
- 数字员工结果被人类采纳或进入下一步流程的比例。
- 单位人力可承接任务量提升幅度。

### 7.2 辅助指标

- 可复用数字员工数量。
- 数字员工实例派发成功率。
- Issue 创建成功率和任务结构化确认率。
- Wiki / Memory 命中率与引用采纳率。
- 数字员工越界识别与人工处理闭环率。
- 第三方工作流调用成功率。

### 7.3 护栏指标

- 越权执行率。
- 错误工具调用率。
- 错误知识引用率。
- 未经确认的自动转交率。
- 用户主动停用或删除实例比例。
- 高风险操作未审计比例。

## 8. 范围与非目标

### 8.1 本次做

本概念模型阶段只做：

1. 统一数字军团OS 的产品愿景。
2. 明确数字员工不是“上架商品”，而是进入组织协作的 AI 同事。
3. 明确五个基础能力域和一个鸿合差异化能力域。
4. 定义核心对象关系和 PRD 修订方向。
5. 明确硬件联动保留在概念模型中，但实现优先级降低。

### 8.2 本次不做

本概念模型阶段不做：

1. 不输出详细技术架构。
2. 不定义数据库表、接口协议、部署拓扑。
3. 不承诺多 Agent 自动协同的完整方案。
4. 不把硬件设备控制列为 Phase 1 必做。
5. 不直接替代 PRD-001/002/003 的详细功能设计。
6. 不定义商业化计费和外部 SaaS 销售策略。

## 9. 假设

- [假设] 第一阶段核心目标仍然是服务鸿合内部产研组织，而不是立即做对外 SaaS 商业化。  
  信心度：8/10  
  验证方式：由业务负责人确认 Phase 1 的目标客户、验收对象和预算来源。

- [假设] 数字员工的优先落地角色仍以产品经理、前端研发、后端研发等产研角色为主。  
  信心度：7/10  
  验证方式：盘点首批 3-5 个数字员工模板与真实任务清单。

- [假设] 鸿合软硬件联动是中长期差异化能力，短期需要概念和接口预留，但不进入 P0 主链路。  
  信心度：9/10  
  验证方式：在下一轮路线图评审中确认硬件联动的业务优先级和依赖团队投入。

- [假设] 组织治理能力会成为规模化使用的关键瓶颈，不能只依赖 Soul 审核和市场审批。  
  信心度：8/10  
  验证方式：当数字员工数量超过 10 个、实例超过 50 个时，观察权限、职责、审计和质量问题是否显著增加。

- [假设] 用户对数字员工的信任主要来自过程透明、结果可验收和越界可控，而不是来自“像人聊天”。  
  信心度：8/10  
  验证方式：在试点中比较任务完成率、结果采纳率、过程查看率和聊天满意度之间的相关性。

## 10. 风险

- 风险等级：high  
  风险描述：如果继续按“Agent 管理平台”叙事推进，团队可能优先建设原型、市场、审批等后台能力，但真实用户仍然不知道如何用数字员工完成任务。  
  缓解方式：把“人机工作台 + Issue 任务闭环”提升为主线，所有后台能力都要服务于任务完成。

- 风险等级：high  
  风险描述：如果缺少 AI 组织治理，数字员工数量增长后会出现职责重叠、权限失控、质量不可评估、实例无人维护等问题。  
  缓解方式：在 PRD-000 和后续 PRD 中补充角色、编制、权限、审计、评价、归档和责任人机制。

- 风险等级：medium  
  风险描述：如果把 Wiki、Memory、RAG 混为一谈，会导致知识能力被低估为“上传文档检索”，无法支撑长期组织经验沉淀。  
  缓解方式：在概念和 PRD 中明确 Wiki 是知识来源、Memory 是经验沉淀、RAG 是技术路径。

- 风险等级：medium  
  风险描述：鸿合软硬件联动范围过早展开，会拉高依赖复杂度，拖慢数字员工主链路验证。  
  缓解方式：概念保留、接口预留、权限先行，具体设备控制能力放到后续阶段。

- 风险等级：medium  
  风险描述：如果过早追求多 Agent 自动协同，可能在单 Agent 任务闭环尚未稳定前放大质量和责任边界问题。  
  缓解方式：Phase 1 坚持单 Agent、单任务、单 Issue、人类决策在环。

## 11. 待确认问题

2. 人机工作台第一阶段是独立产品入口，还是嵌入现有研发协作系统。

5. 鸿合硬件联动的首个示范场景是大屏展示、白板输入、集控操作，还是设备运维。
