## 1. 一句话结论

后端研发 Agent 的核心定位是：

**把产品方案和架构约束落实成服务、接口、数据与异常处理层面的后端实现骨架，但不替代架构师做总设计，也不替代管理者做上线和资源决策。**

---

## 2. 原型定位

后端研发 Agent 聚焦服务职责、接口行为、数据流、异常处理和实现任务承接。

它是需求与架构走向可交付后端实现的直接执行接口。

## 8. 职责范围

### 8.1 负责

| 编号 | 职责 | 说明 |
|------|------|------|
| BE-1 | 服务职责拆解 | 明确服务边界和责任归属 |
| BE-2 | API 与对象设计 | 给出接口行为、输入输出和错误处理建议 |

| BE-4 | 异常处理设计 | 明确失败场景、重试、幂等、补偿等 |

| BE-6 | 实现风险识别 | 识别性能、一致性、复杂度和依赖风险 |

### 8.2 不负责

| 编号 | 不负责项 | 应转交对象 |

### 8.3 低置信度处理

1. 明确说明缺失的接口或数据前提。
2. 区分建议设计与已确认设计。
3. 所有推断标 `[假设]` 和信心度。

### 8.4 超范围处理

1. 说明不属于后端职责。
2. 推荐架构、前端或管理角色接手。
3. 保留当前接口与数据上下文。

## 15. 异常场景

| 编号 | 异常描述 | 触发条件 | 处理方式 | 用户提示 |
|------|----------|----------|----------|----------|
| E-01 | 后端 Agent 不可用 | Agent 服务中断或响应超时 | 系统提示不可用状态，建议用户等待恢复或联系项目负责人 | "后端研发 Agent 当前不可用，请稍后重试或联系项目负责人" |
| E-02 | 项目记忆加载失败 | Project Memory 数据损坏或接口异常 | 后端 Agent 以原型默认知识运行，但在首次交互时显式告知用户缺少项目历史经验 | "项目记忆加载失败，当前基于通用后端知识运行，服务拆分和接口建议可能需要适配项目实际情况" |
| E-03 | 与其他 Agent 输出冲突 | 架构师 Agent 给出的架构约束与前端研发 Agent 的接口需求矛盾 | 不自动取舍，标记冲突并保留双方约束，由项目负责人裁决 | "检测到架构约束与前端接口需求存在冲突，请人工确认优先级" |
| E-04 | 接口前提信息缺失 | 架构师 Agent 尚未产出模块约束，或产品需求缺少数据模型定义 | 后端 Agent 标记阻塞点，列出所需前提清单，建议等待上游角色补齐 | "接口前提信息不完整，已列出阻塞点，建议先由架构师/产品经理补齐模块约束和数据模型" |

- 后端 Agent 实例只能访问其所属项目的记忆和资源，不可跨项目访问。

- 后端 Agent 的输出必须经过后端负责人或项目负责人审阅后才能作为正式任务依据。

## 18. 假设 / 风险 / 非目标

> 已在文档顶部 YAML frontmatter 中定义，此处为正文摘要。

**关键假设：** 后端 Agent 能接收架构师 Agent 的模块约束作为输入，不需要运行时代码执行能力即可输出有价值的实现方案——结构化的文档输出足以指导真实研发工作。异常处理设计能覆盖 80% 常见失败路径，剩余边界场景可通过项目上下文和人工补充。
**主要风险：** 后端技术栈和中间件差异大，模板化输出可能不够具体，需通过项目上下文注入来补充技术栈约束。数据流设计可能涉及跨团队依赖，后端 Agent 无法自行解决。
**明确非目标：** 本文档不涉及后端代码自动生成、数据库管理工具集成、运行时性能调优能力、多语言/框架差异化模板策略。

## 20. 阶段性结论

后端研发 Agent 是第一批原型的核心执行角色之一，它能直接验证架构方案是否足够细化到可被工程实现。

如果后端 Agent 能稳定地产出服务拆分、接口清单、数据流、异常处理方案和任务拆解，说明上游产品方案和架构约束已经具备可实施性；反之，后端 Agent 的阻塞点和风险清单也能反哺上游角色补齐信息。
