## 1. 一句话结论

《PRD-012-数字员工原型清单-v1.0》用于把当前第一批岗位型数字员工原型收敛成一份可浏览、可选型、可持续扩展的总览索引。

它不是替代各岗位详细文档，而是回答三个问题：

1. 当前已经定义了哪些数字员工原型。
2. 每个原型解决什么问题、服务谁、处于协作链路哪个位置。
3. 第一批原型组合起来后，是否足以支撑一个最小可用的项目协作闭环。

---

## 2. 清单用途

这份清单主要服务四类场景：

1. 给员工工坊做冷启动原型目录。
2. 给市场做后续上架对象的总览底册。
3. 给项目负责人做选型参考。
4. 给后续新原型扩展提供统一入口。

## 8. 第一批原型组合的闭环能力

这一批原型组合起来，已经能形成一个最小可用的项目协作闭环：

```text
产品经理 Agent
→ 架构师 Agent
→ 前端研发 Agent / 后端研发 Agent
→ 测试工程师 Agent
```

> 项目协同（状态跟踪、风险协调、阶段汇报等）由人类项目负责人负责，不设数字 PMO 角色。

它覆盖了：

1. 需求收敛
2. 技术方案
3. 工程承接
4. 质量验证

这意味着第一批原型已经具备验证 `Project → Agent Instance → Issue` 主链路的条件。

---

## 9. 当前边界与缺口

虽然第一批原型已经形成闭环，但仍有明显边界：

1. 还没有独立的设计类 Agent。
2. 还没有独立的运维 / 运行时类 Agent。
3. 还没有独立的数据分析 / 运营类 Agent。
4. 还没有定义多 Agent 自动协作协议。
5. 还没有数字化的项目协同角色（当前由人类项目负责人承担）。

因此，v1.0 更适合内部项目协作场景，不适合直接外推为完整企业岗位体系。

---

## 10. 扩展建议

下一批原型建议按以下顺序扩展：

1. 设计师 Agent
2. 运维 / SRE Agent
3. 数据分析 Agent
4. 运营 Agent
5. 客服 / 支持 Agent
6. 项目助理 PMO Agent（当前不纳入第一批，待项目协同需求明确后再评估）

扩展原则保持不变：

1. 一人一档
2. 全部继承 PRD-005-Agent原型定义通用模板-v1.0.md
3. 所有原型必须显式定义职责边界和测试用例

## 11. 员工工坊与市场承接建议

### 11.1 员工工坊承接

建议员工工坊先以上述 5 个岗位型原型作为第一批冷启动模板。

### 11.2 员工市场承接

建议市场中的展示逻辑优先增加以下信息：

1. 原型定位
2. 主要产出物
3. 不负责边界
4. 适用场景
5. 项目中推荐搭配使用的其他 Agent

这样用户选型时不会只看"名字"，而能看见真实协作价值。

## 16. 假设 / 风险 / 非目标

> 已在文档顶部 YAML frontmatter 中定义，此处为正文摘要。

**关键假设：** 第一批 5 个岗位原型足以覆盖最小项目协作闭环；员工工坊和市场能直接消费清单中的结构化信息。
**主要风险：** 闭环假设未经真实项目验证，可能被推翻；清单增长后管理复杂度上升。
**明确非目标：** 不在此定义第二批原型内容，不定义协作协议，不定义版本管理和定价分发机制。
