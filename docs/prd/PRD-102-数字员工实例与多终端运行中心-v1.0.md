## 1. 问题陈述

### 1.1 当前情况

数字员工原型即使被定义出来，如果不能被项目申请、审批、派发到具体载体并持续维护，其价值仍停留在静态资产层。

### 1.2 用户痛点

1. 项目成员不知道如何为项目获得一个真正可运行的数字员工实例。
2. 不同终端和环境之间缺少统一派发模型。
3. 高风险实例申请、更新和删除缺乏治理闭环。
4. 多终端场景下，运行能力、工具能力和权限能力不一致，容易产生混乱。

### 1.3 业务影响

如果实例中心缺位，数字员工会停留在定义层，无法进入日常工作；如果多终端运行模型缺位，平台会在 PC、云端、移动端和设备侧快速分裂。

---

## 2. 目标与方案

### 2.1 目标

建立从“数字员工原型”到“项目内数字员工实例”的标准派发与治理中心，并形成统一的多终端运行模型。

### 2.2 方案概述

```text
浏览原型
→ 选择目标 Project 并申请实例
→ 风险分级与审批
→ 项目配额/项目权限/项目上下文/载体校验
→ 派发为 Project 内实例
→ 启动与运行
→ 更新/回滚/删除/回收
```

### 2.3 成功指标

> [假设] 以下指标的数值目标基于同类产品经验和初步估算，尚未建立实际基线。试点阶段需采集真实数据修正目标值。

1. 实例派发成功率大于等于 90%。
2. 自动通过类申请从提交到项目实例创建时间小于等于 5 分钟。
3. 派发失败原因结构化归因覆盖率等于 100%。
4. 重要更新 7 日确认率大于等于 70%。

---

## 3. 用户与场景

### 3.1 目标用户

| 用户 | 诉求 |
|---|---|
| 项目负责人 / 授权成员 | 为项目快速获得合适实例 |
| 平台管理员 | 治理派发、审批、配额、回收与更新 |
| 审批人 | 控制高风险实例申请与升级 |

### 3.2 关键场景

1. 项目负责人为项目申请一个前端研发数字员工到本地 PC。
2. 项目授权成员为项目申请一个后端研发数字员工到 Linux 或云端容器。
3. 项目负责人把项目实例运行载体从 PC 迁移到云端。
4. 原型更新后，项目实例收到需重审更新通知。
5. 因安全原因回收某类实例。

---

## 4. 功能需求

### 4.1 原型浏览与申请

1. 支持列表、搜索、分类、标签、风险等级和载体筛选。
2. 详情页展示职责、能力、权限、支持载体、更新记录和审批规则。
3. 申请时必须选择目标 Project、运行环境、终端载体、用途和项目上下文绑定项。

#### Project 前置条件

实例申请依赖目标 Project 至少已具备以下 P0 字段或能力：

1. 项目名称。
2. 项目负责人（Owner）。
3. 项目成员列表与角色身份。
4. 项目数字员工实例池。
5. 项目绑定 Wiki 文档集。
6. Project Memory 空间。
7. 项目状态。

若目标 Project 缺失以上任一 P0 必备项，系统不得完成实例派发。

### 4.2 风险分级与审批

1. 基于项目数据权限、工具权限、载体风险、运行环境和项目上下文范围做风险分级。
2. 支持自动通过、人工审批、双人审批。
3. 无法判定时默认进入人工审批。

### 4.3 多终端运行模型

支持以下载体类型：

1. PC 客户端。
2. Linux 主机。
3. 云端容器。
4. 移动端。
5. 设备侧或边缘侧运行载体。

系统必须支持：

1. 载体能力分级。
2. 原型与载体兼容性映射。
3. 不同载体的能力降级说明。
4. 跨载体迁移与重新校验。

### 4.4 实例状态机

#### 4.4.1 Phase 1 状态集

| 编号 | 状态名 | 状态类型 | 说明 |
|---|---|---|---|
| S1 | 待审批 | 初始态 | 实例申请提交后等待审批 |
| S2 | 待派发 | 中间态 | 审批通过，等待系统完成派发 |
| S3 | 运行中 | 中间态 | 实例已派发并启动运行 |
| S4 | 已停止 | 终态（条件性） | 主动停止或异常停止，可重启 |
| S5 | 已删除 | 终态 | 主动删除，元数据按策略保留 |
| S6 | 已回收 | 终态 | 原型归档后系统自动回收，或管理员强制回收 |
| S7 | 已拒绝 | 终态 | 审批拒绝或用户取消申请 |

状态命名规则：终态使用"已"前缀，中间态和初始态不使用前缀。此规则与 Issue 状态机保持一致。

#### 4.4.2 状态转换规则

| 源状态 | 目标状态 | 触发条件 | 触发方 |
|---|---|---|---|
| 待审批 | 待派发 | 低风险自动通过或人工审批通过 | 系统 / 人类 |
| 待审批 | 已拒绝 | 审批拒绝 | 人类 |
| 待审批 | 已拒绝 | 用户取消申请，等同于已拒绝 | 人类 |
| 待派发 | 运行中 | 系统完成派发并启动 | 系统 |
| 待派发 | 已拒绝 | 派发失败且不可重试 | 系统 |
| 运行中 | 已停止 | 用户主动停止或系统异常停止 | 人类 / 系统 |
| 运行中 | 已删除 | 用户主动删除 | 人类 |
| 运行中 | 已回收 | 原型归档触发回收或管理员强制回收 | 系统 / 人类 |
| 已停止 | 运行中 | 用户重启 | 人类 |
| 已停止 | 已删除 | 用户主动删除 | 人类 |
| 已停止 | 已回收 | 原型归档触发回收或管理员强制回收 | 系统 / 人类 |

转换约束：

1. 待审批为唯一初始态，实例创建后必须进入此状态。
2. 已删除、已回收、已拒绝为绝对终态，不可逆转。
3. 已停止为条件性终态，仅允许通过"重启"转换回运行中，或进一步转换到已删除、已回收。
4. 运行中与已停止之间的循环转换不设次数上限，但每次转换必须记录审计日志。
5. 不在上述表格中的状态转换均视为非法，系统必须拒绝并记录异常。

#### 4.4.3 实例管理要求

1. 系统必须基于本状态机实施实例的全生命周期管控，任何状态变更必须经过合法转换校验。
2. 状态变更事件必须写入审计日志，记录变更前后状态、触发方、触发时间和关联操作。
3. 运行状态监控与心跳机制仅对"运行中"状态生效，心跳超时自动转为"已停止"并触发告警。
4. 项目实例侧支持有限自定义白名单，但不得绕过状态机转换约束。
5. 已删除状态的实例，其元数据、审计日志和任务历史必须按策略保留，保留期满后方可物理清除。
6. 已回收状态的实例资源必须立即释放，元数据按保留策略归档。

```text
状态流转示意：

待审批 ──通过──→ 待派发 ──派发成功──→ 运行中 ⇄ 已停止
  │                 │                    │  │      │  │
  │                 │                    │  │      │  ↓
  │                 │                    │  │      │ 已删除
  │                 ↓                    │  ↓      │
  │              已拒绝(派发失败)         │ 已回收←─┘
  ↓                                   │
已拒绝(审批拒绝/取消)                  ↓
                                   已停止→已回收
```

### 4.5 实例生命周期管理

1. 派发、启动、停止、删除、回收。
2. 运行状态监控与心跳。
3. 项目实例侧有限自定义白名单。
4. 删除后元数据、审计日志和任务历史按策略保留。

### 4.6 更新与回滚

1. Patch、Minor、Major 更新处理规则。
2. 支持强制更新。
3. 更新前创建实例快照。
4. 更新失败自动回滚。
5. 原型归档后进入实例回收流程。

---

## 5. 设计要求

1. 详情页必须清晰展示“支持哪些载体”和“不同载体的差异”。
2. 申请页不能只展示审批要求，还要展示运行成本和能力差异提示。
3. 项目数字员工池页面必须突出实例状态、运行载体、版本、待处理动作。
4. 个人视角可提供“我关注的数字员工”，但不得作为实例归属中心。

---

## 6. 技术需求

1. 依赖 runtime 管理服务、权限系统、配额与容量服务、通知服务、审计日志服务。
2. 需定义统一项目实例对象模型、载体能力模型和迁移模型。
3. 需支持运行状态上报、异常状态回传、更新快照和回滚。
4. 需支持不同载体的接入适配层。

---

## 7. 实施计划

| 阶段 | 交付内容 |
|---|---|
| M1 | 原型浏览与检索视图、详情页、实例申请单 |
| M2 | 风险分级、审批流、配额校验 |
| M3 | 多载体派发、启动、停止、删除 |
| M4 | 更新、回滚、迁移、回收 |

资源建议：

1. 产品 1 人。
2. 前端 1 至 2 人。
3. 后端 2 人。
4. 平台/runtime 1 至 2 人。

---

## 8. 风险与缓解

| 风险 | 描述 | 缓解方式 |
|---|---|---|
| 载体差异导致实例模型碎片化 | 各端实现口径不一致 | 先定义统一运行抽象和载体能力分级 |
| 申请流程过长 | 影响项目引入实例的效率 | 低风险默认自动通过，高风险才走人工流 |
| 更新导致实例不可用 | 项目成员信任下降 | 更新前快照 + 更新后自动回滚 |
| 回收策略过硬 | 项目任务和项目上下文丢失 | 增加缓冲期、通知与数据保留策略 |

---

## 9. 验收标准

1. 实例申请必须覆盖审批、项目配额、项目上下文和载体校验。
2. 派发失败必须返回结构化失败原因。
3. 多终端载体必须至少支持能力差异说明和基础迁移规则。
4. 更新失败后必须可恢复到上一次稳定快照。
5. 每个数字员工实例必须且只能归属一个 Project。
