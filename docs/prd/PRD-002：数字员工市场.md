# PRD-002：数字员工市场

版本：v0.2 草稿  
产品：数字军团OS  
范围：Phase 1  
状态：待评审  
更新时间：2026-05-13

## 1. 背景与目标

### 1.1 背景

PRD-001 已定义“数字员工原型”的生产与治理流程：核心管理员或授权业务专家通过 Soul 编排、Body 绑定、能力配置、基础 RAG、测试沙箱和人工审核，产出可上架的数字员工原型。

PRD-002 承接 PRD-001 的“已上架原型”，解决后续分发问题：产研用户如何发现数字员工、申请订阅、获得实例，并在 Soul 原型更新后安全同步到自己的实例。

如果没有数字员工市场，会出现以下问题：

- 已沉淀的数字员工原型无法被产研用户发现和复用。
- 用户不知道有哪些 Agent 可用、适合什么场景、需要什么权限。
- Agent 分发靠人工沟通，无法形成申请、审批、派发、更新、回收的闭环。
- Soul 原型持续迭代后，已派发实例无法感知新版本，容易出现能力割裂。
- 实例归属、权限边界、资源配额不清晰，后续设计和开发会出现歧义。

### 1.2 战略目标

建立内部数字员工市场，让“核心人员生产 Agent 原型”与“产研用户使用 Agent 实例”之间形成可控闭环。

Phase 1 的目标不是做对外 SaaS 商业化市场，也不是做复杂计费体系，而是先打通：

```text
已上架数字员工原型
→ 市场展示
→ 浏览搜索
→ 申请订阅
→ 自动通过 / 人工审批
→ 实例派发
→ 实例管理
→ 版本更新提示
→ 失活回收 / 删除归档
```

### 1.3 成功指标

| 指标类型 | 指标 | 目标值 | 衡量周期 |
|----------|------|--------|----------|
| 产品指标 | 市场可用 Agent 数量 | >= 3 个：产品经理、前端研发、后端研发 Agent | 上线后 4 周 |
| 产品指标 | 详情页到申请页转化率 | >= 30% | 上线后 4 周 |
| 产品指标 | 审批通过后实例派发成功率 | >= 90% | 上线后 4 周 |
| 产品指标 | 自动通过类申请派发时效 | <= 5 分钟 | 上线后 4 周 |
| 产品指标 | 重要更新 7 日确认率 | >= 70% | 上线后 8 周 |
| 治理指标 | 审批超时占比 | < 20% | 上线后 6 周 |
| 治理指标 | 派发失败原因结构化归因覆盖率 | = 100% | 上线后 4 周 |
| 治理指标 | 30 天未活跃实例占比 | < 25% | 上线后 8 周 |
| 治理指标 | 删除 / 回收实例占比可观测 | = 100% 有记录 | 持续监控 |

## 2. 用户与场景

### 2.1 目标用户

| 用户群 | 描述 | 核心诉求 |
|--------|------|----------|
| 产研使用者 | 需要使用数字员工协助工作的人 | 找到合适 Agent，快速获得可运行实例 |
| 核心创作者 | 创建并维护 Soul 原型的人 | 让自己维护的 Agent 被正确展示、订阅和更新 |
| 平台管理员 | 负责市场治理、权限、容量和异常处理 | 控制分发风险，保证派发、更新、回收可追踪 |
| 审批人 | 创作者 / 维护者 / 平台管理员 | 对高权限或敏感 Agent 的订阅申请做判断 |

### 2.2 核心场景

场景 1：浏览和发现数字员工

- 作为产研用户
- 我希望在市场中按角色、场景、能力、运行环境、审批方式搜索数字员工
- 以便快速找到适合当前工作的 Agent

场景 2：申请订阅数字员工

- 作为产研用户
- 我希望查看 Agent 的职责、能力、权限、适用场景、更新记录和审批要求后提交申请
- 以便获得一个绑定到自己上下文的数字员工实例

场景 3：自动派发低风险实例

- 作为产研用户
- 我申请低风险 Agent 后，希望系统自动通过并派发实例
- 以便不用等待人工审批

场景 4：审批高权限实例

- 作为审批人
- 我希望看到申请用途、目标运行环境、所需权限、风险等级和历史审批记录
- 以便决定是否允许该用户获得实例

场景 5：管理已订阅实例

- 作为产研用户
- 我希望启动、停止、删除已派发实例，并做有限自定义
- 以便让数字员工适配我的项目上下文，但不破坏 Soul 原型的一致性

场景 6：处理 Soul 更新

- 作为产研用户
- 我希望在原型 Soul 发布新版本时收到更新提示，并根据兼容性规则选择更新、补审批或暂缓
- 以便在保留历史上下文的前提下获得新能力

## 3. 产品方案

### 3.1 市场商品定义

市场中的“商品”不是一个运行中的实例，而是一个可申请的数字员工原型。

```text
市场 Agent = 已上架 Soul 原型 + Body 绑定信息 + 市场展示信息 + 订阅规则 + 派发策略 + 配额策略 + 更新策略

用户获得的是：
数字员工实例 = 市场 Agent 派发结果 + 用户上下文 + 目标运行环境 + 实例级配置
```

每个市场 Agent 至少包含：

- 基础信息：名称、简介、角色分类、适用场景、标签。
- 来源信息：创建者、维护者、所属业务域、当前版本。
- 能力信息：职责范围、能力集、可用工具、支持运行环境。
- 权限信息：需要的数据权限、工具权限、风险等级、是否需要审批。
- 订阅信息：自动通过/需审批、审批人、申请材料、实例数量限制。
- 更新信息：版本历史、最近更新内容、更新影响范围、是否存在强制更新。
- 配额信息：单用户、单团队、单 Agent 的实例上限。

### 3.3 浏览搜索逻辑

一期采用结构化搜索，不做复杂推荐。

P0 支持：

- 关键词：名称、简介、标签、能力描述。
- 分类：产品、前端、后端、设计、架构、通用。
- 筛选：运行环境（PC / Linux）、是否需审批、风险等级、更新时间、创建者。
- 排序：管理员置顶 > 关键词匹配 > 分类匹配 > 最近更新 > 已订阅数量。

兜底规则：无搜索结果时，展示同分类热门 Agent 和最近上架 Agent。

### 3.4 申请与审批状态机

申请单状态定义：

```text
草稿
→ 已提交
→ 待审批
→ 待补充信息
→ 审批通过
→ 审批驳回
→ 派发中
→ 已派发
→ 派发失败
→ 已过期
→ 已取消
```

状态规则：

- 低风险申请提交后可直接跳过“待审批”，进入“审批通过”。
- 被要求补充用途、权限、目标运行环境时，状态进入“待补充信息”。
- 审批通过后自动进入“派发中”。
- 审批通过但长时间未完成派发时，可进入“已过期”，需重新发起。

### 3.5 审批规则显式化

审批不再只写“低风险自动通过，高风险人工审批”，而是采用显式风险规则。

#### 风险分级

| 等级 | 判定条件 | 审批方式 | 默认审批人 | SLA | 超时升级 |
|------|----------|----------|------------|-----|----------|
| L1 低风险 | 只读知识、低风险工具、无敏感数据、无生产权限 | 自动通过 | 无 | 即时 | 无 |
| L2 中风险 | 项目级知识库、可写非生产工具、Linux 运行环境、可选扩展工具 | 人工审批 | 创作者/维护者 | 4 小时 | 超时升级给平台管理员 |
| L3 高风险 | 敏感数据、生产权限、高风险工具、跨团队高影响运行环境 | 双人审批 | 创作者/维护者 + 平台管理员 | 1 个工作日 | 先催办，再升级给平台管理员兜底 |

#### 风险判定字段

系统至少基于以下字段自动判定风险等级：

- 数据权限级别：公开 / 内部 / 项目级 / 敏感 / 生产。
- 工具权限级别：只读 / 非生产写入 / 生产写入 / 高风险运维。
- 运行环境：PC / 普通 Linux / 高权限 Linux。
- 上下文绑定对象：个人知识库 / 项目知识库 / 跨团队共享数据。
- 是否启用高风险可选工具。

兜底规则：

- 无法判断风险等级时，默认进入人工审批。
- 新增权限项高于当前申请范围时，必须重新审批。

### 3.6 实例归属模型

#### 归属类型

Phase 1 只做一种 P0 归属：`个人私有实例`。

定义如下：

- 实例归属于申请人本人。
- 申请人和平台管理员可见该实例。
- 实例可以绑定项目上下文，但不等于“项目共享实例”。
- 项目成员默认不能看到彼此的个人实例。
- 项目共享实例保留到 P2，不进入一期主流程。

#### 同一 Agent 的多实例规则

- 默认允许同一用户为同一 Agent 在不同运行环境各保留 1 个活跃实例。
- 默认不允许同一用户在同一运行环境重复创建相同 Agent 的多个活跃实例。
- 如确有需要，可由平台管理员调整配额。

#### 删除与保留

- 用户删除实例后，实例立刻停止运行，状态变为“已删除”。
- 实例元数据、审批记录、操作审计日志保留 180 天。
- 对话记录、任务历史、工作记录默认保留 30 天用于恢复和审计，30 天后按平台归档或清理策略处理。

### 3.7 配额与容量策略

资源配额前置到 P0，不等市场上线后再补。

#### 默认配额

| 配额维度 | 默认值 | 说明 |
|----------|--------|------|
| 单用户-单 Agent 活跃实例数 | 1 个 / 运行环境 | 同一用户可各保留 1 个 PC 和 1 个 Linux 实例 |
| 单用户总活跃实例数 | 5 个 | 跨所有 Agent 累计 |
| 单团队总活跃实例数 | 20 个 | 默认可配置 |
| 高风险 Agent 团队活跃实例数 | 3 个 | 默认更严格 |

#### 容量不足处理

- 配额超限：直接拒绝申请，并提示释放实例或申请扩容。
- 运行时资源不足：进入派发队列。
- 自动通过类申请排队超过 30 分钟：通知用户，状态标记为“派发超时”。
- 人工审批通过类申请排队超过 4 小时：通知用户和平台管理员，允许手动重试或更换运行环境。

#### 派发队列结果

- 派发成功：进入“已派发”。
- 派发失败：记录失败原因并结构化归因。
- 派发超时：进入“已过期”或等待用户重试。

### 3.8 实例派发流程

```text
申请通过
→ 校验配额
→ 校验 Body / Soul / 能力 / 运行时兼容性
→ 校验权限与审批范围是否一致
→ 绑定用户上下文、知识库、项目对象
→ 在目标运行时创建实例
→ 返回实例 ID、状态、版本、入口
→ 进入“我的数字员工”列表
```

失败归因必须结构化记录为：

- quota_exceeded
- runtime_unavailable
- permission_missing
- compatibility_failed
- dispatch_timeout
- system_error

### 3.9 有限自定义白名单

有限自定义必须白名单化，避免和原型定义混淆。

#### 允许修改且无需重启

- 默认绑定的项目上下文。
- 默认绑定的知识库集合。
- 通知方式和提醒偏好。
- 实例显示名称或备注。

#### 允许修改但需要重启实例

- 切换同风险等级的运行环境。
- 启用或禁用低风险可选工具。
- 调整允许访问的非敏感上下文对象。

#### 允许修改但需要重新审批

- 新增更高权限工具。
- 绑定敏感数据源或更高权限知识库。
- 切换到更高权限运行环境。
- 任何导致风险等级上升的配置变更。

#### 严禁修改

- 原型人格定义。
- 原型职责边界。
- 共享 Soul 的能力定义。
- 市场展示信息。
- 审批规则。
- 风险等级标记。

### 3.10 实例生命周期

实例状态定义：

```text
待派发
→ 派发中
→ 运行中
→ 已停止
→ 更新可用
→ 待重审更新
→ 更新中
→ 更新失败
→ 已删除
```

说明：

- “更新可用”表示有新版本但用户尚未确认。
- “待重审更新”表示新版本需要更高权限，不能直接更新。
- “更新失败”必须支持一键回滚到更新前稳定快照。

### 3.11 更新策略与兼容性规则

更新不只是“提示用户更新”，还要显式处理兼容性和权限变化。

#### 更新方式

1. 整体更新：实例的 Soul 配置整体替换为新版本。
2. 模块级更新：仅更新能力集、工具、初始记忆、输出规范等模块。
3. 暂不更新：继续保留当前版本。

#### 必须保留的实例资产

- 实例 ID。
- 用户绑定的知识库和项目上下文。
- 对话记忆。
- 工作记录。
- 任务历史。
- 用户侧有限自定义配置。

#### 兼容性规则

| 场景 | 处理方式 |
|------|----------|
| 新版本新增更高权限 | 不允许直接更新，状态进入“待重审更新”，走补审批流程 |
| 新版本运行环境不兼容 | 不允许原地更新，提示迁移到支持的运行环境或继续停留旧版本 |
| 新版本只涉及低风险知识/能力优化 | 允许用户直接确认更新 |
| 新版本是安全或合规修复 | 可标记为“强制更新” |

#### 强制更新规则

- 仅限安全、合规、严重错误修复。
- 强制更新需由平台管理员标记。
- 强制更新提供 72 小时缓冲期。
- 缓冲期后未更新的实例进入“受限模式”：不可发起新任务，但保留查看历史和执行更新。

#### 回滚粒度

- 回滚粒度为“单实例、单次更新尝试”回滚到更新前完整快照。
- 一期不做字段级回滚。
- 模块级更新失败时，仍回滚到该次更新前完整稳定版本，避免状态不一致。

### 3.12 Not in Scope

本期不做：

- 对外 SaaS 商业化入口。
- Token 计费、充值、套餐、账单。
- 项目共享实例。
- 多 Agent 自动协同编排。
- 字段级选择性更新。
- Android / iOS / 大屏运行时适配。
- 第三方开发者接入。

## 4. 策略设计

### 4.1 搜索与排序策略

输入信号：关键词、分类、标签、用户角色、运行环境、风险等级、更新时间、订阅数量。  
策略逻辑：管理员置顶 > 关键词匹配 > 分类匹配 > 最近更新 > 订阅数量。  
输出形式：市场列表排序结果。  
兜底规则：无搜索结果时展示同分类热门 Agent 和最近上架 Agent。

### 4.2 审批判定策略

输入信号：数据权限级别、工具权限级别、运行环境、上下文绑定对象、可选工具开关。  
策略逻辑：自动计算 L1 / L2 / L3 风险等级，并匹配审批方式、审批人、SLA、升级规则。  
输出形式：自动通过、待审批、待补充信息、驳回。  
兜底规则：无法判断风险时默认人工审批。

### 4.3 派发策略

输入信号：目标运行环境、Body 兼容性、Soul 能力依赖、用户权限、实例配额、运行时容量。  
策略逻辑：先校验配额与容量，再校验权限与兼容性，最后创建实例。  
输出形式：实例状态、入口、失败原因。  
兜底规则：资源不足时排队，超时后通知用户并进入超时状态。

### 4.4 更新策略

输入信号：新旧版本 diff、实例当前配置、用户自定义项、运行时兼容性、权限变化、安全标记。  
策略逻辑：先判断是否需要重审或强制更新，再决定整体更新、模块更新或阻断。  
输出形式：更新可用、待重审更新、更新成功、更新失败、受限模式。  
兜底规则：更新失败自动回滚到更新前稳定快照。

## 6. 风险与降级

| 风险 | 概率 | 影响 | 缓解方式 |
|------|------|------|----------|
| 审批规则不清，系统无法自动判断 | 中 | 高 | 用显式风险字段、审批矩阵、SLA 和升级规则固化 |
| 实例归属不清，造成越权可见 | 中 | 高 | Phase 1 明确只做个人私有实例 |
| 有限自定义越界，破坏原型一致性 | 中 | 中 | 白名单化可改项，风险上升即重审 |
| 高风险 Agent 被误自动派发 | 低 | 高 | 无法判断风险时默认人工审批 |
| 资源不足导致大量派发失败 | 中 | 高 | P0 引入配额和排队策略，并记录失败归因 |
| 更新兼容性差，导致实例不可用 | 中 | 高 | 先做权限/运行时兼容判断，再更新；失败自动回滚 |
| 强制更新引发用户反感 | 中 | 中 | 仅限安全/合规修复，并提供 72 小时缓冲期 |

## 8. 明确结论

1. PRD-002 只负责数字员工市场、订阅申请、审批、实例派发、实例管理、更新与回收治理。
2. 一期明确只做个人私有实例，不做项目共享实例。
3. 审批采用显式风险分级，不再停留在“低风险自动通过”的口头描述。
4. 有限自定义采用白名单机制，风险升高即触发重审。
5. 更新不仅要提示用户，还要处理权限提升、运行时不兼容、强制更新和实例级回滚。
6. 配额与容量策略属于 P0，不后置。
7. 治理指标必须和产品指标一起进入评审口径。
