## 1. 问题陈述

### 1.1 当前情况

当前企业内部对智能体的定义仍然偏零散，常见形式是 prompt、脚本、工具链组合或个人经验配置。这些能力可以跑通演示，却无法成为组织级资产。

### 1.2 用户痛点

1. 业务专家无法用结构化方式把专业工作方式沉淀成数字员工。
2. 同一类数字员工缺少统一职责边界、输出规范与权限约束。
3. 缺少测试、审核、版本、回滚和审计能力，导致数字员工质量不可控。
4. 多数字员工协同场景下，数字员工的角色定位和可转交边界没有被前置定义。

### 1.3 业务影响

如果没有定义中心，后续市场、实例、工作台和协同能力都会缺少统一源头，平台会退化成“临时能力拼装器”。

---

## 2. 目标与方案

### 2.1 目标

建立数字员工的标准化生产线，让核心管理员和授权业务专家可以定义、测试、审核、发布并持续维护数字员工原型。

### 2.2 方案概述

定义中心提供一套面向 Soul 原型的结构化生产流程：

```text
新建原型
→ 配置人格/职责/输出/约束
→ 绑定 Body 与能力
→ 配置初始记忆与上下文
→ 定义协同角色与转交边界
→ 校验与测试
→ 审核与上架
→ 版本迭代与归档
```

### 2.3 成功指标

> [假设] 以下指标的数值目标基于同类产品经验和初步估算，尚未建立实际基线。试点阶段需采集真实数据修正目标值。

1. 授权创作者创建原型成功率大于等于 80%。
2. 基础原型配置完成时间小于等于 30 分钟。
3. 提交审核原型测试通过率大于等于 70%。
4. 上架后因配置问题被回退比例小于等于 10%。

## 3. 用户与场景

### 3.1 目标用户

| 用户 | 诉求 |
|---|---|
| 核心管理员 | 平台级治理、Body 管理、上架审核、权限与审计 |
| 授权业务专家 | 在特定业务域内定义数字员工 |
| 审核人 | 评估数字员工质量、风险、职责和适用范围 |

### 3.2 关键场景

1. 定义产品经理数字员工原型。
2. 定义前端研发数字员工原型。
3. 给某个数字员工补充新的能力、知识与协同角色。
4. 对重大职责变更进行审核和版本升级。

---

## 4. 功能需求

### 4.1 原型基础定义

系统必须支持以下配置：

1. 基础信息：名称、角色、业务域、适用场景、负责人。
2. 人格定义：沟通风格、判断倾向、行为准则。
3. 职责范围：负责什么、不负责什么、越界如何处理。
4. 输出规范：模板类型、字段结构、格式要求。
5. 安全与约束：权限红线、风险边界、审批要求。

### 4.2 能力与运行定义

1. 绑定 Body。
2. 绑定 Skills、MCP、Function Calling、Tools。
3. 标注可运行的终端载体和运行环境。
4. 定义载体能力差异的降级规则。

### 4.3 上下文与知识定义

1. 配置关联上下文对象。
2. 配置初始记忆与基础 RAG。
3. 区分原型级知识和实例级动态记忆。
4. 支持引用来源、版本和负责人记录。

### 4.4 协同定义

1. 定义该数字员工在多数字员工协同中的角色定位。
2. 定义可接收任务类型。
3. 定义可转交角色范围。
4. 定义协同输入输出接口要求。

### 4.5 Soul 原型状态机

#### 4.5.1 Phase 1 状态集（8 状态）

| 状态 | 类型 | 说明 |
|------|------|------|
| 草稿 | 初始态 | 新建后保存，可编辑 |
| 待测试 | 中间态 | 配置完成提交测试 |
| 测试中 | 中间态 | 在沙箱中执行测试用例 |
| 待审核 | 中间态 | 测试通过提交审核 |
| 已上架 | 终态 | 审核通过后上架 |
| 已驳回 | 终态（条件性） | 审核驳回，创作者可修改后重新提交 |
| 已下架 | 终态 | 核心管理员主动下架或系统强制下架 |
| 已归档 | 终态 | 归档不再使用 |

#### 4.5.2 状态转换规则

| 从 | 到 | 触发者 | 触发条件 | 可逆 |
|---|---|---|---|---|
| 草稿 | 待测试 | 人类 | 创作者完成配置提交测试 | 否 |
| 待测试 | 测试中 | 系统 | 系统开始执行沙箱测试 | 否 |
| 测试中 | 待审核 | 系统 | 所有测试用例通过 | 否 |
| 测试中 | 草稿 | 系统 | 测试未通过，退回修改 | 是（创作者修改后可重新提交） |
| 待审核 | 已上架 | 人类 | 审核人通过 | 否 |
| 待审核 | 已驳回 | 人类 | 审核人驳回 | 是（创作者修改后重新提交） |
| 已驳回 | 待测试 | 人类 | 创作者修改后重新提交 | — |
| 已上架 | 已下架 | 人类/系统 | 核心管理员主动下架或系统强制下架 | 否 |
| 已上架 | 待测试 | 人类 | 版本升级后重新测试 | — |
| 已下架 | 已归档 | 人类 | 核心管理员归档 | 否 |
| 草稿 | 已归档 | 人类 | 创作者删除草稿 | 否 |

#### 4.5.3 测试与发布要求

1. 完整性校验：必填字段检查、配置结构校验。
2. 依赖兼容性校验：Body、Skills、MCP、Function Calling、Tools 绑定有效性。
3. 权限与运行时兼容性校验。
4. 测试沙箱执行职责内、职责外、工具调用、知识引用、协同转交测试。
5. 原型未通过校验或测试不得提交审核（参见 §9.2）。
6. 上架原型必须具备版本号、负责人、适用范围和风险说明（参见 §9.3）。

### 4.6 测试与发布

测试与发布的完整状态机定义见 §4.5。本节补充执行细节：

1. 测试结果需按"任务 - 输入 - 输出 - 工具调用 - 引用来源 - 耗时"结构展示（参见 §5.2）。
2. 提交审核时系统自动附加测试报告和配置快照。
3. 审核人可查看完整测试报告并给出通过或驳回意见。

### 4.7 版本管理

1. 支持 Major、Minor、Patch 版本规则。
2. 支持完整配置快照。
3. 支持历史版本查看与回滚。
4. 已上架版本不可直接修改。

---

## 5. 设计要求

1. 配置界面采用分步表单与模块化配置，不做自由画布。
2. 测试结果需按“任务 - 输入 - 输出 - 工具调用 - 引用来源 - 耗时”结构展示。
3. 职责边界与约束字段必须强提示，不允许被隐藏在次级配置中。

---

## 6. 技术需求

1. 依赖 Body 注册服务、能力注册中心、向量检索服务、测试沙箱、权限系统和审计日志服务。
2. 需定义统一 Soul 原型 schema。
3. 需定义原型与实例、原型与协同角色、原型与运行环境之间的关系模型。
4. 需支持配置快照与版本 diff。

---

## 7. 实施计划

| 阶段 | 交付内容 |
|---|---|
| M1 | 原型基础信息、人格、职责、输出规范配置 |
| M2 | Body 绑定、能力编排、上下文配置 |
| M3 | 初始记忆、RAG、测试沙箱 |
| M4 | 协同角色定义、审核流、版本管理 |

资源建议：

1. 产品 1 人。
2. 前端 1 至 2 人。
3. 后端 1 至 2 人。
4. AI/平台 1 人。

---

## 8. 风险与缓解

| 风险 | 描述 | 缓解方式 |
|---|---|---|
| 定义中心配置过重 | 业务专家难以完成配置 | 用模板、默认值、校验和分步流程降低复杂度 |
| 职责边界定义模糊 | 后续执行越界频发 | 强制配置职责内/职责外样例测试 |
| 多载体适配过早下沉到原型层细节 | 原型配置复杂度失控 | 用“支持载体 + 降级规则”而非细粒度硬编码 |
| 协同定义不清 | 多数字员工编排时责任混乱 | 在原型阶段明确协同角色与转交边界 |

---

## 9. 验收标准

1. 新建原型必须具备必填字段校验与保存草稿能力。
2. 原型未通过校验或测试不得提交审核。
3. 上架原型必须具备版本号、负责人、适用范围和风险说明。
4. 所有审核、上架、归档和回滚动作必须进入审计日志。
